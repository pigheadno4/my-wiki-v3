# Release notes

On this page, you can find the release notes for the following Adyen plugins:

* [Salesforce Commerce Cloud (SFCC)](/plugins/salesforce-commerce-cloud)
* [Salesforce Order Management System](/plugins/salesforce-order-management-system)
* [Shopware 6](/plugins/shopware-6)
* [NetSuite](/plugins/netsuite) and [NetSuite Reconciliation Bundle](/plugins/netsuite/reconciliation-bundle)
* [Cegid Retail Y2](/plugins/cegid-retail-y2)

For [Adobe Commerce](/plugins/adobe-commerce), from v9.9.1 onwards, we document the minor and patch releases exclusively on GitHub:

* [Adobe Commerce plugin](https://github.com/Adyen/adyen-magento2/releases)
* [Adobe Commerce express checkout module](https://github.com/Adyen/adyen-magento2-express-checkout/releases)

There is no fixed time period between our plugin releases. We release if we have an urgent fix, or when we have accumulated a certain amount of changes to release. We recommend upgrading your plugin when we release to benefit from new features and bug fixes.

For technical details about our [Salesforce Commerce Cloud](https://github.com/Adyen/adyen-salesforce-commerce-cloud/releases), and [Shopware 6](https://github.com/Adyen/adyen-shopware6/releases) releases, refer to the release notes on GitHub.

## 2026-08-24 — Adobe Commerce — Version 11.0.0

*\<p>For technical details about the changes in this release, refer to our release notes on \<a href="https\://github.com/Adyen/adyen-magento2/releases">Github\</a>.\</p>*

### Breaking Changes

* The `cc_type` field is no longer set in the `additional_information` field of the payment object. This affects headless integrations that read `cc_type` from order or payment data.

  * Previously: the plugin stored the card type under `additional_information.cc_type`.
  * Now: use the `ccType` field of the payment object instead, through `getCcType()`/`setCcType()` on `PaymentInterface`.

* The `sortAndFilterPaymentMethods()` method no longer returns `adyenPaymentMethodsResponse`. If you customized or extended `Helper/PaymentMethodsFilter.php`, use `PaymentMethods::getApiResponse()` to get the `/paymentMethods` response instead.

* The `/payments/details` REST endpoint and the `adyenPaymentDetails` GraphQL mutation no longer throw a generic exception on refusals, cancellations, or errors.

  * Previously: these cases all resulted in a generic `The payment is REFUSED.` exception, regardless of the actual reason.
  * Now: the endpoint returns a structured response, including a new `Cancelled` case. If your headless integration catches the generic exception, update it to parse the structured response instead.

* We refactored how the plugin determines a payment method's capture mode, and removed the `MANUAL_CAPTURE_SUPPORTED_PAYMENT_METHODS` constant from `PaymentMethodUtil`. If you customized capture-mode logic, review your customization.

The following change may be breaking if you have [customizations](/plugins/adobe-commerce/customize/):

* The plugin no longer populates `window.customerData` in the Multishipping Billing template; it now reads shopper data from `window.checkoutConfig`. If you built custom themes or scripts that relied on the `window.customerData` global variable in this template, update them.

### Improved

* Refactored duplicated logic between `PaymentResponseHandler::handlePaymentDetailsResponse()` and `CheckoutPaymentsResponseHandler::handle()`.

### New

* Added an optional cron job that cleans up stale `adyen_payment_response` table rows for orders in a final state (cancelled, complete, or closed). The cron job is disabled by default; enable it under **Testing and performance** in your Adobe Commerce admin panel. It runs nightly at midnight server time.
* Added support for the **NEA** (Japan) region in the **Front end resources region** setting.
* Upgraded to [Web Components/Drop-in v6.35.0](/online-payments/release-notes?title%5B0%5D=Web%2BComponents%2FDrop-in\&version%5B0%5D=6.35.0).
* The plugin now uses the [Adyen PHP API library v29.0.0](https://github.com/Adyen/adyen-php-api-library/releases/tag/v29.0.0).

### Removed

* Removed the unused `supports_auto_capture` configuration flag from `config.xml`. This flag had no functional implementation and was not a documented admin setting.

### Fixed

* We fixed a potential race condition in the Authorisation webhook handler on Adobe Commerce instances with synchronous database replication enabled, by comparing the order's `amountAuthorized`/`baseAmountAuthorized` fields directly.
* We fixed an inconsistency where invoice generation and order status could differ depending on the order in which `Authorisation` webhooks were processed, for orders paid with multiple payment methods that have different capture configurations (for example, one method set to immediate capture and another to manual capture). Invoices are now only generated after the full order amount has been authorized or captured.

### Updating

* Follow our [migration guide](/plugins/adobe-commerce/migrate-to-a-new-version) to learn about the steps required to update to this version. If you have customized the plugin, carefully review the breaking changes to make sure your customizations are compatible with the new version.

### Breaking Changes

The following changes may be breaking if you have [customizations](/plugins/adobe-commerce/customize/):

* [Web Components v6](/online-payments/release-notes/?utm_source=online-payments-release-notes\&utm_medium=banner\&utm_id=v6-banner\&title%5B0%5D=Web%2BComponents%2FDrop-in\&version%5B0%5D=6.0.0#releaseNote=2024-07-24-web-componentsdrop-in-6.0.0) introduces the following changes that may affect your integration if you customized our front end components, or are using your own front end.

  * Donations are now handled using the Campaign Manager. The back-end methods and configurations for donations are removed from the plugin. If you customized using legacy donation properties, remove them from your implementation.
  * [Credit card installments](/payment-methods/cards/credit-card-installments/) are now offered with Adyen's Card Component instead of the plugin's custom installment template. If you used the custom installment rendering logic, update your implementation to align with the Web Component.

* The plugin now supports [Adobe Commerce Monolog library v3](https://developer.adobe.com/commerce/php/development/backward-incompatible-changes/#upgraded-monologmonolog-dependency) that introduces stricter type declarations. See the [Monolog upgrade guide](https://github.com/Seldaek/monolog/blob/main/UPGRADE.md) to learn more about this version. If you have custom `Monolog` handlers, or extended our logging logic, this change may affect your integration. Our custom `LoggerHandler`:

  * Previously: extended `Monolog\Handler\AbstractProcessingHandler`.
  * Now: extends `Monolog\Logger. Uses`Monolog\LoggerFactory\` to generate a logger class.

* We refactored the order comment history logic to improve consistency across the module. If you implemented custom logic that extended or depended on the old logic for adding order comments, this change may affect your integration.

  * Previously: all order comments were in `arguments`, which led to issues in some cases.
  * Now: added an abstract handler for order status history.

* To mitigate security risks, the `PaymentResponseHandler` no longer returns the full `additionalData` object. If you built custom logic using other fields from the `additionalData` object, remove this logic.

  * Previously: you received the full `additionalData` object.
  * Now: you only receive the `action` object. To securely retrieve other `additionalData` fields, you can use your back end.

* For Boleto, the payment lifecycle now uses the `AdyenPaymentCommandPool` as other payment methods, and no longer requires Boleto specific commands. If you have custom logic that overrides or extends the old Boleto specific commands, update your implementation.

* We removed the methods in the plugin that was used for deprecated logic. Refer to the [list of replacements for deprecated logic on GitHub](https://github.com/Adyen/adyen-magento2/releases/tag/v10.0.0) to see the new methods that replace their functionality.

### Improved

* Refactored the `Adyen\Payment\Helper\Data` class to remove deprecated and unused methods, and created more appropriate helper classes for methods that are not related to data. The methods are now in the following classes:

  | Helper                  | Location                     |
  | ----------------------- | ---------------------------- |
  | `Helper\Config`         | API key handling helpers     |
  | `Helper\PlatformInfo`   | Platform metadata helpers    |
  | `Helper\PaymentMethods` | Payment method logic helpers |
  | `Helper\Locale`         | Locale helpers               |

### New

* The plugin now uses [Web Components v6](/online-payments/release-notes?title%5B0%5D=Web%20Components%2FDrop-in\&version%5B0%5D=6.0.0) that offer an enhanced user experience, improved performance, and increased design flexibility.

* [Donations](/plugins/adobe-commerce/set-up-the-payment-methods-in-adobe-commerce#donations) are now offered with the [Campaign Manager](/online-payments/donations) for round-up and fixed amount donations.

  * Previously: you configured donations in the Adyen Customer Area and the Adobe Commerce admin panel, and you had to enable donations.
  * Now: the Campaign Manager lets you manage your donation campaigns from your Adyen Customer Area in a simplified manner, and you no longer have to configure donations in your Adobe Commerce admin panel. Donations are enabled by default.

* Localization for payment method titles.

  * Previously: payment method titles were hardcoded in `config.xml`.
  * Now: the plugin front end uses the [/paymentMethods](https://docs.adyen.com/api-explorer/Checkout/latest/post/paymentMethods) response to display payment method tiles, and the titles are localized based on the `shopperLocale`.

For headless integrations, you no longer have to send the `brand_code` field when creating a data object for placing the order. To identify transaction variants, you can now use `getAlternativePaymentMethodTxVariant()`.

### Fixed

* The plugin no longer incorrectly sets the `cc_type` for alternative payment methods in the database with the `BRAND_CODE` value. The `cc_type` is only set for credit cards. Previously, this issue could lead to misclassification of payment methods in records and reports, and inconsistent payment processing.
