# C21 worker retrieval checks: docs-issuing-3d-secure-troubleshooting

Q1. How does this guide distinguish an authentication failure from a processing merchant's skipped-SCA soft decline?
Answer: Failed 3D Secure authentication blocks the payment before authorisation reaches Adyen, with no relayed authorisation or Payments-list entry according to this page (raw lines 31–35). When a processing merchant skips required SCA, Adyen defaults to decline; optional Issuing soft declines require contact-led enablement, send a failed-authorisation transfer webhook and leave 3D Secure retry to the merchant (lines 46–56). Q2. What limits and cross-source conflict prevent a misleading failure diagnosis?
Answer: The snapshot says five consecutive failed authentications temporarily block 3D Secure, with an automatic one-hour release and Support path for earlier unblocking (raw lines 37–44). The troubleshooting page broadly says no webhook for failed authentication (line 33), but the related Issuing OTP guide says `balancePlatform.authentication.created` is sent regardless of authentication outcome (raw OTP line 945); do not treat transfer/authorisation webhooks and authentication-outcome webhooks as identical. A soft decline's `balancePlatform.transfer.created` includes `psd2SoftDeclineCheck: invalid` (troubleshooting line 52), while `transfer.updated` reports status changes (line 54).
