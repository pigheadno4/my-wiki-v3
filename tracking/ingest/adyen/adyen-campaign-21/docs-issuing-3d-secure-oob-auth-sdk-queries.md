Q1. What does this Issuing-path OOB SDK page ask an integration to do, and which authentication factors does the SDK use?
Answer: For the described EEA/UK Adyen-issued-card flow, register an eligible cardholder device and subsequently authenticate transaction requests on it (pinned raw lines 19–21). The client-side SDK uses possession through device binding plus knowledge or inherence depending on device access configuration (line 29). Its sequence is install for iOS/Android, register the mobile device, then authenticate cardholders (lines 31–37). Q2. Does this overview prove Issuing-only SDK eligibility or that every payment requires OOB and succeeds?
Answer: No. The Issuing-path overview mentions Adyen-issued EEA/UK cards (pinned raw line 21), while the linked SDK-installation requirements table says the feature is supported with an Adyen for Platforms integration (companion raw `issuing/3d-secure/oob-auth-sdk/install-sdk-mobile/2026-09-15.md` lines 29–35). The parent 3D Secure enrollment page says some online payments are out of SCA scope or exempt and proceed to separate authorisation (parent raw `issuing/3d-secure/2026-09-15.md` lines 48–69). Installation, binding and authentication do not themselves prove a specific Issuing authorisation, capture or settlement.
