# C10 retrieval probes — out-of-app payments on iOS

Q1. What routes does this dated Adyen guide describe, and how should its Apple/US recommendation be interpreted?
Expected: This Adyen page was last modified in 2023 and captured 2026-09-15. It describes redirecting an iOS app shopper to a mobile browser to pay for an in-app purchase, using the merchant's Web Drop-in/Components checkout or Adyen Hosted Checkout, then returning to the app. Adyen recommends this route only for US-based merchants or merchants elsewhere accepting US App Store payments for digital goods/services, and points other purchase types to native iOS Drop-in/Components. The page's Apple-guideline framing is historical provider guidance, not proof of current Apple policy, legal permission, entitlement, App Review approval, or merchant eligibility. Raw lines 11, 15–19, 21–33, 35–54; canonical route https://docs.adyen.com/online-payments/out-of-app-payments-on-ios.

Q2. What setup and return responsibilities differ between merchant Web checkout and Hosted Checkout, and how is payment outcome determined?
Expected: Setup requires a qualifying Web Advanced integration (Drop-in/Components or API-only), Web Sessions integration (Drop-in/Components), or Hosted Checkout, plus the Checkout webservice API-credential role and Standard webhooks. With merchant Web checkout, the app opens the merchant's mobile-browser checkout; Sessions uses `/sessions`, Advanced uses `/paymentMethods`, `/payments`, and `/payments/details`, and the merchant implements return-to-app logic. Hosted Checkout uses `/sessions` with the app URL in `returnUrl`, then opens the Adyen-hosted URL; that flow redirects back to the app. Either route gets payment outcome from an `AUTHORISATION` webhook, so returning or showing confirmation alone is not authorization evidence. Browser-route subscriptions are merchant-managed. Adyen directs pre-live testing with test cards but gives no live acceptance proof. Raw lines 25–33, 47–89; same canonical route.
