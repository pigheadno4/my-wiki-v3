# C10 retrieval probes — testing result codes and refusal reasons

Q1. How can an online Checkout test integration trigger an expired-card refusal, and when is holder name ignored?
Expected: In the test `/payments` request, set `paymentMethod.holderName` to the table's `CARD_EXPIRED` value or set `additionalData.RequestedTestAcquirerResponseCode` to `6`. The illustrated response has `resultCode` `Refused` and an expired-card refusal; its USD 10.00 amount is sample payment data, not the refusal trigger. Some card-related methods such as Alipay redirect to a simulator to select the result, so a supplied holder name is ignored there. The guide sends in-person testing to a separate POS route. Raw lines 19–25, 35–119; canonical route https://docs.adyen.com/development-resources/testing/result-codes.

Q2. Which non-refusal results can this table simulate, and what does a test response establish?
Expected: `APPROVED` or code `1` maps to `Authorised`; `PENDING` or code `13` maps to `Received`. The table also has `Error`, `Cancelled`, and many `Refused` mappings. The implementer should verify the triggered `resultCode` and `refusalReason` where applicable and check its integration's response handling. Shopper messages, retry logic and order-management handling are offered as testing benefits, not a mandatory retry policy. A test `Authorised` result is simulated, `Received` is distinct, and neither proves live authorization or settlement. The sample endpoint is Checkout v72 test, while linked API Explorer uses `latest`. Raw lines 27–33, 108–127, 129–176; same canonical route.
