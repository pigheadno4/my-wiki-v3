# C10 retrieval probes — Test Cards API reference

Q1. What test-only endpoints and required request fields does the Test Cards API reference document?
Expected: This 2026-09-15 snapshot of a 2020-modified reference lists the test SOAP `TestCard/v1` service and WSDL separately from the JSON/FORM `/createTestCardRanges` endpoint. Valid API credentials are required. `CreateTestCardRangesRequest` requires `accountCode`, case-sensitive `accountTypeCode` (`Company` or `MerchantAccount`), and one or more `testCardRanges`. A range has required address, holder, expiry and start/end card fields, optional CVC and 3DS fields; AVS address includes at least `streetAddress`, and bounds are described as BIN-compliant 6–19-digit card numbers. This is test-platform QA, not live-card creation or production eligibility. Raw lines 10, 14–113; canonical route https://docs.adyen.com/development-resources/test-cards-and-credentials/create-test-cards/test-cards-api.

Q2. How should a range-creation result and the related parent guide's role and range example be read?
Expected: `CreateTestCardRangesResult` contains per-range results with start/end numbers and `creationResultCode` values `CREATED`, `ALREADY_EXISTS`, or `ERROR`; `ALREADY_EXISTS` does not show that a newly requested range was created. The related Create test cards guide requires the Manage test cards Customer Area role but does not explicitly partition that role between UI and API paths. Its SOAP request example reverses numeric start/end bounds, while its error handling says a start greater than an end fails; do not copy the inconsistent pair as a proven working request. The API reference itself requires valid credentials and gives no live eligibility proof. API raw lines 22–42 and 115–125; related parent raw lines 27–39, 51–67, 110–129 and 229–245; same canonical API-reference route.
