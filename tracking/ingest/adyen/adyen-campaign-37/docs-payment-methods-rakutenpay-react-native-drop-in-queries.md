Q1. What does the Rakuten Pay React Native Drop-in guide cover, and what cannot be inferred?
A1. It documents method-specific additions to existing React Native Drop-in Sessions and Advanced redirect integrations, plus recurring qualifications and a TEST simulator route (raw lines 17–64, 66–104). It does not establish a live merchant entitlement, final redirect/webhook outcome, issued token or authorized/captured/settled transaction (raw lines 25–104). Q2. What are the key prerequisites, recurring limits and source warnings?
A2. Sessions requires Checkout API v68+, redirect handling and Rakuten Pay in Customer Area; Advanced requires redirect handling and the same setup, with no extra method request/configuration parameters stated for either base flow (raw lines 29–48, 70–88). The Sessions requirement links to an Advanced URL despite its Sessions wording (raw line 33). Card-on-file use is review-gated; without periodic charging cadence the Recurring Processing Model is prohibited, and merchants must apply for every model; explicit shopper permission is strongly recommended (raw lines 50–56, 90–96). The page's TEST acquirer route uses a DGFT simulator rather than a Rakuten Pay app (raw lines 58–64, 98–104).
