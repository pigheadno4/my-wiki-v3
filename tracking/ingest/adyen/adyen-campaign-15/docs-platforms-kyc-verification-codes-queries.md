# Fixed retrieval checks — Verification codes

## Q1. What is this page for, what is in scope, and what should not be inferred?

The 2021-modified, 2026-09-15-captured Platforms/Issuing page gives the three-level verification-error taxonomy and how to find codes in account-holder capability problems via Customer Area, Configuration API response or account-holder webhooks. It links to separate detailed code catalogs. It is not proof of an actual user's current verification status, capability permission, compliance, or success after taking an action; the JSON is illustrative. Issuing and Platforms remain distinct. ## Q2. What is the central capability, prerequisites, and material warnings?

A general code describes a failed verification check, a linked suberror gives a specific cause, and a remediating action suggests a possible fix; Adyen says actions accompany errors whenever possible. Customer Area viewing requires Manage account holder capabilities; API viewing requires a Configuration API web-service credential, with GET /accountHolders/{id} or created/updated webhooks. In a capability problems array, entity.id refers to the affected legal entity; verificationErrors hold type, general code/message, a common remediatingActions field when applicable, and subErrors with their own type/code/message/remediatingActions arrays. The prose describes that common field as an object (line 80), whereas the example shows an array (lines 98-103); this page does not establish a definitive runtime type, so check the current API schema or an observed payload before parsing. The example's 1_30/1_3001/1_3000, 1_300/1_301 actions and invalid status are a single case. Use suberrors for API-only error handling, without assuming a suggested action, universal response, successful remediation or capability approval.
