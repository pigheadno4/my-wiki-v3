# C08 Unified Commerce referenced refunds — fixed retrieval checks

1. **Q: How can a merchant refund an ecommerce purchase at a POS terminal, and which merchant account supplies the funds?**
   **A:** For the Terminal API `ReversalRequest`, use the original ecommerce payment's PSP reference as `.pspReference` with the leading dot in `POITransactionID.TransactionID`, put the original payment time in the separate `POITransactionID.TimeStamp` field, and supply matching currency; a POS-origin payment uses `tenderReference.pspReference` as its TransactionID value, with its original timestamp likewise separate. The refund returns to the original payment method without presenting a card. The original payment's merchant account supplies the in-process refund funds, even if a different store/account handles the return. The merchant needs the original PSP reference shared across channel systems, Standard webhooks and company-level refund enablement for cross-merchant-account returns. The 2022-modified guide does not prove current account enablement or a completed refund.

2. **Q: Does a successful Terminal API reversal or Checkout refund response mean the shopper has received funds?**
   **A:** No. Terminal API `ReversalResponse.Result=Success` and a **REFUND REQUESTED** receipt acknowledge receipt; its outcome route is a `CANCEL_OR_REFUND` webhook. The server-to-server `/payments/{paymentPspReference}/refunds` response can show `status=received` and a distinct refund PSP reference; its outcome route is a `REFUND` webhook. Webhook `success=true` reports validation and sending to the card scheme, with rare later `REFUND_FAILED` or `REFUNDED_REVERSED` possible. For server refunds, the requested value cannot exceed the captured amount and the currency must match the original authorization; an uncaptured transaction calls for cancellation or waiting for settlement.
