# C08 Customer Area MOTO — fixed retrieval checks

1. **Q: Who uses Adyen's Customer Area Virtual Terminal MOTO route, and what permissions and form fields does this page require?**
   **A:** A merchant staff user enters card details supplied by a mail/telephone-order shopper in Customer Area's Virtual Terminal. The user needs **Create payments from virtual terminal in the CA**; the merchant subscribes to a **Standard webhook**. The user selects a merchant account and store, completes shopper/payment details and submits. Amount, Merchant reference and Country/Region are always required; an account's MCC may expose extra industry fields. This is a Customer Area UI path, distinct from merchant Checkout API and POS-terminal MOTO routes. Evidence: `raw/adyen/docs/unified-commerce/mail-order-telephone-order/customer-area/2026-09-15.md:15-49`; canonical URL: https://docs.adyen.com/unified-commerce/mail-order-telephone-order/customer-area. The page does not give CVC-specific storage or operator-handling rules.

2. **Q: What test and live checks does the guide prescribe, and does a confirmation page prove settled funds?**
   **A:** It says to use test Customer Area with test card details, check the payment appears in the payment list, and receive an **AUTHORISATION** webhook on the merchant server. Before live use, check the form fields, submit SAQ C-VT for PCI DSS compliance and ensure Customer Area users know the Virtual Terminal UI. Live MOTO uses live Customer Area. The submission confirmation shows whether the transaction was successful in that UI; the page does not establish settlement, funds availability, current account approval or completed PCI assessment.
