# C08 payment-linked loyalty — fixed retrieval checks

1. **Q: What does the payment-linked loyalty tutorial assume, and how does online recognition differ from in-person synchronous recognition?**
   **A:** It assumes the merchant already creates customer profiles and recognizes returning customers across channels, and operates its own loyalty database for registration, points and rewards. Online, the merchant compares shopper-provided contact details with stored `shopperEmail`, queries loyalty status, then sends a distinct `shopperReference` in the illustrated Checkout `/payments` request. In-person synchronous flow starts with Terminal API CardAcquisition; an `alias` in its response's `AdditionalResponse` is used to query the merchant loyalty database before a separate payment. The email, shopper reference, card alias and payment references are distinct objects. The examples do not establish consent, a universal identity match or a successful live payment.

2. **Q: What changes in the asynchronous in-person loyalty path, and can the tutorial snippets be copied as a matched Terminal API exchange?**
   **A:** The asynchronous path updates the merchant's loyalty system after payment using an `AUTHORISATION` webhook; the merchant must enable the card `alias` in webhook `additionalData`. It cannot show real-time points/rewards during the in-store purchase and needs another registration path. The snippets are illustrative and inconsistent: shopper `InputRequest` bodies are shown under `MessageCategory: Payment`, one `InputResponse` is wrapped as `SaleToPOIRequest`, and the synchronous PaymentRequest's `CardAcquisitionReference.TransactionID` differs from the prior CardAcquisition response ID. The asynchronous payment response writes `aliasA37317672402294` without an equals sign in `AdditionalResponse`, while the webhook has `alias` as a separate key.
