# C08 POS wallet passes — fixed retrieval checks

1. **Q: Which wallet-pass platform, terminal software and flow choices does the pinned guide actually support?**
   **A:** The page describes merchant NFC loyalty passes in a Terminal API payment-terminal integration. Its dated requirements list Verifone Engage terminals on software 1.64+, Castles Android terminals on 1.105+, **Apple Wallet passes only**, and an Apple agreement to present them. A payment flow checks the pass after payment; redeem flows check it through card acquisition before payment. Single tap polls both pass and payment-method details, requires the final amount not to exceed acquisition amount and may need Support-enabled single tap when the amount differs; double tap polls the pass only first and permits a second presentation with another payment method. For an existing pass, the single-tap payment response does not repeat loyalty details, while the double-tap payment response includes `LoyaltyResult` with the same details. Evidence: `raw/adyen/docs/point-of-sale/loyalty/wallet-passes/2026-09-15.md:29-90`; canonical URL: https://docs.adyen.com/point-of-sale/loyalty/wallet-passes. This snapshot is not evidence of current Apple/Google availability, device eligibility or successful payment.

2. **Q: Is the wallet loyalty pass ID a card token, and what setup and identity limits accompany on-the-spot issuance?**
   **A:** No. `LoyaltyAccountID.LoyaltyID` is the unique ID of the merchant pass used to look up its loyalty account; the payment-flow sample shows separate card/payment fields but no visible alias; the following prose says to use the returned card alias, and a separate double-tap example shows one in `AdditionalResponse`. The merchant runs or uses a third-party pass server, creates a pass type ID and private key, configures flow/protocol/key in Customer Area, and ties the pass to its POS and loyalty program. The documented on-the-spot issue route is limited to Verifone Engage: if the shopper agrees to enroll, the merchant creates a profile and sends `LoyaltyData` with the new pass ID or configured URL plus ID; the optional case-sensitive `shopperReference` must be at least three characters and contain no name/email PII. A redeem payment references the prior card acquisition with its returned `POITransactionID` timestamp and transaction ID. Evidence: `raw/adyen/docs/point-of-sale/loyalty/wallet-passes/2026-09-15.md:92-166,206-216,261-295,339-351,410-431,546-600`; canonical URL: https://docs.adyen.com/point-of-sale/loyalty/wallet-passes. The sample payment response is illustrative, not proof of live pass issuance, consent, authorization or settlement.
