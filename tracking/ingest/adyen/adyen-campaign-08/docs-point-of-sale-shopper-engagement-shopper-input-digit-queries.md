# C08 numeric DigitString input — fixed retrieval checks

1. **Q: How does a POS app request numeric input, and does the terminal validate or default the value?**
   **A:** A Terminal API `Device/Input` request uses `DisplayOutput` with `GetDigit` on `CustomerDisplay` and `InputData` with `DigitString` on `CustomerInput`. `MaxInputTime` sets seconds to finish; `DefaultInputString` is placeholder text showing an expected format, not a validated or prefilled value. The ZIP-code request's 30-second timeout and example placeholder are example values. The guide explicitly says the returned `InputResult.Input.DigitInput` numerals are **not validated against a format** and must be passed to the merchant system for validation. It gives no digit-length, phone-number or PIN-validation rule. Capturing digits does not prove a payment, identity or consent.

2. **Q: What does the guide say about masking and about timeout, Cancel or payment override while digit input is pending?**
   **A:** It lists a true/false masking flag, but the table prints `MaskChararctersFlag` while the JSON sample uses `MaskCharactersFlag`; the Java sample omits it, so verify the API field before implementing. A timeout returns input `Failure/Cancel` with `message=Screen%20timeout`; shopper Cancel returns `Failure/Cancel` and empty `DigitInput`. A payment request received while the terminal waits overrides the input request and returns input `Failure/Busy` with a higher-priority-request message. The request can also end on an explicit cancel-input request or another POS-app request. These are input outcomes, not payment results or proof of secure PIN handling.
