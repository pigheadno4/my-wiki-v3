# C08 cancel in-progress input — fixed query answers

1. **How does a POS app cancel an active Terminal API input request, and what confirms it?** Send a new Service/Abort request with `AbortReason: MerchantAbort` and `MessageReference` pointing to the target Input request's SaleID and ServiceID. The abort header has its own new ServiceID. The guide says a successful abort returns HTTP `200 OK` without a body, then directs the POS to check that the prompt disappears and the original input returns `Failure`/`Aborted`. The sample target ServiceID `21796` conflicts with the illustrative InputResponse header ServiceID `010`; use the stated correlation fields, not that sample as a matching-ID proof. Evidence: `raw/adyen/docs/point-of-sale/shopper-engagement/shopper-input/cancel-input/2026-09-15.md`, `## Cancel from POS app` lines 32–136; proposed source `[[source-adyen-docs-point-of-sale-shopper-engagement-shopper-input-cancel-input]]`.

2. **Does terminal Cancel always return `Failure`, and does it cancel a payment?** No. The guide's terminal-cancel table says Confirmation and Signature input return `Result: Success` with `ConfirmedFlag: false`; Menu, Digit and Text return `Result: Failure` with `ErrorCondition: Cancel`. These are outcomes of an in-progress input prompt. The page only links to a separate guide for canceling an in-progress transaction and provides no payment-cancellation result. Evidence: `raw/adyen/docs/point-of-sale/shopper-engagement/shopper-input/cancel-input/2026-09-15.md`, `# Cancel collecting input` lines 15–22 and `## Cancel from terminal` lines 138–166; proposed source `[[source-adyen-docs-point-of-sale-shopper-engagement-shopper-input-cancel-input]]`.
