1. **Who enters the card details in this MOTO flow, and what confirms the outcome?** A merchant user, such as a call-center agent, enters the shopper's details in a Web Drop-in form in the merchant UI after the server creates a Checkout `/sessions` resource. The server supplies the returned session data to the UI. After submission, the guide says to wait for an asynchronous `AUTHORISATION` webhook and match its `merchantReference` to the order; `success: true` denotes the successful outcome, while `false` includes a failure reason. Session creation and UI callbacks alone do not establish the payment outcome. Locators: raw lines 19–21, 33–45, 49–53, 86–90, 292–333.

2. **Which setup and compliance claims can this page actually support?** It lists an API key, Merchant PAL webservice, Checkout webservice, Checkout encrypted cardholder data roles, and Standard webhook. The `/sessions` table specifies MOTO interaction, card-only `scheme`, amount, merchant account, unique reference and return URL, but the table spells the interaction `Moto` while sample JSON sends `MOTO`; that case conflict is unresolved by this page. Its go-live steps include live account/endpoints, a submitted SAQ C-VT form and matching Drop-in environment. The page does not prove account eligibility, PCI compliance, an SCA exemption, recurring use, merchant-of-record allocation, funds flow or a successful live transaction. Locators: raw lines 23–31, 53–83, 367–393.
