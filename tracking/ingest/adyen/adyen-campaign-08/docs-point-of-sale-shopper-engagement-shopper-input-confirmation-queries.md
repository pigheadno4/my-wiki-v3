# C08 GetConfirmation input — fixed retrieval checks

1. **Q: How is a GetConfirmation prompt and its two choices encoded, and what do the returned flags mean?**
   **A:** The Terminal API request uses `MessageClass: Device`, `MessageCategory: Input`, and `InputCommand: GetConfirmation`. `OutputText` is an ordered four-field array: title, additional text, left Cancel-button label, right Confirm-button label. In the example, those labels are Decline and Agree. `Input.ConfirmedFlag: true` means the right button or keypad Confirm was selected; `false` means the left button or keypad Cancel. The title is about 20 characters on a portrait display. This is terminal input, not financial authorization or proof that legal consent requirements were met.

2. **Q: What happens when a GetConfirmation request times out or a payment request arrives while it waits?**
   **A:** Timeout returns input `Result: Failure`, `ErrorCondition: Cancel` and `message=Screen%20timeout`. A new payment request overrides the pending input and returns input Failure/`ErrorCondition: Busy` with the higher-priority-request message. A shopper's left-button or keypad Cancel is described as `ConfirmedFlag: false`, so it must be distinguished from timeout Failure/Cancel. The guide also says the input is not format-validated and tells the merchant to validate and use the returned data in its own system.
