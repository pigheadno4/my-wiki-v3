# C08 multiple-answer MenuButtons — fixed retrieval checks

1. **Q: How does a POS app ask a shopper to select multiple terminal-menu answers, and what limits are documented?**
   **A:** It sends a Terminal API `SaleToPOIRequest` with `MessageClass=Device`, `MessageCategory=Input`, a `MenuButtons` `DisplayOutput` for `CustomerDisplay`, up to 15 one-line `MenuEntry` option buttons, and `InputData` for `CustomerInput/GetMenuEntry`. Including `MinLength` or `MaxLength` enables multiple answers and bounds the count; `MaxInputTime` is in seconds. The sample's 60-second, 0-to-3 choice settings are example values, not defaults. The guide routes one-answer menus to another page; its survey/subscription sample does not establish legal consent or payment authorization. 2. **Q: How are selected options and unsuccessful multi-menu input reported?**
   **A:** The `InputResult.Input.MenuEntryNumber` array is positional: `1` marks a selected option and `0` an unselected one, so first-plus-third appears as `[1,0,1]`. Too few or too many choices yield input `Failure/NotAllowed` with an explanatory `AdditionalResponse`. Timeout yields an `EventNotification` with the documented no-response `EventDetails`; a payment request during pending input overrides it and yields input `Failure/Busy`; shopper Cancel yields `Failure/Cancel`. The POS system then validates and uses relevant input data itself. These outcomes describe terminal input, not a financial result or consent validity.
