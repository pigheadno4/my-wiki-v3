# C08 shopper-engagement flow session — fixed retrieval checks

1. **Q: What request sequence creates and ends an Adyen shopper-engagement flow, and what does its timeout control?**
   **A:** The captured guide sends a Terminal API **Admin** request whose Base64 `ServiceIdentification` JSON has a unique `Session.Id` and `Type=Begin`; its `Operation` entries select InputRequest, DisplayRequest and/or Payment with `Variant=WaitingScreen` and `UserInterfaceData.WaitingScreenTimeoutMs`. The POS then sends the selected input/display/payment requests and finishes with a second Admin request using the **same Session.Id** and `Type=End`. The milliseconds configure how long the waiting screen appears after an operation; they are not a stated session lifetime or payment timeout. A new request interrupts the waiting screen, while an End Admin request sent while it is displayed does not interrupt it; subsequent requests after End no longer trigger that waiting screen. 2. **Q: Does a successful Begin/End AdminResponse prove a payment was authorized or that the terminal is exclusively reserved?**
   **A:** No. The guide asks for `AdminResponse.Response.Result=Success` at each session-boundary request, and describes a waiting-screen UI around potentially financial **Payment** requests. It gives no payment-response/authorization result, no Login/Logout operation, no exclusive resource claim, no concurrent-session or notification/cancellation behavior, and no local/cloud or model-eligibility rule. The request table's `ServiceID` constraint is 1–10 alphanumeric characters unique within 48 hours for the terminal, but the sample **Begin** request puts a longer POS-system string in `ServiceID` and its displayed response reverses the `ServiceID`/`SaleID` values; the **End** request uses the table-consistent placement. The human-readable Begin JSON lists InputRequest and DisplayRequest; its standalone Base64 decodes to both but contains a trailing comma after `Type: Begin`, while the Base64 embedded in the Begin Admin request decodes to InputRequest only. Validate the intended JSON/Base64 rather than copying the mismatched sample.
