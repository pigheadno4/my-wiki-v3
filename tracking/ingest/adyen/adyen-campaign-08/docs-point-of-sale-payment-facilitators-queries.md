# C08 POS payment facilitators — fixed retrieval checks

1. **Q: In Adyen's POS payment-facilitator guide, who is Merchant of Record and how can required sub-merchant data be supplied?**
   **A:** For a transaction facilitated by a payment facilitator, the guide says the **sub-merchant** is considered Merchant of Record and card schemes require data about it. Adyen adds some fields; the facilitator supplies the rest. Standalone terminals require Management API store `subMerchantData`; integrated terminals or Mobile solutions may use store configuration, Terminal API request fields, or both, with request fields overriding store values. Evidence: `raw/adyen/docs/point-of-sale/payment-facilitators/2026-09-15.md:19-50`; canonical URL: https://docs.adyen.com/point-of-sale/payment-facilitators. The source does not establish settlement recipient, funds flow, splits or payout terms.

2. **Q: Which POS requests need request-level sub-merchant fields, and what can be inferred from the response?**
   **A:** Request-level fields are for Terminal API payments and referenced/unreferenced refunds. Non-Terminal-API modifications such as manual capture and authorization adjustment use data from the initial payment, according to this guide. The Terminal API route Base64-encodes `additionalData` into `SaleData.SaleToAcquirerData`; its field table does not mark all properties required, and the response does **not** echo the supplied sub-merchant data. Store-configured `subMerchantData.id` is capped at 15 alphanumeric characters, while request `subMerchantId` is capped at 19.
