# Fixed retrieval checks: virtual receipt display

1. **Q:** Does a successful virtual-receipt display mean the POS charged the shopper or printed a receipt, and when does the display end? **A:** No. The guide uses a Terminal API `DisplayRequest` before payment begins to show POS-supplied line items and optional QR content. In its single-item response example, `DisplayResponse.OutputResult[0].Response.Result=Success` is a display-request result, not a payment, print, legal-receipt or shopper-acceptance result. The request has no display timeout; the receipt remains until another request, such as payment or standby-display request, replaces it. 2. **Q:** How is the virtual receipt supplied, and what validation and model qualifications apply? **A:** The POS builds XML with a terminal-compatible `<screen name>`, encodes that XML as Base64, and supplies it in one `DisplayOutput` item as `OutputXHTML` with `OutputFormat=XHTML`, `CustomerDisplay` and `InfoQualify=Display`; the header uses `MessageClass=Device` and `MessageCategory=Display`. QR support depends on the screen template; SFO1-only image/icon/subtitle fields and model-specific non-QR templates need the raw table/steps. Adyen always parses XML, while XSD validation requires account-level Support enablement. A parse or XSD failure can return `MessageFormat`; a sample incompatible terminal returns `NotAllowed`. The table and steps differ on SFO1 for an auto-scroll template, so current compatibility needs checking. Base64 and validation do not verify QR safety, privacy or receipt amounts.
