# C08 POS single-answer menu input — fixed retrieval checks

1. **Q: How does a POS app ask for one menu choice on a terminal, and what does the response identify?**
   **A:** Use Terminal API `MessageClass=Device`, `MessageCategory=Input` with an `InputRequest`. Set `DisplayOutput` to text `MenuButtons` with a header, optional second header and up to 15 scrollable one- or two-line options; set `InputData.InputCommand=GetMenuEntry` for one selected answer. On received input, `InputResult.Input.MenuEntryNumber` marks the chosen option position with `1` and other positions with `0`. The guide says the input is not format-validated; the merchant system handles subsequent validation and use. Evidence: `raw/adyen/docs/point-of-sale/shopper-engagement/shopper-input/menu/2026-09-15.md:15-29,68-118,259-270,319`; canonical URL: https://docs.adyen.com/point-of-sale/shopper-engagement/shopper-input/menu. This Device/Input response does not authorize payment or prove consent.

2. **Q: What happens if the menu times out, the user cancels, or the POS app sends a payment request during input?**
   **A:** The menu remains until input, the configured maximum time, terminal Cancel, or another POS request. Timeout returns `Failure` / `Cancel` with `message=Screen%20timeout`; terminal Cancel returns `Failure` / `Cancel` and an empty `MenuEntryNumber`. A payment request overrides waiting input and produces `Failure` / `Busy` with a higher-priority-request message. These results describe interruption of the input request, not the payment outcome.
