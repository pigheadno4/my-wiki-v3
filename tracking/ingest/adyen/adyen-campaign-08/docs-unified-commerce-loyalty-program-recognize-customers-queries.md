# Fixed retrieval checks: cross-channel customer recognition

1. **Q:** Can an online customer be shown a card saved from a prior POS payment using email alone? **A:** The guide first has the merchant compare shopper-supplied email with `shopperEmail` in its own customer database. For an existing online account with a card previously saved and tokenized from a POS payment, the merchant retrieves `shopperReference` and `storedPaymentMethodId` from that database; `/paymentMethods` with the shopper reference can return a matching `storedPaymentMethods.id`. The UI then collects a CVC/CVV, and the separate `/payments` example sends the token, shopper reference, security code, `ContAuth` and `CardOnFile`. API-only raw card submission is described only for fully PCI-compliant merchants. Email matching does not authenticate the person, and the sample `Authorised` response is not a live-result guarantee. 2. **Q:** Does a missing POS card alias prove that an in-store shopper is new, and does card acquisition charge them? **A:** No. A Terminal API `CardAcquisition` response can return a card `alias` for merchant-profile lookup and a `shopperReference` only if previously stored with Adyen. An unmatched alias can belong to a returning customer using a new card. The guide suggests collecting email for a `shopperEmail` lookup and asking whether to save the new card before tokenizing it with the existing shopper reference. Card acquisition is separate from the later `PaymentRequest`, which references the acquisition and has its own result and terminal transaction ID. The alias, shopper reference, saved-card token, and payment transaction ID are different objects, and the sample success is not proof of a real payment.
