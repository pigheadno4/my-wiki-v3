- Q1: For `post/donations`, what is the endpoint purpose and object identity, and which central required or conditional inputs/prerequisites govern using it?
  - A: The captured Checkout v72 test-server endpoint makes a donation, including a route using a token generated by `/payments`. The body marks `amount` with currency/minor-unit value, `merchantAccount`, `reference` and `returnUrl` required. If `donationToken` is supplied, `donationOriginalPspReference` identifies its original transaction and is required; the payment method derives from the token. Other examples show a stored-method route. Conditional 3DS and recurring fields depend on the integration (raw lines 5–12, 45–47, 78–95, 109–112, 171–189, 263–323).
- Q2: For `post/donations`, what does the documented response or failure establish, and which lifecycle, asynchronous outcome, version/environment or missing-evidence boundaries prevent broader inference?
  - A: A 200 response can contain donation resource `id`, donation `status` (`completed`, `pending`, `refused`) and nested payment action/result/`pspReference`, distinct from the original purchase reference. Examples show `completed` and `Authorised`, but are illustrative; the Giving concept's merchant `DONATION` webhook is the outcome route. Errors listed are 400, 401, 403, 422 and 500, including a token-specific 422 example. The `latest` URL captured a v72 test server and supplies no current-version, live-result or settlement proof (raw lines 1–12, 324–402, 405–620).
