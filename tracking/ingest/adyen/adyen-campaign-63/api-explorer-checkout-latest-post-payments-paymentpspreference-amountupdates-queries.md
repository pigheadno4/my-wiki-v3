# C63 amountUpdates fixed-query answers

## Q1

The 2026-11-02 captured Checkout API `latest` page describes `POST /payments/{paymentPspReference}/amountUpdates` on TEST server `https://checkout-test.adyen.com/v72` as increasing or decreasing an authorised payment amount to a new total, returning a unique update-request reference; it says the amount must not yet have been captured. The path parameter is the original payment `pspReference`. The request table requires `merchantAccount`, `amount.currency` matching the authorisation currency, and `amount.value` in minor units. It marks `reference` optional with an 80-character maximum, `adjustAuthorisationData` optional for synchronous adjustments, `mpiData` conditionally required for cardholder-initiated adjustments, and `splits` optional with type-dependent nested requirements and the original-payment currency default for split currency. The optional `Idempotency-Key` is at most 64 characters. The 201 response requires `amount`, `merchantAccount`, original `paymentPspReference`, distinct 16-character update `pspReference`, `reference`, and `status`; it optionally returns `adjustAuthorisationData` for the synchronous flow. ## Q2

The endpoint's 201 response records creation/fulfilment of the amount-update request, with the update's own PSP reference; it is not blanket proof that the authorisation increased or decreased. If the request included `adjustAuthorisationData`, documented statuses are `authorised` and `refused`; otherwise the status is `received` and the page directs the outcome to an asynchronous `AUTHORISATION_ADJUSTMENT` webhook. The page says only uncaptured authorised amounts can be updated. Its optional idempotency header supplies a unique message identifier and length limit, but no duplicate-request guarantee; 401 means authentication required and 403 insufficient permissions, with 400/422 validation-related and 500 server errors also documented. This endpoint page states no deletion, propagation, reversal, capture, settlement, or live-availability guarantee. A separate pre-authorisation guide describes Support-enabled adjustment after a first partial capture, in tension with this endpoint's uncaptured wording; that guide's exception cannot establish general post-capture eligibility. The 2026-11-02 TEST v72 snapshot alone cannot prove current live access, merchant eligibility or financial finality.
