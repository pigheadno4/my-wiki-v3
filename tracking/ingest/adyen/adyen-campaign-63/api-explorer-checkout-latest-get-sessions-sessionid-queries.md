# Fixed retrieval answers — api-explorer-checkout-latest-get-sessions-sessionid

## Q1

The 2026-11-02 captured Checkout API Explorer reference describes GET /sessions/{sessionId} as returning a session result on the listed Checkout TEST v72 server. The unique sessionId is a required path parameter; the Drop-in or Component sessionResult is a required query parameter, despite the introductory sentence saying both are in the path. This is the session resource, not a payment-link or token lookup. Its optional response fields are additionalData (some fields require Customer Area enablement), session id, payments, the merchant-provided original /sessions reference, and session status. Optional payment entries can include amount, paymentMethod, Adyen pspReference and resultCode; currency and minor-unit value are required inside an amount object. paymentMethod is returned only for Authorised and brand only for scheme. Session status values are completed, paymentPending, refused, canceled and expired; default expiry is one hour after creation. Retrieval: [[source-adyen-api-explorer-checkout-latest-get-sessions-sessionid]], https://docs.adyen.com/api-explorer/Checkout/latest/get/sessions/(sessionId), verified raw lines 5–45.

## Q2

A 200 means this GET request succeeded, while returned session/payment states have their own meanings. Authorised is final authorisation, Received is initial receipt and Pending lacks final payment status; none of these proves capture or settlement. The session status is explicitly not updated, so repeating this GET is not a payment-status polling method. paymentPending describes asynchronous shopper completion; refused after too many refused attempts and expired prevent further completion, while canceled means shopper cancellation. The captured reference gives no authentication header, idempotency rule, error schema, deletion or propagation contract, modification/reversal response, or live-server proof, so those cannot be inferred here. Its description of payments as “all authorised payments” conflicts with Received and Pending in the nested resultCode enum. The sole success example is illustrative.
