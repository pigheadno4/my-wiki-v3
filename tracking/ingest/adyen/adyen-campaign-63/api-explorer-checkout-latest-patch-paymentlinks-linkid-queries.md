# C63 fixed-query answers — PATCH /paymentLinks/{linkId}

## Q1 — Purpose, version/environment, identities, inputs, defaults/limits, response

The 2026-11-02 capture of Checkout API Explorer's `PATCH /paymentLinks/{linkId}` describes forced expiry of one payment link. Its listed server is `https://checkout-test.adyen.com/v72`; the URL's `latest` label does not establish a later version or LIVE availability. The caller supplies a required `linkId` path string and a request body with required `status`; the only listed request value is `expired`. No other request fields are shown. A 200 returns the link object: required `amount` with three-character `currency` and minor-unit integer `value`, `id` (the link identifier), `merchantAccount`, `reference` (a reference for future payment-status communications), `status`, and shopper payment-page `url`. Its response status set is `active`, `expired`, `completed`, `paymentPending`. Optional `expiresAt` is described as defaulting to 24 hours after creation with a 70-day maximum; optional `reusable` defaults false, allowing one successful payment; optional `updatedAt` records a status-update time. These are returned-link schema descriptions, not PATCH inputs. The related Pay by Link API guide says setting `expired` also changes `expiresAt` to the current date/time. ## Q2 — What success/state establishes and limiting boundaries

HTTP 200 is a successful status-update request and the example returns `expired`; the response schema says an expired link can no longer be used to make payments. This is link lifecycle state, not proof of a payment authorization, capture, refund, cancellation or reversal. `paymentPending` means the shopper is in an unfinished asynchronous payment flow, not financial finality. The endpoint page specifies no idempotency key or retry semantics and no authentication method; it does document 401 authentication required and 403 insufficient permissions. It also lists 400 request-reading error, 422 validation error and 500 server error with generic error fields. The 422 example's `Return URL is missing.` does not make `returnUrl` required in this PATCH body, which lists only `status`. A generic error's optional `pspReference` is a payment PSP reference, separate from the link `id` and merchant `reference`. The TEST v72 snapshot does not prove current availability, merchant eligibility, propagation timing, an actual shopper/payment outcome or LIVE behavior; the endpoint gives no deletion or rollback contract.
