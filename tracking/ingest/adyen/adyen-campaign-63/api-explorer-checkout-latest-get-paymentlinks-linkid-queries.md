# C63 fixed answers — GET payment link

## Q1

The 2026-11-02-captured Checkout API Explorer page documents TEST v72 `GET /paymentLinks/{linkId}` at `https://checkout-test.adyen.com/v72`, retrieving a payment link by its unique `id`. The only listed request input is required path `linkId`; the page lists no request body. The 200 response requires `amount` with ISO currency and minor-unit value, link `id`, `merchantAccount`, merchant payment `reference`, link `status`, and shopper payment `url`. The link ID, merchant payment reference and optional shopper reference are distinct. Its optional `expiresAt` describes a 24-hour creation default and 70-day maximum, and `reusable` defaults to `false` for one successful payment. Other optional fields retain nested or method-specific conditions, not blanket top-level requirements. ## Q2

HTTP 200 establishes that this GET lookup succeeded. The returned `status` is a payment-link state: `active`, `expired`, `completed` (shopper completed payment), or `paymentPending` (asynchronous shopper payment in progress). Neither the lookup nor these labels establishes authorization, capture, settlement, reversal or final financial outcome. The captured GET page lists no idempotency header or request body, and makes no deletion or propagation guarantee. It does specify 401 authentication required, 403 insufficient permissions, plus 400, 422 and 500 error categories; example error payloads are illustrative. The optional `expiresAt` and `reusable` fields describe link lifecycle settings, including default 24-hour expiry, maximum 70-day expiry and default one-successful-payment use. This TEST v72 snapshot does not verify current live availability or an executed payment.
