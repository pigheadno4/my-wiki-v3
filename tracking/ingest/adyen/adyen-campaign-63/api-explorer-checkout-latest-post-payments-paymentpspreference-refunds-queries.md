# C63 fixed query answers — api-explorer-checkout-latest-post-payments-paymentpspreference-refunds

## Q1

For the 2026-11-02-captured Checkout API `latest` page, `POST /payments/{paymentPspReference}/refunds` requests a full or partial refund of an already captured payment on the listed v72 test server `https://checkout-test.adyen.com/v72`. The caller supplies the original payment's PSP reference in the path. The body table requires `merchantAccount` and `amount`, with `amount.currency` (authorization currency) and minor-unit integer `amount.value`; the table says value at most the authorized amount, while the overview caps cumulative partial refunds at the captured amount. Partial-refund support depends on the payment method. `capturePspReference` is optional and only available for PayPal capture-specific refunds. `lineItems` is table-optional but required for partial refunds with the named buy-now-pay-later methods. `reference` is optional, maximum 80 characters; `merchantRefundReason` is optional with `FRAUD`, `CUSTOMER REQUEST`, `RETURN`, `DUPLICATE`, `OTHER`. `splits` and their child requirements depend on Classic Platforms or Balance Platform integration and split type; optional `store` must match the configured Customer Area store name. The 201 body requires refund `amount`, `merchantAccount`, original `paymentPspReference`, separate 16-character refund-request `pspReference`, and `status: received`; optional fields include `capturePspReference`, `lineItems`, reason, reference, splits, and store. The request example is illustrative. ## Q2

A 201 `received` means the refund request was accepted/created as a request resource; the page directs the reader to a later `REFUND` webhook for its asynchronous outcome. It does not establish final refund completion, shopper receipt, or bank credit. `Idempotency-Key` is optional, uniquely identifies the message, has a 64-character maximum, and is recommended as a UUID; the page does not specify replay behavior. Authentication is required (401), insufficient permission can give 403; 400, 422, and 500 cover request-reading, validation, and server-processing errors, with optional error body fields. A mismatched store name causes refund failure. If capture status is uncertain, use the separate reversal route. Partial-refund support and cumulative captured-amount limit apply; the authorization-amount wording in the amount row differs and should not broaden the captured limit. This endpoint page defines no deletion or propagation contract, no synchronous financial-finality guarantee, and no explicit later `REFUND_FAILED` taxonomy; those need their separate source. The `latest` label and 2026-11-02 test-server snapshot prove neither current live availability nor actual processing.
