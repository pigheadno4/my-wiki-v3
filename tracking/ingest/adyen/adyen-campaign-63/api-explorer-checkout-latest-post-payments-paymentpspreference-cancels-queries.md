## api-explorer-checkout-latest-post-payments-paymentpspreference-cancels — fixed answers

### Q1

`POST /payments/{paymentPspReference}/cancels` is the 2026-11-02-captured Checkout API v72 TEST operation at `https://checkout-test.adyen.com/v72` for cancelling the authorization on an uncaptured payment. The caller identifies the original payment with required path `paymentPspReference` (the original payment's `pspReference`) and supplies required body property `merchantAccount`; the request-body table does not separately declare body-container requiredness. Optional body `reference` names this cancellation request and has an 80-character maximum; optional `applicationInfo` carries nested metadata. The optional `Idempotency-Key` header has a 64-character maximum and a UUID recommendation. A 201 response requires `merchantAccount`, original `paymentPspReference`, a distinct 16-character `pspReference` for the cancellation request, and `status` fixed to `received`; `reference` is optional. ### Q2

The 201 `received` state and request PSP reference establish receipt of the cancellation request, not cancellation success or financial finality; its outcome is asynchronous in a `CANCELLATION` webhook. This operation applies to an authorization not yet captured. When the original PSP reference is missing, the page points to separate `POST /cancels`; when capture status is uncertain, it points to separate `POST /payments/{paymentPspReference}/reversals`. The optional idempotency header is specified as a unique identifier, but this page does not define retry/replay semantics. Listed 401 and 403 errors identify authentication and permission failures, while 400, 422 and 500 cover request, validation and server failure; the generic 422 missing-return-URL example does not add a cancellation request field. The snapshot gives a TEST server only and proves neither live availability nor a completed cancellation, post-capture reversal, fund release, or downstream propagation.
