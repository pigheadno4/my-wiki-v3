# Fixed retrieval checks — use managed payouts

Q1. What does this source let a platform configure, and what outcomes must not be inferred?
- Expected: After an Adyen contact configures managed payout schedules on the balance platform, this 2026-09-15 Platforms guide shows Customer Area and Configuration API routes to list schedules, apply one to a user's balance account, view, update, deactivate or delete an applied schedule. Automatic application is an Adyen-contact-enabled route for qualifying **new** balance accounts, not existing-legal-entity accounts. A balance account has at most one schedule per currency; each schedule serves one location and currency. Schedule setup, HTTP 200/204, or a created webhook is configuration evidence, not payout execution, transfer completion, legal ownership, or beneficiary bank receipt. Managed schedules do not override pass-through or T+7-or-longer sales-day payment settlement timing.

Q2. Which roles, account/region/currency, cutoff, business-day and lifecycle qualifiers govern application and updates?
- Expected: Configuration API credentials need Bank Scheduled Payouts Merchant Role; Customer Area needs Balance platform base and Configure scheduled payouts; the guide calls for Configuration/Scheduled payout webhooks and the user's `sendToTransferInstrument` capability. Applying through API requires a platform schedule ID and transfer-instrument ID, with omitted optional values inherited from the schedule. Automatic application checks active/default-currency balance account, no existing same-currency schedule, non-liable sole account-holder legal entity, one eligible verified transfer instrument and country/currency match (Eurozone exception for euro schedules). For **automatic application only**, failed prerequisite checks leave application pending with retry after account/instrument updates. The later sales-day closing and banking-rail checks can select a regional fallback preserving delay; when no viable schedule exists, manual Customer Area or Configuration API application returns a validation error, while automatic-application failure has its dedicated webhook. PATCH permits only allowed frequencies; monthly weekend dates shift initiation to the next business day, while absent 29–31 dates use month end. An active schedule blocks balance-account `timeZone` edits until deletion, per the test scenario. The deactivation prose says PATCH but its sample uses DELETE on the deletion path, so the current API contract is needed before execution. Test-bank details and US/Australia timing examples are not live availability, fee, refund, payout-return, or bank-credit proof.
