# Fixed retrieval checks — scheduled balance-account top-ups

Q1. What is this source's purpose and scope, and what must not be inferred?
- Expected: A 2026-09-15 Adyen for Platforms guide to configuring a **pull sweep** on a user's balance account so a condition triggers an incoming top-up request from a verified transfer instrument. It describes timing and/or available-balance conditions in general, but its worked Configuration API request is a **balance-threshold** sweep (`schedule.type: balance`), not a cron example. It differs from a one-off Checkout top-up and a platform-liable internal transfer. Creating an active sweep or receiving `balancePlatform.balanceAccountSweep.created` is configuration evidence, not proof that a debit executed, funds reached the user's balance account, a payout occurred, or a bank received funds.

Q2. Which capability, geography, source-account, request-field and outcome boundaries apply?
- Expected: The guide requires Adyen for Platforms, Configuration API credentials, Configuration/Transfer/Transaction webhook subscriptions, the user's `receiveFromTransferInstrument` capability, and Support enablement. Scheduled top-ups are limited in this snapshot to account holders with verified bank accounts in the EU, UK or US through corresponding SEPA, BACS or ACH standard debit rails; it does not establish current account or mandate eligibility. POST `/balanceAccounts/{balanceAccountId}/sweeps` uses the destination user balance account in the path and table-marked required source transfer-instrument ID, merchant account, currency, `schedule.type: balance`, `type: pull`, trigger amount and sweep amount; the transfer instrument must be linked to the account holder's legal entity. Do not infer exact source-debit mechanics solely from the two counterparty field descriptions. The example's EUR 5,000 threshold and EUR 1,000 pull are illustrative; a trigger initiates a transfer request, whose received/authorized/funds-added or failure progression belongs to the linked top-up webhooks. New sweeps default active and can be changed with PATCH, but neither status nor creation proves external debit finality or booked credit.
