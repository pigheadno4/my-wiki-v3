# C22 Issuing recurring top-up webhook query checks

Q1 — Which webhook families answer configuration versus funding questions, and what is required? The Top-up API's recurring configuration operation is asynchronous; a successful API response does not prove create/update/delete completion (pinned raw line 19). For an Issuing integration with a webhook-receiving server (lines 25–33), Configuration `balancePlatform.balanceAccount.recurringTopUp.created/updated/deleted` events track successful configuration changes and carry `data.accountId`, configuration details, and event type (lines 35–49). Transfer `.created/.updated` track the triggered direct-debit transfer and status changes (lines 164–169); Transaction `.created` reports funds credited to the balance account (lines 706–712). Q2 — Can an accepted request, early transfer state, or sample direction prove final funds movement? No. The guide says an accepted request can later fail and shows `rejected` and `returned` transfer updates (lines 435–439, 573–704). Its top-up identification fields are `category=bank`, `type=bankDirectDebit` (lines 171–178). Direction is internally inconsistent: prose calls initiation outgoing (line 168), initiated/authorised samples show outgoing (lines 216, 291), but booked and failure samples show incoming (lines 380, 492, 625). Use actual transfer statuses/accounting records and credited-transaction evidence (lines 706–712), keeping the sample conflict visible.
