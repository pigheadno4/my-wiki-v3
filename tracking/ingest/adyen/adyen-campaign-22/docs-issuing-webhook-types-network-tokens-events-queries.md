# C22 Issuing network-token webhook query checks

Q1 — Which events show an Adyen-issued card added to a wallet, and how are they received? In this Issuing guide, a cardholder's digital-wallet addition leads to network token lifecycle events (pinned raw lines 17–24). Subscribe to Network token webhooks in the Customer Area (line 26). `balancePlatform.networkToken.created` reports the created, inactive token after risk analysis, with a decision such as `requireAuthentication` or `approved` (lines 43–50); `.updated` reports later status changes (lines 194–196). `data.status` and `data.decision` are identified in the field table (lines 32–41). Q2 — Does `decision=approved` in `created` prove wallet activation or payment success, and what closes a token? No. The `created` event still has `status=inactive` (lines 45, 104–112); the guide says to expect a later `.updated` active confirmation (line 106). Authentication-required provisioning waits for OTP or phone-call verification (lines 47–62), and active `.updated` examples distinguish `authenticationApplied` false/true (lines 198–251). A closed `.updated` event is permanent, with failed risk analysis, wallet removal, API revocation, and underlying payment-instrument closure listed as causes (lines 283–297). These lifecycle notifications do not establish a particular payment result.
