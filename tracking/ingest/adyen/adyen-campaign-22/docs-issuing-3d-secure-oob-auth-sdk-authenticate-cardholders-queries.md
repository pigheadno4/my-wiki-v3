# C22 retrieval probes — OOB Authentication SDK challenge

Q1. When an Adyen-issued card transaction requires issuer-side OOB 3D Secure, how does the platform authenticate the cardholder, and what are the deadlines?

Answer: The 2026-09-15 captured guide says to set up a JSON/basic-auth HTTPS webhook endpoint and share its URL with Adyen; the server must respond to a relayed authentication webhook within two seconds (raw lines 29–49). The webhook carries `sdkInput`, challenge `id`, `paymentInstrumentId` and purchase details; acknowledge with HTTP 200 and `authenticationDecision.status: proceed` (lines 53–111). The app shows details and sends `sdkInput` through the Authentication SDK; successful SDK output goes to the server (lines 115–175). The server finalizes the challenge with ACS PATCH `/challenges/{id}`, `sdkOutput` and `completed: true` within ten minutes of receiving the request, then checks `challengeCompleted: true` (lines 177–220). Q2. If the relayed webhook is late or refused, does authentication finish or prove payment approval? Are failure webhooks possible?

Answer: A response later than two seconds, or `status: refused`, stops authentication (raw line 111). `challengeCompleted: true` indicates cardholder authentication and continuation of the transaction (lines 204–209); it does not itself prove authorisation, capture or settlement. The guide says `balancePlatform.authentication.created` is sent regardless of outcome and shows a rejected example (lines 222–224, 314–359). [[source-adyen-docs-issuing-3d-secure-troubleshooting]] has a conflicting broad “no webhook” statement for a failed 3D Secure attempt, so distinguish authentication events from later transfer/authorisation events.
