# C22 docs-issuing-webhook-types-fund-transfers-webhooks retrieval checks

Q1. Which webhooks and fields identify an outgoing versus incoming Issuing bank transfer, and what balance-account state does booked indicate?

Answer: The guide scopes these events to transfers out to a transfer instrument or into a balance account from an external source (raw lines 23–26). For transfer webhooks, `category=bank`, `type=bankTransfer`, and `direction` is relative to the balance account (28–38). Outgoing: `transfer.created/received`, then `transfer.updated/authorised`, then `transfer.updated/booked` when funds are deducted from the source account (44–50, 109–114, 189–196). Incoming uses the same transfer event/status progression with `incoming`; booked means added to the target account (350–355, 415–420, 498–505). After booking, `transaction.created` describes a distinct transaction event (291–303, 600–611). Q2. Does outgoing booked prove the external recipient received funds, and what sample or webhook-count conflicts should a reader retain?

Answer: No. This page says `transfer.updated` may arrive **after** funds leave the balance account, including when the transfer to a transfer instrument fails (raw lines 342–344). The page says three webhooks for each direction yet describes a subsequent `transaction.created` event and an optional outgoing `transfer.updated` (42, 291–293, 342–348, 600–602); interpret the three as described transfer lifecycle states, not a fixed total event count. The outgoing authorised example caption says `transfer.created`, while its JSON has `type: balancePlatform.transfer.updated` (109–116, 181–186). Transaction field tables name `transfer.counterparty.transferInstrumentId`, while example transaction JSON does not show that field (295–303, 326–333; 604–611, 635–642). Payment webhooks for transfer events route to a separate deprecated page (19–21).
