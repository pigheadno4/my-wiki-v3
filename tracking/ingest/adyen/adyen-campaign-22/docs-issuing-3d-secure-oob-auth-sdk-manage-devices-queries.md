# C22 docs-issuing-3d-secure-oob-auth-sdk-manage-devices retrieval checks

Q1. What does the Issuing guide let a platform do with an already registered SCA device, and what is required to associate more cards?

Answer: The API credential needs the Bank SCA Webservice Role (raw lines 25–29). Use `GET /registeredDevices` filtered by the card's `paymentInstrumentId` for lookup (31–41). For association, a registered device can serve multiple payment instruments, but each instrument can link to only one device; up to five IDs may be sent **per POST request** (256–262). The server POSTs the target device/IDs, passes encoded `sdkInput` to the client, receives the client's authentication `sdkOutput`, and PATCHes the same device and IDs (470–567). A successful API association should be checked by listing registered devices for each card (813). Q2. What device association or removal boundaries and failures matter?

Answer: A POST 422 “Device limit reached” means one or more submitted cards are already linked; check and deregister those existing associations before retrying (raw lines 837–861). A PATCH 422 “Challenge not found” usually indicates a mismatch between the challenged client device and PATCH device ID; keep the initial POST and PATCH device IDs aligned (865–886). A cancelled client challenge can yield `NotAllowedError`; same-session retries may reuse `sdkInput` (890–898). Deregistration is **per card** with device `id` and card `paymentInstrumentId`; repeat DELETE for each associated card and check HTTP 204 (900–918, 1071). The GET endpoint prose/curl conflicts with adjacent language SDK snippets that call registration methods (35–50, 68–72); those snippets need version-specific verification.
