# C22 query check: Manage network tokens

Q1. What does this Issuing guide manage, and what does it require? It covers Visa/Mastercard network tokens for Adyen-issued cards added to digital wallets, with a distinct token for each card-device-wallet pairing (raw line 19). The guide requires an Issuing-supporting integration and a Configuration API credential with account-scoped NetworkTokens read/patch permission (raw lines 29–36). Lookup is by payment-instrument ID for a list, including all statuses (raw lines 38–42, 188), or token ID for a single token (raw lines 237–257). Q2. What is the material status/failure boundary and what conflicts should an implementer notice? The documented transitions include phone-call-authenticated inactive → active, suspension/reactivation, and permanent closure; closed cannot change (raw lines 299–316). A PATCH HTTP 202 is only asynchronous acceptance; listen for the final webhook (raw lines 332–334). The single-token and PATCH operation links use `/networkTokens/{networkTokenId}` but their curl samples use a payment-instrument-nested path (raw lines 241, 251, 306, 323). The list and single-token `type` tables disagree (`applePay`/`googlePay` versus `wallet`/`cof`; raw lines 192, 261). The one-per-card example uses an authorization transaction rule with `activeNetworkTokens`, so its effect on provisioning is not established by the sample alone (raw lines 356–383).
