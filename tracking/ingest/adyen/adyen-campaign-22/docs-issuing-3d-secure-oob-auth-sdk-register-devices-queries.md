# C22 query checks — docs-issuing-3d-secure-oob-auth-sdk-register-devices

Q1. What is this registration guide for, and what must be in place before using its flow?

It describes binding an eligible Android or iOS device to an Adyen-issued card (`paymentInstrumentId`) for future out-of-band SCA, with four steps: eligibility check, server initiation, SDK registration, and server finalization (pinned raw lines 15–28). The OS must support SCA, the Authentication SDK must be installed, the API credential must have **Bank SCA Webservice Role**, and the eligibility feature needs additional Adyen configuration (lines 30–39). The companion installation guide labels its integration type **Adyen for Platforms**, so this Issuing-path snapshot does not prove Issuing-only eligibility (companion raw lines 29–35). Q2. What must complete, and what are the consequential replacement or failure boundaries?

Client availability checks produce `sdkOutput` for the server (raw lines 41–103). The server POST `/registeredDevices` uses `paymentInstrumentId` and `strongCustomerAuthentication.sdkOutput`, returning `sdkInput` and a `BSDR`/`RD` device ID (105–120, 348–363). The app performs cardholder 2FA, passes `sdkInput` to SDK registration, and sends successful SDK `sdkOutput` back; Android has cancellation/error branches (366–417). The server PATCHes `/registeredDevices/{id}` with card ID and that output, then must verify final-response `success: true`; only this completion connects the device to the card (419–429, 658–660). One device per card is registered; a new registration deregisters its predecessor, while separately associating further cards to an already registered device is allowed (105–109, 662). Registration alone proves no later authentication or payment approval.
