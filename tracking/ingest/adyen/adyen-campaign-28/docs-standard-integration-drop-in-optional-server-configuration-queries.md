Q1. How can Standard Drop-in update a cart amount before payment, and when does that become final?
A1. This optional path starts a session with `payable: false` so its amount can be updated before the shopper submits (raw lines 24–81). The server PATCHes the session with original `sessionData`, amount and `payable`; setting `payable: true` makes the session payable and prevents further updates (raw lines 83–123). Client Drop-in can show interim amounts, but the final amount for the server PATCH must come from the merchant server, not the client; `beforeSubmit` resolves with returned sessionData (raw lines 125–171). Q2. Can the optional server session-result GET be polled for the final payment outcome, and do the version snippets prove compatibility?
A2. No. The server can GET a result using session ID and `sessionResult` from completion/failure events (raw lines 174–182), but its status is an immutable snapshot; use webhooks or Customer Area Transactions for later updates (raw lines 340–378). `paymentPending` is explicitly asynchronous, and a completed/authorized result is not capture or settlement proof (raw lines 369–378). The lookup curl sample is v70 and older libraries appear alongside v72 creation/PATCH examples, so they do not establish a required or tested mixed-version Standard implementation (raw lines 40–45, 97–111, 184–337).
