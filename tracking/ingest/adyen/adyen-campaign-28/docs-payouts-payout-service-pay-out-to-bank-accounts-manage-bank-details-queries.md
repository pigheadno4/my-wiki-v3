Q1. How does this Payout Service guide create a reusable third-party bank-detail token, and what must be enabled?
A1. The dated guide requires a Payout Service integration, Checkout API, company API credential with the named Checkout encrypted cardholder data role, webhook handling and Adyen-contact feature enablement (raw lines 25–37). It shows a zero-value `POST /payments` with bank details, `enablePayOut`, `storePaymentMethod`, `shopperReference` and other fields (raw lines 54–112). A token follows successful authorization and its ID is in the response or `recurring.token.created`; store it with the tokenization shopper reference for a later payout request (raw lines 519–565). Q2. Does a created token validate the recipient bank account or prove a bank payout, and can local details serve cross-border transfers?
A2. No. The guide says tokenization does not validate bank accounts and invalid details can fail at payout time; local account details cannot be used for cross-border transfers and a supported cross-border identification format is needed (raw lines 34–35). Its listed tokenized local formats are SEPA IBAN, UK Local/BACS and US Local/ACH (raw lines 39–52). Successful authorization creates a token, while an actual bank payout is a separate child-guide request (raw lines 519–571). No PCI conclusion or deletion rule is supplied by this page.
