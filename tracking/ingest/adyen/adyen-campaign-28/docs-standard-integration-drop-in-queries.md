# docs-standard-integration-drop-in — worker retrieval checks

Q1. What is the Standard Drop-in integration and what components and versions does this guide require?
A. The page is an online-payments Web Drop-in Sessions integration: merchant payment server creates a Checkout session, client website uses session data to mount Drop-in and handle shopper flow, and a webhook server receives outcomes (raw lines 15–19, 42–68). It specifies Checkout API v72+, server library released March 30, 2026 or later and Web Drop-in v6.30.0+ (lines 46–54), plus credential/role and standard-webhook preparations (lines 21–40). Q2. What happens on redirect or failure, and what outcome claims are bounded?
A. A returning shopper's `sessionId` and `redirectResult` are submitted with `submitDetails`; if the shopper does not return, the guide says wait for the server webhook (raw lines 983–1024). Client callbacks provide current shopper status, while order management uses the standard `AUTHORISATION` webhook and its success flag (lines 1026–1036, 1054–1134); neither session creation nor authorization proves capture/settlement. The request table has unresolved required-icon versus conditional/recommended descriptions for `countryCode` and `shopperEmail` (lines 473–475), and embedding/SSR/CSP can alter flow (lines 35–38).
