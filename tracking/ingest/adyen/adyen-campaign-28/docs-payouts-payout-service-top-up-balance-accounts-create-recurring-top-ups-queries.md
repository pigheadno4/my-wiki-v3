Q1. What moves where in a recurring top-up, and what gates creation and triggering?

A1. This enterprise-payouts feature configures direct-debit pulls from a funding bank/transfer instrument into a balance account (raw lines 19–27). API creation needs BankAPI Advanced Webservice role and accepted Terms of Service; Customer Area needs Balance platform base/Configure scheduled payouts roles and wizard acceptance of the direct-debit agreement (raw lines 28–38, 248–252). The account holder needs active receiveFromTransferInstrument capability with valid verificationStatus; only EUR/USD recurring, not on-demand, is supported (raw lines 34–38). The API schedule includes source counterparty, amount, threshold and optional check frequency; fixed and target branches are mutually exclusive (raw lines 40–99). Q2. Does an active schedule or trigger prove credit, and what conflicts or failures limit a reliable implementation?

A2. No. The example has USD 500 available versus a USD 250 threshold, so its active create response does not show a triggered debit or credited balance (raw lines 103–178). The API text says trigger **below** threshold, while the Customer Area wizard says **at or below** (raw lines 99, 242); the fixed amount table says `topUpAmount.fixed` but a later example uses `fixedAmount` (raw lines 76–83, 203–225). A triggered top-up creates a transfer record, while later status, transaction and report evidence must establish movement (raw lines 254–268); failed configuration/capability/terms/route conditions have explicit errors (raw lines 277–304).
