Q1. How does Standard Hosted Checkout create and reuse a stored-payment token, and what prerequisites apply?
A. The guide covers Hosted Checkout storage and shopper-initiated one-click reuse (raw lines 15–26). It lists Checkout webservice/Merchant Recurring credential roles, a Recurring tokens life cycle events webhook and recurring-capable payment methods (lines 28–38). Ask consent before payment; create a session with Ecommerce, CardOnFile and storage mode; a token follows successful authorization and arrives as `recurring.token.created`, whose `storedPaymentMethodId` is stored with `shopperReference` (lines 104–179). A later session presents stored details and its payment outcome comes by webhook (lines 181–225). Q2. Which consent, amount, example and outcome boundaries qualify the guide?
A. `askForConsent` shows a Hosted Checkout checkbox and `enabled` does not, but the merchant is still told to seek consent before the shopper pays (raw lines 108, 118–123). Zero-value authorization is conditional because some methods such as iDEAL require a positive minimum (lines 123–125). The one-click table says Ecommerce but its example sends ContAuth; the page does not resolve that mismatch and notes possible SCA on ContAuth/CardOnFile (lines 190–193, 216). Token receipt and browser return do not prove later payment, capture or settlement; use the separate payment-outcome webhook (lines 76–83, 221–225).
