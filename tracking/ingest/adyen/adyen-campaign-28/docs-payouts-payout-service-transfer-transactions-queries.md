# Query proposal — docs-payouts-payout-service-transfer-transactions

Q1. How are Payout Service-path balance-account transactions queried, and how do their IDs differ from transfer IDs?
Answer: The Transfers API `GET /transactions` can query platform, holder or balance-account scope, with a required one-of identifier and createdSince/createdUntil window; `data` and `_links` support records and pagination (raw lines 19, 38-53, 226-229). `GET /transactions/{id}` uses the transactionId (line 354). Each sample record's own `id` is distinct from nested `transfer.id` (lines 236-264, 267-318). The raw allows Platforms, Issuing or Payouts integrations and requires Retrieve role/source transfer enablement (lines 21-27). Q2. What does signed amount/booked status establish, and what example caveat matters?
Answer: Positive `amount.value` adds to that balance account; negative deducts, and pending versus booked distinguishes reserved/pending from completed balance-account credit/debit (raw lines 356-366). `bookingDate` and `valueDate` separate recording from availability/deduction, with outgoing deduction at booked (lines 489-498). External bank/card payout and internal transfers are distinct categories (lines 368-411). The outgoing and incoming internal records are separate illustrations with different transaction **and nested transfer** IDs, so the page does not establish that they are paired sides of one transfer (lines 419-486). The list example's first transaction ID ends EUR but `amount.currency` is USD (lines 240-247), so it is not reliable currency-reconciliation evidence. None of this proves an external beneficiary received funds.
