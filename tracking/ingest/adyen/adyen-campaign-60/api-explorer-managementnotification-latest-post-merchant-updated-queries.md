## Q1

The captured `ManagementNotification/latest` POST page defines an incoming `merchant.updated` webhook about changes to a merchant account's verification status and capabilities; failed verification can bring errors and remediation actions (raw lines 5–7). It is a merchant-account resource notification, not a merchant management request or payment event. Required top-level body fields are `createdAt`, `data`, `environment`, and `type`; within `data`, `capabilities`, `merchantId`, and `status` are required, while `legalEntityId` is optional (lines 11–16, 25–29). Each capability value has required `requested` and `requestedLevel`, with optional `allowed`, `allowedLevel`, `capability`, `problems`, `verificationDeadline`, and `verificationStatus` (lines 16–24). `capabilities` is keyed by capability; `sendToTransferInstrument` is the payout-to-bank example in the description and `receivePayments` appears in the payload examples (lines 16, 33–53). `verificationStatus` can be `pending`, `invalid`, `valid`, or `rejected`; optional `problems` can contain entities, errors and remediation actions (lines 20, 24, 55–124). `merchantId` identifies the merchant account; optional `legalEntityId` identifies a legal entity (lines 25–26). `environment` is test or live, and the example `type` is `merchant.updated` (lines 28–29, 35–38). `createdAt` is the webhook-creation timestamp (line 14); no delivery timing follows from it.

## Q2

The merchant `status` enum is `PreActive`, `Active`, `InactiveWithModifications`, `Inactive`, and irreversible `Closed`, with distinct Customer Area, payment-processing, and payout effects (raw line 27). `Active` processing and payouts also require the company account to be Active; `PreActive` cannot process payments. The valid example has `receivePayments.allowed: true` and `verificationStatus: valid` while merchant `status` remains `PreActive` (lines 33–53), so capability verification alone is not processing readiness. The error example has `allowed: false`, `verificationStatus: invalid`, and illustrative legal-entity remediation detail, still with `PreActive` status (lines 55–124). The page's `200 Success` response and optional `notificationResponse` state that any `2xx` accepts the webhook (lines 125–133); acceptance is separate from status/capability state and proves no payment or payout. The pinned reference states no delivery-order, retry, deduplication, or signature-verification rule. `latest` is the captured 2026-09-15 API Explorer path (lines 1–3), not proof of current version or account eligibility.
