# Retrieval checks — GrabPay API only

## Q1. What is this source's purpose and scope, and what cannot be inferred?

The detailed request/return walkthrough uses `/payments` and `/payments/details` (raw lines 65–79 and 897–957); its listed Sessions prerequisite does not itself make this a complete Sessions procedure. It does not prove current merchant enablement, availability, capture or settlement. ## Q2. What central capability, prerequisites and warnings matter?

Both Wallet and PayLater requests specify `grabpay_XX`, return URL, reference and amount, while PayLater adds delivery address and item data with nonzero `amountIncludingTax` (raw lines 65–79 and 397–409); PayLater is excluded in PH (raw line 61). The `/payments` response action directs redirect, then `/payments/details` consumes URL-decoded `redirectResult` after return (raw lines 381–395 and 897–935). Pending/Received require final AUTHORISATION webhook, and a shopper who never returns requires webhook-based outcome handling; AUTHORISATION and OFFER_CLOSED event meanings are tabulated (raw lines 959–974). TEST requires Support-provided wallet credentials; live acceptance requires a separate live Customer Area request (raw lines 976–985). Mixed v68 `/payments` and v72 `/payments/details` samples and mobile-browser advice are not proof of runtime compatibility or a native integration (raw lines 83, 901–922).
