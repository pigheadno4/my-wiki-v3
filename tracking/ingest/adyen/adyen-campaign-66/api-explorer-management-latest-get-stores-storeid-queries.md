# api-explorer-management-latest-get-stores-storeid — original query answers

## Q1

The 2026-11-03 Management API v3 capture describes `GET /stores/{storeId}` as a read of the store identified by required path `storeId`, on listed TEST server `https://management-test.adyen.com/v3`. The caller's API credential must have **Management API—Stores read** or **Management API—Stores read and write**. There is no query or body input in the captured parameter table. The `200` response can include Adyen-generated store `id`, owning merchant `merchantId`, human-readable store `reference`, address, associated `businessLineIds`, country-specific `externalReferenceId`, localized/shopper statements, split profile and balance-account references, payment-facilitator `subMerchantData`, status, and links. Top-level response fields are marked optional; nested required fields and conditional descriptions are scoped to their containing objects or use cases. Live rate limits are mentioned without numeric values. ## Q2

A `200` establishes store-detail readback, not creation or activation of a store, terminal assignment/boarding, payment-method readiness, split booking, payment execution, settlement or bank receipt. Status semantics in the response description are consequential: `active` is assigned on creation; `inactive` prevents new terminal transactions but outstanding captures remain possible; `closed` is irreversible and moves terminals to merchant inventory. Authentication and permissions can fail (`401`, `403`), as can request/validation (`400`, `422`) or server processing (`500`). This GET does not specify idempotency, deletion, propagation, asynchronous review/approval or reversal. The TEST server is `/v3`, but the `200` example self-link is `/v1/stores/...`; that contradiction prevents treating the sample link as the endpoint route. The dated capture does not prove present access or live readiness.
