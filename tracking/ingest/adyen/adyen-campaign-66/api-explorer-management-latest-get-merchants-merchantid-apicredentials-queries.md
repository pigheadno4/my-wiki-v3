# Original query answers — api-explorer-management-latest-get-merchants-merchantid-apicredentials

## Q1

For `GET /merchants/{merchantId}/apiCredentials`, the 2026-11-03 Management API v3 snapshot lists API credentials for the merchant account selected by required string path `merchantId`, in pages. Its listed server is TEST `https://management-test.adyen.com/v3`. The caller's API credential must have `Management API—API credentials read and write`. Optional `pageSize` defaults to 10 with maximum 100, and optional `pageNumber` selects the page; no request body or conditional input is specified. A 200 requires `itemsTotal` and `pagesTotal`, with optional `data` records and pagination `_links`; if the latter appears, `first`, `last` and `self` are required within it, and `next`/`prev` are conditional. Each credential record requires `active`, `allowedIpAddresses`, public `clientKey`, `id`, `roles` and `username`, with optional allowed origins, description, subject DN and resource links. An empty IP list permits requests from any IP; a nonempty list causes a security error for requests from unlisted IPs. The schema contains no secret API-key value. A separate 204 has no content. Source: [[source-adyen-api-explorer-management-latest-get-merchants-merchantid-apicredentials]]; https://docs.adyen.com/api-explorer/Management/latest/get/merchants/(merchantId)/apiCredentials; verified pinned raw lines 5–74.

## Q2

A 200 establishes a successful, paginated read of credential metadata; 204 establishes successful processing without content. `active=true` is required to use a credential, but returned roles, client key, IP restrictions and links do not prove successful authentication, effective account/endpoint scope or Live access. `generateApiKey` and `generateClientKey` are optional links whose descriptions mention 24-hour overlap after generation; this GET itself does not generate, rotate or deactivate a key. It does not establish payment authorization or financial outcome. The page lists 400, 401 authentication-required, 403 insufficient-permission, 422 and 500 errors, with no GET idempotency, deletion/propagation, asynchronous approval/activation, reversal or version-conflict rule. **Contradiction:** the stated TEST server uses `/v3`, while sample pagination and credential links use `/v1`; the example cannot settle the v3 resource-link route. The `latest` URL and sample credentials are a dated snapshot, not current eligibility proof.
