## Q1

The 2026-11-03 capture describes Management API v3 `PATCH /stores/{storeId}` for changing supported fields of the unique store ID in the path, at listed TEST server `https://management-test.adyen.com/v3` (raw lines 5–24). The API credential requires Management API—Stores read and write; the page mentions Live rate limits without a number (lines 10–17). Top-level request fields are optional: address (except country cannot change), business-line IDs, description, external reference, phone, split configuration (balance-account and split-profile IDs), status, and registered-facilitator `subMerchantData` for standalone terminals. The four children of `subMerchantData` are required when that object is supplied; `stateOrProvince` and external reference have described country-specific conditions (lines 27–49). A 200 returns store configuration, including Adyen-generated store `id`, merchant `merchantId`, optional address, business-line, split and status fields; its response description says business-line IDs fall back to the merchant-account business line if unspecified and are required with multiple merchant business lines (lines 86–125). ## Q2

A 200 reports a successful store update and returns store configuration, not terminal boarding, payment-method enablement, transaction acceptance, split booking, payout or bank receipt (raw lines 88–125). Active can move to inactive; inactive can move to active or closed. Inactive blocks new transactions but permits outstanding captures. Closed reassigns terminals to merchant inventory and cannot reopen (line 44; response line 120). The capture lists authentication/permission errors 401/403 and 400, 422 and 500; no idempotency, propagation delay, asynchronous review/approval, reversal or 409 conflict contract is stated (lines 128–225). The example `self.href` uses `/v1/stores/` despite the listed `/v3` TEST server (lines 17, 252–253, 285–286), so it cannot establish a v3 link route.
