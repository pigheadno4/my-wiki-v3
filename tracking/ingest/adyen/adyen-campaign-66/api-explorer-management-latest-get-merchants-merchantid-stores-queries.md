# Original query answers — api-explorer-management-latest-get-merchants-merchantid-stores

## Q1

For `GET /merchants/{merchantId}/stores`, the 2026-11-03 Management API v3 snapshot describes a paginated list of stores belonging to the merchant account identified by the required string path `merchantId`. The listed server is TEST `https://management-test.adyen.com/v3`; the page notes Live rate limits without giving a numeric value. The calling API credential must have `Management API—Stores read` or `Management API—Stores read and write`. Optional query `reference` selects a store reference, `pageSize` defaults to 10 with maximum 100, and `pageNumber` chooses the page. No body or conditional GET input is specified. A 200 has required `itemsTotal` and `pagesTotal`, optional pagination `_links` and optional `data` store array. If `_links` appears, `first`, `last` and `self` are required within it; `next` and `prev` depend on adjacent pages. Listed store data can include Adyen-generated store `id`, its `merchantId`, `reference`, address, business-line and external-reference fields, shopper statements, split configuration, `status`, and sub-merchant data. Those nested fields and their conditional descriptions are response schema, not GET parameters. A 204 has no additional content. Source: [[source-adyen-api-explorer-management-latest-get-merchants-merchantid-stores]]; https://docs.adyen.com/api-explorer/Management/latest/get/merchants/(merchantId)/stores; verified pinned raw lines 5–89.

## Q2

A 200 establishes a successful store-list read with reported counts and any returned store records; 204 establishes successful processing without additional content. Neither proves the stores are ready to take payments, terminals are assigned and boarded, payment methods are enabled, or a payment was authorized or captured. The returned `status` description says `active` is assigned on creation, `inactive` blocks new terminal transactions while outstanding captures remain possible, and `closed` is irreversible with terminals reassigned to merchant inventory; this GET does not perform those lifecycle changes. Credential roles are specified, with 401 authentication-required and 403 insufficient-permission errors; 400, 422 and 500 are also listed. The raw gives no idempotency, deletion/propagation action of the GET, asynchronous review/approval/activation, reversal or version-conflict behavior. The `latest` URL and TEST server are a captured reference, not proof of current Live eligibility. **Contradiction:** the stated server is `/v3`, but sample pagination/store links use `/v1`; the sample reports `pagesTotal: 1` while its last/next links point to page 2. Those links and counts do not establish a consistent v3 pagination result.
