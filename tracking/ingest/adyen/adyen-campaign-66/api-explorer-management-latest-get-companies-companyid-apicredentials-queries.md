# api-explorer-management-latest-get-companies-companyid-apicredentials — original query answers

## Q1

The 2026-11-03 Management API v3 TEST capture lists a company account's API credentials through `GET /companies/{companyId}/apiCredentials`; required `companyId` identifies that company, and the caller needs the **Management API—API credentials read and write** role. The listed server is `https://management-test.adyen.com/v3`. Optional `pageSize` defaults to 10 and is capped at 100; optional `pageNumber` selects a page. The `200` body requires `itemsTotal` and `pagesTotal` and may include pagination `_links` and `data`. Within each credential item, the table requires `id`, `username`, public `clientKey`, `active`, `roles`, and `allowedIpAddresses`; optional fields include allowed origins, explicit associated merchant accounts, `subjectDN`, description and links. An empty allowed-IP list permits any source IP; company-level access implies all merchant accounts, so such merchants are omitted from the explicit association list. ## Q2

A `200` is a paged read of credential metadata and counts. The `active` flag, role labels, merchant associations, allowed origins and key-generation links do not prove a successful authenticated request, live entitlement, generated key, client-side acceptance or payment. The key links' descriptions say an existing key stays valid for 24 hours when a new API/client key is generated, but this GET performs no generation. The reference lists `400`, `401`, `403`, `422` and `500` errors and does not specify idempotency, deletion, propagation, approval, reversal or financial finality for the read. Its TEST server is `/v3`, while the entire illustrative response uses `/v1` links; those links are not reliable v3-route evidence. A dated capture does not prove present access or live eligibility.
