# Original C66 query answers: api-explorer-management-latest-patch-merchants-merchantid-users-userid

## Q1

The captured Management API v3 TEST reference describes `PATCH /merchants/{merchantId}/users/{userId}` at `https://management-test.adyen.com/v3`. It updates a user identified by required path `userId` under required `merchantId`; the API credential must have `Management API—Users read and write`. Every listed body field is optional: `accountGroups`, `active`, `email`, `loginMethod`, `name.firstName/lastName`, `roles` and `timeZoneCode`. `active` sets active or inactive; `loginMethod` is `Email` or `SSO`, with the page saying SSO must already be configured before creating a user. No default or numeric limit is stated. A `200` response schema includes user `id`, `username`, `email`, `roles`, `timeZoneCode`, optional active flag, account groups, apps, name and link. `204` has no content. ## Q2

A `200` reports request success with a user-detail response; a `204` reports successful processing without a payload. The optional returned `active` flag and roles are readback, not evidence of effective permission, SSO enrollment, successful login or live access. The page describes an active/inactive setting but does not state a deletion, reversal, propagation delay, asynchronous review/approval or activation workflow. It gives no idempotency or version/conflict rule. `401` means authentication required, `403` insufficient permission, with `400`, `422` and `500` also listed. The capture lists a TEST `/v3` server and cannot establish current live eligibility or any payment/financial result.
