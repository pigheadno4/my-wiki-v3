# Original C66 query answers: api-explorer-management-latest-post-merchants-merchantid-apicredentials

## Q1

The captured Management API v3 TEST reference describes `POST /merchants/{merchantId}/apiCredentials` at `https://management-test.adyen.com/v3`. The required path table calls `merchantId` a merchant-account ID, while the introduction calls it a company account; this conflict is unresolved. The calling credential needs `Management API—API credentials read and write`. Optional request fields are `allowedOrigins`, `description` and `roles`; only roles assigned to `ws@Company.<CompanyName>` can be delegated. No whole-body requiredness or default is given. The `200` response schema marks `active`, `allowedIpAddresses`, `apiKey`, `clientKey`, `id`, `password`, `roles` and `username` required as properties, with optional origin and resource links. The API key authenticates API requests, client key is public for client-side use, and username/password support Basic authentication. The API key cannot be retrieved later. An empty allowed-IP list allows any IP; a nonempty list blocks unlisted IPs. `204` has no content. No numeric rate limit is stated. ## Q2

A `200` reports request success and can return credential details, while `204` reports successful processing without content. `active=true` is necessary for integration use, but creation/readback does not prove successful authentication, effective downstream permissions, live eligibility or payment execution. The API key must be stored because it cannot be retrieved later; lost/compromised keys require a new generation. The response-link descriptions say existing API/client keys remain valid for 24 hours when replacements are generated, a separate later rotation step. The page does not specify idempotency, propagation timing, asynchronous approval or a version-conflict rule. It lists `401` authentication required, `403` insufficient permissions, plus `400`, `422`, `500` errors. The company-versus-merchant wording is unresolved; the TEST server is `/v3` while the example includes company-scoped `/v1` credential links, which do not establish subsequent-call routing. A dated `latest` capture does not prove current live access.
