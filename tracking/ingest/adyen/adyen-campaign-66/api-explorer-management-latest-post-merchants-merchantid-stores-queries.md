# Original C66 query answers: api-explorer-management-latest-post-merchants-merchantid-stores

## Q1

The captured Management API v3 reference describes `POST /merchants/{merchantId}/stores` on `https://management-test.adyen.com/v3`; the required path `merchantId` names the merchant account under which to create a store. The API credential needs `Management API—Stores read and write`. The request-body table marks `address`, `description`, `phoneNumber` and `shopperStatement` required, with required `address.country` and conditional `stateOrProvince` for Australia, Brazil, Canada, India, Mexico, New Zealand and the US. `businessLineIds` becomes required with multiple merchant business lines; otherwise the merchant's business line is used. `externalReferenceId` is required for Brazil CNPJ, optional for France SIRET and Australia Zip. Optional `reference` defaults to Adyen's generated store `id`; `shopperStatement` is at most 22 characters and cannot be all digits. Optional localized, split-configuration and payment-facilitator sub-merchant objects contain their own nested conditions. A `200` response schema has optional Adyen-generated `id`, `merchantId`, `reference`, `status`, address and other fields; `204` has no content. Live rate limits are linked but no values are given. [[source-adyen-api-explorer-management-latest-post-merchants-merchantid-stores]]; [captured API reference](https://docs.adyen.com/api-explorer/Management/latest/post/merchants/(merchantId)/stores); verified raw lines 5–54 and 76–119.

## Q2

The documented `200` means the store-creation request succeeded and can return a store record; `204` says the request was processed without additional content. A new store's status is assigned `active` automatically. The status descriptions also say `inactive` blocks terminals under the store from new transactions while outstanding captures remain possible, and `closed` is irreversible and reassigns terminals to merchant inventory. None of this demonstrates terminal assignment, payment-method activation, payment authorization/capture, split booking, settlement, or bank receipt. The page lists `401` for required authentication, `403` for insufficient permission, and `400`, `422`, `500` failures; it gives no idempotency contract, propagation timing, asynchronous approval/review step, or reversal mechanism. The listed server is TEST `/v3` while the `200` example self-link is `/v1/stores/`; this mismatch is unresolved. This 2026-11-03 `latest` capture cannot prove current live availability or eligibility.
