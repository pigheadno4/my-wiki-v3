# Original query answers — api-explorer-management-latest-get-merchants-merchantid-payoutsettings-payoutsettingsid

## Q1

For `GET /merchants/{merchantId}/payoutSettings/{payoutSettingsId}`, the 2026-11-03 Management API v3 snapshot returns one payout setting for a merchant account. Its listed server is TEST `https://management-test.adyen.com/v3`. Adyen says to use the endpoint if an integration requires it, such as Adyen for Platforms Manage, and that an Adyen contact sets up access. The API credential needs `Management API—Payout account settings read`. Both string path IDs are required: `merchantId` is the merchant account and `payoutSettingsId` is the setting. No query/body/conditional input or numeric rate limit is specified. A 200 requires response `id` and `transferInstrumentId` (bank-detail transfer instrument); optional fields are verification-derived `allowed`, `enabled` (default true), `enabledFromDate`, `priority` and `verificationStatus`. The page says both `enabled` and `allowed` must be true to receive payouts, and explains how a specified enable date changes `enabled`. Status values are valid/pending/invalid/rejected; priority values are first/urgent/normal with payout-frequency and bank/currency timing qualifications. A separate 204 has no content. Source: [[source-adyen-api-explorer-management-latest-get-merchants-merchantid-payoutsettings-payoutsettingsid]]; https://docs.adyen.com/api-explorer/Management/latest/get/merchants/(merchantId)/payoutSettings/(payoutSettingsId); verified pinned raw lines 5–44.

## Q2

A 200 establishes a successful read of the payout-setting fields, while 204 says the request was processed without additional content. `allowed=true` reflects the table's `verificationStatus=valid` condition, and `enabled=true` is a separate setting; the page requires both for payouts into that bank account but does not say they alone cause or prove a payout. The stated first/urgent/normal priority timing is qualified by payout frequency, currencies and banks, with arrival potentially taking up to three days; none of this is bank-receipt evidence. The role and Adyen-contact access setup remain distinct from an actual caller's grant or Live eligibility. The endpoint lists 400, 401 authentication-required, 403 insufficient-permission, 422 and 500 errors. It states no idempotency, mutation/deletion/propagation or reversal effect for this GET, asynchronous review/approval/activation completion, or version-conflict rule. The `latest` URL and TEST server are a dated snapshot, not current eligibility or financial-outcome proof.
