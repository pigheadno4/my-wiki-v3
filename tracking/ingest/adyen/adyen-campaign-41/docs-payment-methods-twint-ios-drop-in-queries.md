# TWINT iOS Drop-in — Q1/Q2

## Q1 — Purpose and scope; what cannot be inferred?

The canonical source `source-adyen-docs-payment-methods-twint-ios-drop-in` is a 2026-09-15 capture of TWINT-specific additions to an **existing** iOS Drop-in integration; it separates Sessions and Advanced server flows (raw `raw/adyen/docs/payment-methods/twint/ios-drop-in/2026-09-15.md:15-25`, `:97-107`). It does not alone prove present-day method eligibility, enabled merchant status, successful redirect completion, token delivery or payment outcome: live use needs a Customer Area request, and the token ID arrives by a later webhook when details have been stored (same raw `:64-71`, `:95`, `:137-144`, `:168`). ## Q2 — Central capability, prerequisites and warnings

Sessions requires an existing iOS Drop-in integration using Checkout API v68+ and adding TWINT in Customer Area; ordinary `/sessions` and Drop-in configuration need no extra TWINT parameters (same raw `:25-46`). Advanced requires an existing iOS Drop-in integration that handles a `redirect` action and TWINT Customer Area setup; ordinary `/payments` and Drop-in configuration likewise need no extra method parameters (same raw `:97-119`). Recurring is a **separate** `/payments` path: send `storePaymentMethod: true` and a three-character-minimum shopper reference, receive `storedPaymentMethodId` by `recurring.token.created`, then use it with the same shopper reference, `ContAuth`, and Subscription or UnscheduledCardOnFile (same raw `:48-87`, `:121-160`). The recurring block repeats at `:170-207` and is not an additional flow. TEST status is in test Customer Area; live acceptance requires a TWINT request in live Customer Area (same raw `:89-95`, `:162-168`).
