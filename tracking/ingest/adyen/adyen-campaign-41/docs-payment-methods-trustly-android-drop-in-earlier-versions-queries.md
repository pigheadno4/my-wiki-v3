## Q1 — What is this page for, and what cannot be inferred?

[[source-adyen-docs-payment-methods-trustly-android-drop-in-earlier-versions]] documents Trustly Android Drop-in v4.x.x as an add-on to an existing Advanced-flow Drop-in integration, from supported-country/currency discovery through server `/payments`, Trustly redirect, return to app, `/payments/details`, and webhook outcomes (raw lines 15–45, 348–421). Its introduction and See also routes link Sessions-flow guides despite the explicit Advanced requirement, so those links do not establish this procedure as Sessions-compatible (raw lines 19, 25, 431–435). SE/SEK, the package URL, v68 `/payments`, v72 `/payments/details`, SDK versions and an `Authorised` response are examples; they do not establish universal requirements, current live eligibility, or a real successful payment (raw lines 34–36, 47–346, 374–399).

## Q2 — What central capability, prerequisites, and warnings are stated?

[[source-adyen-docs-payment-methods-trustly-android-drop-in-earlier-versions]] requires Advanced Android Drop-in and Trustly in Customer Area; `/paymentMethods` uses a supported country/currency and amount, then the client hands `paymentComponentData.paymentMethod` to the server for `/payments` with a Component-derived `returnUrl` (raw lines 21–45). The response `action` redirects to Trustly; on return, the app hands `actionComponentData.details` to the server for `/payments/details` (raw lines 348–390). `Pending`/`Received` are not final, and a missed shopper return calls for webhook outcome tracking; `AUTHORISATION` true/false and `OFFER_CLOSED` true have distinct meanings (raw lines 401–421). The earlier-version table calls `Authorised` successful and says funds will arrive in three days (raw line 409), but [[source-adyen-docs-payment-methods-trustly]] says successful `AUTHORISATION` confirms checks and an initiated transfer, not funds received; the transfer can still fail, `SentForSettle` persists until receipt, and eight calendar days without funds can lead to `Chargeback` and a webhook (overview raw lines 40–51). Authorization or an initiated transfer is not a receipt guarantee. Live acceptance requires a Trustly request in live Customer Area (raw lines 423–429).
