## Q2 — What payment and token capabilities have which prerequisites and warnings?

After an Adyen test account, Support must enable OPI in Customer Area (raw lines 33–40). The feature list distinguishes a temporary check-in preauthorization hold, possible top-up/release, checkout Sales Completion, direct Sale/Purchase, refunds, same-settlement-day Void and connection-loss/timeout Reversal (lines 48–68). Get Token and Get Token Bulk are listed for later use or migration scenarios, without proving a migration outcome (lines 68–74). Ecommerce OPI tokens require separate Support-enabled merchant-account settings. For this OPI flow the `/payments` table instructs `additionalData.opi.includeTransToken=true`, `shopperInteraction=Ecommerce`, `shopperReference=not_provided`, `recurringProcessingModel=CardOnFile` and `storePaymentMethod=true`; `opi.transToken` is a response output, not a request input (lines 76–94, 115–136). `not_provided` is this guide's stated request value, not a universal stored-credential permission or identity rule. The shown `Authorised` response is only an example, not proof of a payment outcome (lines 125–143). Use the proposed concept→source→raw route and keep hold, charge, token and financial outcome distinct.
