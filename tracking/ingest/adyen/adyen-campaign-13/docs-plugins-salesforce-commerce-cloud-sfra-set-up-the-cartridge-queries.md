## Q1 — Purpose, scope, and what not to infer

**Question:** What does this SFRA setup guide configure, and what does it establish about a merchant integration?

**Answer:** The 2026-09-15 guide configures Adyen's **Salesforce Commerce Cloud SFRA cartridge** through Customer Area and Salesforce Business Manager. It starts with a test account, imported metadata and site-wide HTTPS; Salesforce is described as allowing one Adyen merchant account per storefront (raw lines 19–68). It then routes storefront/Business Manager cartridge paths, API and client keys, account environment settings, webhooks and optional features (lines 45–431). The page does not pin an installed package version or prove a live account, eligible payment method, webhook delivery, payment result, capture, refund, settlement or processed order. A feature version floor of v20.1.3 applies only to Level 2/3 data and system-integrator info here (lines 355–385). ## Q2 — Central setup, prerequisites, and warnings

**Question:** Which credentials, webhook/order-processing and test-to-live steps matter, and how should optional paths be read?

**Answer:** Generate the server API key and client key for the integration credential, store the API key securely because it cannot be copied again after leaving the page, configure client-key allowed origins, and enter both in Business Manager (raw lines 70–113). The guide uses **Test** while integrating and sends **Live**, live prefix and front-end resource region to a separate go-live path; enable its SFRA v6/v7 switch only for those versions (lines 117–131). The Standard webhook uses a server URL ending `/Adyen-Notify`, HTTP POST, TLS 1.3 and Basic auth, with HMAC strongly recommended; SFCC must acknowledge it with a successful HTTP response such as 202 (lines 133–201). After metadata import, the `Process` scheduled job processes stored webhook objects to update order payment status and `Clean` deletes them; a one-minute interval is a recommendation (lines 203–216). Optional tokenization has a saved-detail deletion setup through Support; optional in-person endless aisle has separate merchant/site and Terminal API store mapping; Giving needs campaign and method conditions; case management needs RevenueProtect premium and a manual-review configuration before capture (lines 218–345). The CSC path creates a **pending** payment link; the order is processed only after the shopper completes payment, and the link/status has inspection routes (lines 433–449). No configuration step or test webhook alone proves an actual payment or order outcome.
