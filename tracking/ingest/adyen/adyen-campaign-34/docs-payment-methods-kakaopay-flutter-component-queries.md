# KakaoPay Flutter Component retrieval questions

## Q1 — What is this guide for, and what is required?

It adds KakaoPay to an existing Flutter Components integration. Sessions requires Checkout API v68+, redirect handling and Customer Area method addition (raw lines 25–34); Advanced requires redirect handling and method addition, without a repeated v68 row (lines 298–308). Ordinary base `/sessions` and Advanced `/payments` calls need no KakaoPay-specific extra parameters or configuration (lines 36–46, 310–320). The Integration type links in both tables point to Drop-in, and the Sessions one also points to Advanced, despite Components/Sessions prose (lines 31, 306); independently select the corresponding main guide. ## Q2 — What limits recurring, token and live-outcome claims?

The recurring sections use `/payments` with `storePaymentMethod: true` and unique `shopperReference`, followed by shopper Kakao login/confirmation; only after settlement does `recurring.token.created` supply the token through a merchant-received lifecycle webhook (raw lines 48–73, 322–347). Later token payments need `storedPaymentMethodId`, shopper reference, `ContAuth`, and fixed-interval `Subscription` or non-fixed `UnscheduledCardOnFile` (lines 75–87, 349–361). The sample `v68` requests and KRW/Subscription/TEST client settings illustrate one path, not final payment or live enablement (lines 89–286, 363–560). Live payment testing calls for a real registered mobile number and live method acceptance requires submitting a Customer Area request (lines 288–296, 562–570).
