Q1. What is needed for base KakaoPay Flutter Drop-in, and when do recurring fields apply?
A1. Existing Sessions (Checkout API v68+) or Advanced Flutter Drop-in with redirect handling and Customer Area setup is required; Sessions says contact Support, Advanced says add KakaoPay in Customer Area. No extra method-specific base request/configuration fields are stated (raw lines 25–48, 300–322). For recurring token creation, the merchant includes storePaymentMethod: true and shopperReference in the initial /payments request; this triggers Kakao login and shopper confirmation. Only after that initial payment settles does recurring.token.created supply storedPaymentMethodId; later token payments use that ID, shopperReference, ContAuth and a recurringProcessingModel (raw lines 50–89, 324–363). Q2. Does redirect or token request prove token availability or completed payment, and what example/environment limits apply?
A2. No. The guide conditions recurring.token.created on the initial payment being settled, with storedPaymentMethodId in the webhook (raw lines 66–75, 340–349). Examples differ in KRW amount and returnUrl presence (raw lines 93–143, 154–197), and test/live prose distinguishes a real KakaoPay mobile number for successful live tests, test Customer Area status lookup, and a separate live method request (raw lines 290–298, 564–572).
