# KakaoPay Web Drop-in retrieval questions

## Q1 — What is this guide for, and what is required?

It gives KakaoPay-specific additions to an existing Web Drop-in integration. Sessions requires an existing Sessions flow, Checkout API v68+, redirect handling and Customer Area method addition (raw lines 29–36); Advanced requires existing Advanced Drop-in, redirect handling and method addition (lines 312–318). Its integration-type URL contains an unresolved encoded platform template (line 316); use the stated Web Drop-in context and Web-scoped Advanced step links at lines 317 and 324 instead. No extra parameters are required for the ordinary Sessions `/sessions` or Advanced `/payments` request respectively (lines 40–42, 332–336). Optional tree-shaken import uses `Redirect` (lines 44–54, 320–330). ## Q2 — What limits the recurring and live-payment claims?

Both recurring sections require `storePaymentMethod: true` and `shopperReference` for token creation; the shopper logs in and confirms; the `recurring.token.created` webhook arrives after the initial payment has settled and supplies the token identifier (raw lines 56–81, 338–363). Later `/payments` needs that token, shopper reference, `ContAuth`, and the appropriate fixed-interval `Subscription` or non-fixed `UnscheduledCardOnFile` model (lines 83–95, 365–377). Thus base-request “no extra parameters” does not govern recurring requests. The samples use test environments/KRW/Subscription and do not prove live success (lines 97–294, 379–576). Live acceptance requires a request in the live Customer Area, and testing a successful live payment needs a real registered mobile number (lines 296–306, 578–588).
