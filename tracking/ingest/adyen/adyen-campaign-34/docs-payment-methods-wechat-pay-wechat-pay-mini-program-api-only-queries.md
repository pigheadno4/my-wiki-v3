# WeChat Pay Mini Program API-only retrieval check

Q1. Which roles and prerequisites does this Mini Program guide describe for starting a payment?

It requires an API-only integration and adding WeChat Pay Mini Program in test Customer Area, plus a WeChat Mini Program account and AppID/entity/currency details given to Adyen Support or an Implementation Manager (raw lines 21–40). The Mini Program uses `wx.login()`/`jscode2session` to obtain an `openid`, sends its `wechatpayMiniProgram` request to the merchant server, and the server makes Adyen `/payments` calls. Adyen obtains a WeChat `prepay_id` returned in `redirect.data.package` for `wx.requestPayment()` (raw lines 42–70, 80–203). The live v72 CN/CNY values are example scope. Q2. What does the Mini Program callback prove, and which example/environment conflicts matter?

The callback reports `res.errMsg` as ok, cancel, or failure and passes paymentData/paymentStatus through the merchant server for `/payments/details`; Pending/Received still await the final AUTHORISATION webhook (raw lines 205–286). The Step 4 curl labeled as a details request actually targets `/payments` and lacks a comma; the sequence diagram note also conflates `wx.requestPayment()` with `/payments/details`, despite the server arrows/prose (raw lines 52–70, 233–255). Test Customer Area references and live URLs appear alongside a no-test-platform statement and advice about cancellation or low-value live tests (raw lines 25–26, 72–78, 148–169, 288–295). None proves a real authorization, capture or settlement.
