# Retrieval checks

Q1. What are the base iOS Drop-in conditions and the additional KakaoPay recurring-token stages?
Answer: Sessions requires existing iOS Drop-in Sessions, Checkout API v68+ and Customer Area KakaoPay, with no extra base method-specific `/sessions` or configuration parameters (raw lines 25–46). Advanced requires its existing iOS Drop-in, explicit redirect handling and Customer Area KakaoPay, with no extra base method-specific `/payments` or configuration parameters (raw lines 300–322). Recurring starts with `storePaymentMethod: true` and `shopperReference` on `/payments`, shopper login/confirmation, then a token-created webhook **after settlement**; later requests use its token, the same shopper reference, `ContAuth` and the stated processing model (raw lines 48–87 and 324–363). Q2. What limits apply to sample versions, live testing and payment outcomes?
Answer: Curl uses TEST Checkout v68 and examples name particular API-library versions, placeholders and differing KRW amounts (raw lines 89–285 and 365–561); they do not set a universal iOS SDK version or prove execution. The page says live testing requires a real registered number yet directs “test payments” to the test Customer Area, without explaining the environment relationship; live acceptance separately needs a Customer Area request (raw lines 288–298 and 564–574). Token delivery is settlement-conditioned and a later token request is not proof of later authorization/capture/settlement (raw lines 66–73, 342–349).
