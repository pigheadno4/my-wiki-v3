Q1. What does this Android Component guide require in Sessions versus Advanced UPI Intent?
A1. Sessions requires existing Android Components, Checkout API v68+ and Customer Area UPI, with no extra /sessions parameters and optional submit-button visibility (raw lines 23–90). Advanced requires existing Components, Customer Area UPI and action.type await; its action-handling link uses a #handle-the-redirect anchor, which does not establish identical await and redirect handling (raw line 170). paymentMethod.appId is required only for UPI Intent's upi_intent type, identifying a TPAP, with gpay in a TEST v72 example (raw lines 163–204, 275–305). Q2. Does the simulator redirect or QR wording prove an Android payment outcome or support Collect/AutoPay?
A2. No. The TEST checklist describes an Intent simulator redirect and explicitly says “UPI QR (on web)”, then instructs validation through webhook/Customer Area; it reports no observed result. It asks the tester to select an outcome but lists eventCode AUTHORISED without conditioning that code on the selection; the page does not guarantee it for every outcome or specify alternatives (raw lines 152–159, 318–325). This child page gives no Collect-deprecation or AutoPay mandate flow; those require separate source authority (raw lines 15–327).
