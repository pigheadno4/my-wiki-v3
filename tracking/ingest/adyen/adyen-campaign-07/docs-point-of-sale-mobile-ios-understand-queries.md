# C07 iOS Mobile understand — fixed retrieval checks

1. **Q: How does an iOS Mobile SDK POS transaction establish and use a communication session?**
   **A:** The merchant POS app calls its backend; that backend makes a server-to-server POST `/auth/certificate` request and returns session data. The SDK uses the data to authenticate with Adyen and checks for expiry/renewal. For a transaction, the app optionally warms up, creates or receives a Terminal API JSON request, passes it to the SDK, and gets the Terminal API response after the SDK checks its session and starts the mobile-device transaction. The page links TerminalAPIKit for iOS as a request-building aid. Evidence: `raw/adyen/docs/point-of-sale/mobile-ios/understand/2026-09-15.md:19-48`; canonical URL: https://docs.adyen.com/point-of-sale/mobile-ios/understand. This concept snapshot does not prove an authenticated live session or completed payment.

2. **Q: What iOS NYC1 reader PIN, connection and firmware distinctions does the page state?**
   **A:** Both Tap to Pay and card-reader solutions can make PIN transactions, and the on-device PIN pad may appear in a random position for security. For US card-reader PIN, an NYC1 with PIN support requires Mobile SDK 3.8.0+; `connectedDevice.type=nyc1` supports PIN while `nyc1SCR` does not. The reader path has Bluetooth pairing, details and firmware-update UI; custom UI must check for and handle reader updates. In the iOS Mobile SDK path, a mobile device can connect by USB-C **to an NYC1 dock with the reader seated**, or the dock can merely charge a reader while the mobile device still uses Bluetooth. The separate NYC1 manual's Android USB-host condition applies to a **direct cable from mobile device to reader**. Custom UI must also handle dock firmware updates. The page's NYC1-SCR 2026-02-01 order cutoff is dated documentation, not current ordering proof.
