# C07 terminal connection tests — fixed query answers

1. **Which diagnostic checks Adyen platform reachability, and can a red Receiving data cross still coexist with a successful first connection?** **PSP connection** tests the terminal-to-Adyen platform path through DNS, network connection, TLS negotiation, writing and receiving. The guide permits the red **Receiving data** result to be ignored **only** when the terminal was connected for the first time and the overall PSP test result is **No Error**; otherwise it points to possible inbound router/firewall trouble and says to contact the merchant's network or IT team. A connection result is not evidence that a payment authorized or settled. Evidence: `raw/adyen/docs/point-of-sale/pos-troubleshooting/connection-tests/2026-09-15.md`, `## PSP connection test` lines 66–80; proposed `[[source-adyen-docs-point-of-sale-pos-troubleshooting-connection-tests]]`.

2. **Should a local Terminal API integration treat a failed WebSocket result as its POS-to-terminal failure, and where does the local TLS detail apply?** No. The dated guide says integrated terminals using **local communications** may ignore WebSocket test results because that part of the Terminal API test checks the **cloud** connection. The Terminal API diagnostic's TLS version, cipher and URL fields describe the local POS-to-terminal link and are inapplicable to cloud-integrated and standalone terminals. The separate Endpoints test checks four terminal URLs for sync, configuration, PAL requests and firmware. A passing diagnostic only verifies its tested path at that moment. Evidence: same raw, `## Terminal API test` lines 82–92, `## Local communications TLS test` lines 94–104 and `## Endpoints test` lines 106–115; proposed `[[source-adyen-docs-point-of-sale-pos-troubleshooting-connection-tests]]`.
