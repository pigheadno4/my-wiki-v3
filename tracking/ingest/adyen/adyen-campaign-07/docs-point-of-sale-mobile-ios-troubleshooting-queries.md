# C07 iOS Mobile POS troubleshooting — fixed retrieval checks

1. **Q: Does restoring an iPhone device passcode recover earlier offline Store and Forward payments after a passcode error?**
   **A:** The captured guide's device message `PASSCODE_NOT_ENABLED` says the transaction was canceled after the passcode was removed and that **all offline Store and Forward transactions previously performed with the original passcode were lost and cannot be recovered**. The user must set a device passcode to resolve the condition before further offline transactions. Separately, the Swift `AdyenPOSError.passcodeDisabled` case says offline data saved with the previous passcode **may** be lost. Do not turn that weaker SDK wording into proof of recovery or merge the two error surfaces. 2. **Q: How should an iOS Mobile SDK integration distinguish transaction, session, Tap to Pay, and NYC1 failures before retrying?**
   **A:** `malformedTransactionRequest` calls for correcting the Terminal API request; `transactionInProgress` says to wait for the current transaction to finish before another begins. `tooManyRequests` is about excessive **session-related** calls: wait, add backoff, and review session establishment. `tapToPayNotSupported` points to device/iOS requirements, while `tapToPayNotAllowed` points to the Apple entitlement. NYC1-specific cases include reader connection/pairing, battery access, invalid reader firmware, and firmware/dock failures. Device-attestation messages require resolving the device condition; `SYSTEM_CHANGE` has an inconsistent crossed-out internet indicator even though its action requires a network check after restart/date changes. These error remedies do not make a payment retry idempotent or prove authorization, refund outcome, or settlement.
