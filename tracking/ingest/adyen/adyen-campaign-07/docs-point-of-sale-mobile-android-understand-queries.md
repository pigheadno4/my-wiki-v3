# C07 Android Mobile solution comparison — fixed retrieval checks

1. **Q: How do the embedded Mobile SDK and separate Payments app differ for Android Tap to Pay and NYC1 card-reader acceptance?**
   **A:** The merchant POS app can embed the Mobile SDK for Tap to Pay, reader payments, or both; the separate Adyen Payments app contains the SDK and supports Tap to Pay only. Both shapes require Terminal API integration and frontend/backend work. The SDK route passes Terminal API messages directly to the embedded SDK after obtaining a communication session; the Payments app route sends an encrypted, Base64URL-encoded request by App Link and receives the encoded response through a return URL. Evidence: `raw/adyen/docs/point-of-sale/mobile-android/understand/2026-09-15.md:19-30,46-82`; canonical URL: https://docs.adyen.com/point-of-sale/mobile-android/understand. This is a 2026-09-15 snapshot, not proof of current eligibility or payment outcome.

2. **Q: Which PIN, reader UI/firmware and kiosk limits would an Android Mobile POS design need to retain?**
   **A:** The source describes randomized on-screen PIN-pad placement. In the US, NYC1 reader PIN requires a PIN-capable unit and Mobile SDK 2.4.0 or later; `connectedDevice.model` returns SCRP for PIN support and SCR without it. The SDK offers built-in reader/dock management UI, while custom UI must handle firmware update flows. Kiosk mode for Tap to Pay must not be used unattended under the cited PCI MPoC requirement.
