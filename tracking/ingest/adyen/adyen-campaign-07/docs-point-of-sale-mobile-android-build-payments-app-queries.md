# C07 Android Payments app — fixed retrieval checks

1. **Q: How does the Android Payments app route start a payment, and is it the POS Mobile SDK or a direct Terminal API endpoint call?**
   **A:** It is a separate installed Payments app route. A merchant POS app integrated with Terminal API uses Android App Links: after boarding, it sets `POIID` to the Payments app `installationId`, encrypts and Base64URL-encodes the Terminal API request, and calls the `/nexo` App Link. The guide explicitly says not to call a transaction endpoint directly for this route. 2. **Q: What happens if the boarded app changes merchant/store or fails authenticity verification, and does this snapshot prove live eligibility?**
   **A:** Reboarding immediately removes the prior merchant/store association, so payments on that app-device combination stop until reboarding finishes; a reboarding error requires starting the flow again. Failed app-instance verification automatically revokes the instance and requires boarding again. The dated guide also names Support enablement, app-role credentials, NFC COTS hardware and separate regional support limits, so it is not proof of current merchant/device eligibility or a successful payment.
