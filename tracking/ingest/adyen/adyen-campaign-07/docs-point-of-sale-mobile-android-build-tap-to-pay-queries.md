# C07 Tap to Pay on Android — fixed retrieval checks

1. **Q: What device and software path does this build guide use, and what OS and environment limits does it state?**
   **A:** It covers an Android POS app integrated with Terminal API, using Adyen's Mobile SDK and the integrated NFC reader of a commercial Android device that is not a payment terminal. The app sets `minSdkVersion` 26+, but the SDK initializes only on Android 12+ devices. The documented `-debug` artifact accesses test and `-release` accesses live; the page routes country, payment-method, functionality and device support to separate requirements/support pages. 2. **Q: Which system creates the secure session, how do facilitator and store fields differ, and what recovery/security boundaries matter?**
   **A:** The merchant backend calls `/auth/certificate` using a session credential distinct from the SDK-download key, with `merchantAccount` and SDK `setupToken`, then returns `sdkData` to the POS app. A non-facilitator includes `store` unless merchant accounts act as stores; a registered payment facilitator instead supplies `subMerchantData` in the session request and must not place it in Terminal API requests. A changed store/merchant assignment calls for clearing the device session to avoid attributing a later transaction to the old store. The guide recommends diagnosis for transaction-blocking security threats and SDK expiry, and status checks when a payment response is missing.
