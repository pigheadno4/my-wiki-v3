# Retrieval checks — docs-marketplaces-surcharge

## Q1 — What is this surcharge flow and what must a marketplace have before using it?

The 2026-09-15-captured page describes a Marketplace-path pilot allowing platform users to pass payment-acceptance costs to customers, with user agreements on fee charging and default booking to the platform liable balance account unless a `Surcharge` split sends the amount to a user's balance account (raw lines 15–21). It requires Adyen for Platforms, API-only online cards with raw or encrypted data, a Checkout webservice role/API key and Standard-webhook reception; the pilot may have restrictions (lines 23–35). The platform uses server `/cardDetails` information, makes its own eligibility/amount decision, discloses the surcharge, then submits `/payments` with `amount.value` including the surcharge (lines 45–53, 290–332). ## Q2 — Which limits and evidence boundaries constrain surcharge booking and reconciliation?

The feature lacks automated global compliance enforcement, with dated EEA consumer-card and US debit examples, and the platform must validate applicable rules (raw lines 37–43). The page prohibits adding surcharge to authorization adjustments or overcaptures or exceeding the amount displayed at purchase (lines 32–35). The split table labels `amount.currency` required (line 341), but example surcharge split amounts omit it (lines 394–407), so the example is not a settled API contract. An example `Authorised` payment response (1092–1112) and `received`/`authorised` transfer events (1142–1214) do not establish captured credit; the page shows later captured and booked events (1296–1441), all illustrative test payloads, not payout or bank receipt.
