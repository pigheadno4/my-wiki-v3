# Q1 — purpose and prerequisites

**Question:** What does this on-demand internal-transfer guide initiate, and which access/account gates apply?

**Answer:** The introduction names sending funds and internal direct debit between Marketplace balance accounts, but the concrete Customer Area and Transfers API instructions/examples show a **push** from source to counterparty balance account, not a demonstrated pull/direct-debit procedure (raw lines 17, 44–70, 90–125; the reference field mentions push/pull at line 102). This is not an external bank payout. It lists an Adyen for Platforms integration, TransferService Webservice Initiate API role, two Customer Area roles for the UI route, Transfer webhook handling, and source-balance-account enablement by Adyen Support (lines 21–38). Only when source and destination belong to different account holders does the guide require sender `sendToBalanceAccount` and receiver `receiveFromBalanceAccount` capability checks (lines 35–37). # Q2 — review, future execution and funds boundary

**Question:** Does a 2XX or received response prove movement, and what happens to a reviewed future-date request?

**Answer:** No. The illustrative API response is `received/pending`; the page requires transfer webhooks to confirm booked and describes outgoing and incoming series for the two balance accounts (raw lines 419–463, 909–915). Optional `review.numberOfApprovalsRequired=1` adds one team approval before processing (lines 467–475, 830–836). A future `executionDate.date` must be within 30 days and leaves the request received/pending until execution; the 00:00–03:00 window checks source funds and approval, then Adyen attempts execution **once**. Errors such as insufficient funds end failed with a webhook; cancellation is described before the date (lines 840–859, 890–892). The narrative's configured Balance Platform timezone and field-table Europe/Amsterdam default need checking for an actual schedule (lines 844, 859).
