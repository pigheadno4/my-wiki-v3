Q1. How does a marketplace allocate a chargeback, and which configuration takes precedence?

The default disputed amount debits the marketplace liable balance account; a successful defense/customer repayment credits a reversal, while an issuer-rejected defense can cause another debit (raw lines 19–35). `platformChargebackLogic` can deduct from the liable account, one specified user balance account, or according to original payment/session split ratio; `costAllocationAccount` selects fee destination separately (lines 37–66). Support can set a balance-platform default, overridden by per-payment logic, and capture-request logic overrides the payment request (lines 45–50). Configure in `/payments`, `/sessions` or a capture request and use `CHARGEBACK` notification for occurrence (lines 52–68). Q2. Why does a successful request or an early webhook fail to prove the desired account was debited, and what conflicts are in the examples?

Checkout validates split format, not target-account existence/status; an absent balance account or closed-holder target sends the full transaction and fees to the liable account despite apparent request success (raw lines 70–74). Track per-split transfer and transaction webhooks: `received` then `authorised` precede example `chargeback` transfer status with transaction ID and `booked` transaction (lines 2189–2207, 2222–2522). The original-ratio example calls the dispute USD 88 but parentheticals EUR 88 (lines 1481–1493); the tracking prose says `event` while payloads use `events` (lines 2200–2203, 2250–2265), and fee/commission sample account IDs and status labels conflict (lines 2691–2837, 3006–3152). The examples are not proof of live chargeback outcome, booking or bank receipt.
