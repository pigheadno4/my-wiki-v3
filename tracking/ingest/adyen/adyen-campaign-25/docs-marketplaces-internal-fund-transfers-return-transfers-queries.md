# Q1 — Purpose, prerequisites and request

This route returns mistaken internal balance-account funds to the original sender as a modification, only if the original transfer was a push (raw lines 17–21). Webhook receipt/subscription, Support enablement on the account returning funds, Transfers API access and **TransferService Webservice Initiate** role are required; when holders differ, the sending-back holder needs `sendToBalanceAccount` and original sender/return-recipient holder `receiveFromBalanceAccount` (raw lines 23–37). POST `/transfers/{transferId}/returns` uses the original incoming transfer ID and the request amount/currency must match the original (raw lines 39–50). # Q2 — Identity and outcome boundary

The response `id` is the return request; `transferId` is the original incoming transfer in the URL (raw lines 293–307). The sample is `authorised`, which is not booked movement, and the guide says a `Declined` status **can** mean the URL used a wrong transfer ID rather than asserting a unique cause (raw lines 293–308). Follow the status/failure through internal-transfer webhooks or Customer Area (raw lines 310–314), and use [[source-adyen-docs-marketplaces-internal-fund-transfers-internal-transfer-webhooks]] for nested return modifications and the eventual two account legs. This is internal account-to-account movement, not a bank payout.
