# C25 Q1–Q2: Marketplace multi pay-in refunds

**Q1. What does this guide let a marketplace initiate, and what must be in place and identified first?**
From [[index]] → [[adyen-index]] → [[adyen-platforms]] → [[source-adyen-docs-marketplaces-multi-pay-in-refunds]] → [[raw/adyen/docs/marketplaces/multi-pay-in/refunds/2026-09-15]], the page covers a Checkout API refund for a third-party-processed payment already settled in a user's balance account. The marketplace initiates deductions from user/platform balances and a return to its multi pay-in account; the pay-in partner must have a separate process to send the refund to the customer before the Adyen step (raw lines 17-23). Use the original payment PSP reference from the initial API response or authorization/transfer webhooks in POST `/payments/{paymentPspReference}/refunds`, with required `amount` and `merchantAccount`; value is no more than the captured amount and currency matches authorization (raw lines 27-39). The `REFUND` webhook supplies an asynchronous request outcome (raw lines 23, 779).

**Q2. What split, fallback and outcome boundaries matter when refunding and reconciling?**
At the same route, explicit `splits` allocate deductions to specified user/platform balance accounts; the guide strongly recommends them for partial refunds (raw lines 39, 43-60). Its field table marks `account`, `amount.value` and `type` Required per item and `reference` conditionally required for `BalanceAccount`, but the TEST curl `Commission` item omits `account` while the `BalanceAccount` item includes it. That table/example conflict is unresolved; the sample does not establish a validated field schema (raw lines 45-58, 67-96). Omitting splits to inherit the **authorization**, not capture, ratio is described for a full refund matching the original payment amount when authorization had splits; with no authorization splits, the whole refund debits the marketplace liable account (raw lines 501-511). The API checks split format but not account validity: a nonexistent account or closed holder sends the full transaction and fees to the liable account, and remediation is a separate internal transfer (raw lines 781-785). Distinguish the `REFUND` webhook from outgoing user/liable deduction transfer and transaction events and the incoming multi pay-in credit; intermediate `received`/`authorised` states are not booked funds, and none proves the partner sent money to the customer (raw lines 787-800, 969-971, 1412-1424, 1666-1702). TEST examples are not a reconciled ledger: the request shows USD 8,000 minor units while later example webhooks show USD 39,600/40,000, and the booked-transfer section repeats a received-status description (raw lines 67-96, 833-835, 1444-1446, 1569-1572).
