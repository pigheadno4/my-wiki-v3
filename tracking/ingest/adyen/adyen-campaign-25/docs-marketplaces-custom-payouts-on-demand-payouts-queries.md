Q1. What does on-demand payout do, and what prerequisites and identities apply?
A. It triggers an off-schedule bank payout from a user's source balance account to that user's verified transfer instrument using Customer Area or Transfers API POST `/transfers` (raw lines 15–27, 46–48, 99–112). It requires Adyen for Platforms; route-specific API/Customer Area roles; webhook reception; allowed `sendToTransferInstrument` capability verified per instrument from LEM API v3; and Support enablement of transfers plus default description (lines 29–44). The destination instrument must be linked to the account holder legal entity (line 108). Q2. What status, timing and retry boundaries prevent interpreting a request as received bank funds?
A. HTTP 2XX returns a transfer request ID (raw line 436), and route-priority fallback tries another available priority within that request (lines 440–446); neither proves bank receipt. Optional one-person review needs approval (lines 542–550, 921). Future-dated requests remain `received/pending`, check funds and approval on execution day, then are attempted once; failures end `failed` with webhook, and cancellation is available before execution (lines 925–978). Track transfer/transaction webhooks for status and balance-account debit (lines 980–1003). A prior bank return can block later payouts with `1063_101`; final return reasons must not be retried, while recommended retry codes and updated bank details support a later new request (lines 1011–1039).
