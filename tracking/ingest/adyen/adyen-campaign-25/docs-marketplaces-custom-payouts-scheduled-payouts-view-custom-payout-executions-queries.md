# Q1 — Purpose and prerequisites

A custom payout schedule's payout attempt is an execution, visible in Customer Area or by Configuration API (raw lines 17–19). API reads require **Bank Scheduled Payouts Merchant Role**, Customer Area reads require **Balance platform base role** and **Configure scheduled payouts**, and Configuration plus Transfer webhook subscriptions cover execution and later funds movement (raw lines 21–31). Customer Area Events show next/past executions; Configuration API GET `/balanceAccounts/{balanceAccountId}/sweeps/{id}/executions` returns `sweepExecutions` with result and details (raw lines 33–65). # Q2 — Failure, contradictory examples and bank boundary

UI `Sent` means created/sent, `Not sent` conditions unmet, and `Failed` an error; the page says root causes must be resolved to stop continuing failures (raw lines 49–57). Execution webhooks carry `succeeded` with transfer ID or `skipped`/`failed` with reason; final failures can disable the schedule and expose `sweepConfigurationDisabled` (raw lines 118–149, 174–213). The API example's `sweepDisabled: "true"` conflicts with webhook `sweepConfigurationDisabled: true`; `counterpartyAccountBlocked` in table/API conflicts with webhook `counterpartyBlocked` (raw lines 103–106, 161, 228–230). A successful execution only triggers a transfer; use Transfer webhooks for authorized/captured/returned states, and do not infer beneficiary bank receipt (raw lines 238–242).
