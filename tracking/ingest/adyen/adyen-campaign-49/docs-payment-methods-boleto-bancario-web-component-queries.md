# Fixed queries — Boleto Bancário Web Component

## Q1 — purpose, scope and limits

**Query:** What does the captured Boleto Bancário Web Component guide establish, and what does voucher presentation not establish?

**Expected answer:** The page at `https://docs.adyen.com/payment-methods/boleto-bancario/web-component` is a 2026-09-15-captured guide for adding Boleto to existing Web Components integrations through Sessions or Advanced flow, with request fields, Component setup, voucher response and test reconciliation. It does not prove a voucher was paid, current merchant enablement, or a successful live payment. ## Q2 — flow requirements, due dates, voucher and finality

**Query:** In the captured Web Component guide, how do Sessions and Advanced Boleto requirements and due-date fields differ, and how is a paid test Boleto distinguished from a presented voucher?

**Expected answer:** Sessions requires an existing Sessions Web Components integration, Checkout API v68 or later, and Customer Area addition. Its `/sessions` fields include required name, billing address, CPF/CNPJ and optional `deliverAt` UTC due date; the page states a five-day default and next-working-day allowance for weekend/national holiday (pinned `raw/adyen/docs/payment-methods/boleto-bancario/web-component/2026-09-15.md`, `## Sessions flow Component` lines 25–50). Advanced requires an existing Advanced integration, Customer Area addition and voucher action handling; its action-handling link at raw line 158 has a #handle-the-redirect anchor despite action.type voucher, so do not infer redirect behavior; its `/payments` fields include `paymentMethod.type: boletobancario`, the same personal/address identifiers and optional **`deliveryDate`** (lines 151–203). The Advanced response `PresentToShopper` carries voucher PDF/expiry/barcode/amount data, so it is not paid confirmation (lines 214–226). In test, a pending offer is manually promoted to sale; pending/expired are under Offers and paid under Payment list, and the page calls for reconciliation tests (lines 131–149, 228–246). Live acceptance requires a request in live Customer Area (lines 149, 246). The Sessions configuration example at lines 95–113 appears syntactically incomplete and should not be treated as copy-ready.
