## Q1 — What is this source for, and what does it not prove?

This is a Bancontact **card** iOS Components add-on, for an existing Sessions or Advanced flow with the method added in Customer Area (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:15-43). It says Bancontact card has no CVC except possible co-badged display, requires 3D Secure, and has no separate captures (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:19-25). It is integration documentation, not proof of current account eligibility, completed 3DS, or live payment success. The separate live notes concern Customer Area method addition and a live Client Key (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:505-540).

## Q2 — What component and recurring qualifications matter?

The base API reference says no extra Bancontact-card fields; `/sessions` is the default with Components v5.0.0+ and `/payments` is for additional use cases (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:45-50). v5+ Swift snippets select `bcmc` and construct `InstantPaymentComponent`, delegating to `session` or `self`; a v4.x.x example uses generic `Component` (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:52-107). The v5+ samples do not show the card-entry fields described in prose, so implementation details need the linked iOS guide. WIP recurring requires signup/eligibility and amount limits, recommends shopper permission, and needs Support setup to test; token creation uses `storePaymentMethod` and `shopperReference`, with a token-created webhook after settlement and later `ContAuth` payments using the stored method ID (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:109-166). The co-badged Visa test card can route to either scheme depending on setup (raw/adyen/docs/payment-methods/bancontact/bancontact-card/ios-component/2026-09-15.md:505-515).
