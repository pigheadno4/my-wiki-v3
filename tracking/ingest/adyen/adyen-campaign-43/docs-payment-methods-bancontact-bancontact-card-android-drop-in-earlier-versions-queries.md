## Q1 — What does this source cover, and what should not be inferred?

It is the **Bancontact card Android Drop-in v4.x.x earlier-versions** add-on, requiring an existing Advanced-flow Android Drop-in integration and Bancontact card added in Customer Area (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:15-34). Its BE/EUR `/paymentMethods` values are method-display conditions, not proof that a merchant is enabled or a payment works; the page is version-scoped and its test/live section is not a complete current live-key procedure (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:36-41,870-905). Bancontact card here has no CVC except possible co-badged field, requires 3D Secure, and does not support separate captures (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:19-25).

## Q2 — What payment transition and qualifications matter?

The Requirements table specifies Advanced-flow Android Drop-in, while the opening, optional-config and See also links point to Sessions guides; those links are not verified Advanced routes (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:25,33,45,909). Drop-in returns `paymentComponentData`; the merchant server is instructed to send `/payments` with its method, required `channel: Android` and Drop-in return URL, then passes the redirect action to the app. Every illustrated `/payments` request omits `channel`, so the examples are incomplete templates (raw lines 69–72,75–401). After app return, send `actionComponentData.details` to `/payments/details`; use its result code for shopper presentation and expect an asynchronous webhook outcome (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:63-74,403-472). The opening says “website” return, but the redirect section says app; the `/payments` curl key contains annotation markup (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:25-27,87-95,426-445). WIP recurring requires signup/eligibility and amount limits, consent is strongly recommended, and token creation/settlement webhook precedes future token payments; test recurring needs Support configuration (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:474-531). The optional Kotlin snippet claims to require cardholder name but shows no such setting (raw/adyen/docs/payment-methods/bancontact/bancontact-card/android-drop-in/earlier-versions/2026-09-15.md:43-61).
