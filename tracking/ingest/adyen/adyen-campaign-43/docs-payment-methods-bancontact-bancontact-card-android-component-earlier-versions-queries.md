## Q2. What are the central capability, prerequisites and warnings?

Bancontact card has no CVC except that co-badged cards can still show a CVC field; 3DS is mandatory and separate captures unsupported (`:19-27`). The v4 flow requests BE/EUR `/paymentMethods`, selects `bcmc` and uses `BcmcComponent` with a client key (`:36-90`). Send Component data to the merchant server for `/payments` only when state is valid **and the shopper proceeds to pay**; the observer sample instead calls `sendPayment` as soon as `isValid` is true without an explicit pay-action guard, so it is not a copy-ready submit handler (`:91-102`). A redirect action handles 3DS; after return, send Redirect Component details to `/payments/details` and present its result, while also receiving asynchronous webhook outcome (`:442-509`). Samples conflict with `bcmc` selection (`scheme` type), include a hint-wrapped paymentMethod key, and show web `returnUrl`; verify exact Android handling before implementation (`:102-132`). WIP recurring requires signup, eligibility and amount limits, with initial SCA/consent, a token-created webhook **after settlement**, and later stored-ID/ContAuth payments (`:511-568`). Co-badged TEST routing can go to Bancontact or Visa depending on setup; live setup says add Bancontact in Customer Area but uses **Client Encryption Public Key** wording after earlier **client key** wording (`:57-68,907-942`).
