## Q1 — What does this source cover, and what cannot be inferred?

It is Bancontact **mobile** in existing **iOS Drop-in**, not Bancontact card. Phone shoppers switch to the Bancontact app with QR fallback on failure; tablet shoppers see QR and an app-switch button (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:15-24). The stated requirements are an iOS Drop-in integration, adding Bancontact in test Customer Area, and enabling 3DS2 Additional Fields to receive `bcmcmobile.urlIntent` (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:26-36). These statements do not prove app-switch success, shopper eligibility, or a live payment.

## Q2 — What API, recurring and testing boundaries matter?

The base API reference says no additional Bancontact fields, `/sessions` is default with Drop-in v5.0.0+, `/payments` covers an additional use case, and neither v5+ nor v4.x.x needs Bancontact-specific Drop-in configuration (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:38-53). WIP recurring requires signup/eligibility and amount limits; consent is strongly recommended. Token creation uses `storePaymentMethod` and `shopperReference`, a token-created webhook arrives after settlement, and later `/payments` use the stored method ID, `ContAuth` and a recurring model (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:55-112). The sample identifies the mobile method as `bcmc_mobile` (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:114-135). The page says Bancontact mobile has no test platform and recommends a live EUR 0.01 penny test, despite test Customer Area and WIP test-setup references; these are not evidence of an actual live test (raw/adyen/docs/payment-methods/bancontact/bancontact-mobile/ios-drop-in/2026-09-15.md:31-36,83,451-455).
