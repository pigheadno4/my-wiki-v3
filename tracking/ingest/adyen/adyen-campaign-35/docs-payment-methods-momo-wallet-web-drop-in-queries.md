Q1. What is this MoMo Web Drop-in guide for, and what cannot be inferred?
A1. It adds MoMo to an existing Web Drop-in integration, distinguishing Sessions prerequisites (Checkout API v68+, redirect handling and Customer Area setup) from Advanced prerequisites (existing Advanced Drop-in, redirect handling and Customer Area setup) (raw lines 19–36, 307–317). It does not record a successful payment, settled token or live merchant approval; the TEST status list and separate live request are instructions (raw lines 294–305, 575–586). Q2. How do ordinary requests differ from recurring token payments, and what warnings matter?
A2. Ordinary Sessions creation and Advanced /payments sections say no extra MoMo-specific parameters, but the recurring route separately requires storePaymentMethod and shopperReference for token creation, a recurring.token.created webhook only after settlement, then storedPaymentMethodId, ContAuth and a fixed/non-fixed recurring model for later payments (raw lines 40–42, 60–93, 333–335, 341–374). The Advanced base link has an encoded platform placeholder, and Java examples use RecurringDetailReference where prose says storedPaymentMethodId; snippets are TEST examples, not outcome proof (raw lines 136–147, 315–316, 417–428).
