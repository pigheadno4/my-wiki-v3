Q1. What is the DANA Android Drop-in page for, and what cannot be inferred?
A1. It adds DANA to an existing Android Drop-in integration: Sessions requires Checkout API v68+ and Customer Area setup, while Advanced requires an existing Advanced Drop-in, redirect handling and Customer Area setup (raw lines 25–46, 298–318). It records no successful payment, settled token, live enablement or capture/settlement result; examples and status-check directions are not execution evidence (raw lines 87–296, 359–566). Q2. How do ordinary requests and recurring token payments differ, and what warnings apply?
A2. The base Sessions and Advanced sections say no extra DANA-specific request or configuration parameters, but recurring token creation separately requires storePaymentMethod and shopperReference; token webhook receipt is conditioned on the initial payment settling, and later /payments requests use storedPaymentMethodId, ContAuth and Subscription or UnscheduledCardOnFile (raw lines 38–85, 310–357). Sessions does not separately list redirect handling while Advanced does, and TEST directions say “successful DANA live payments” beside test-status lookup and a separate live request (raw lines 29–34, 290–296, 304–306, 558–566).
