# Fixed retrieval checks — Adyen POS offline payments

Catalog route pending coordinator promotion: `wiki/index.md` → `wiki/adyen-index.md` → `wiki/concepts/adyen-terminal-api.md` → proposed `wiki/sources/adyen/source-adyen-docs-point-of-sale-offline-payment.md` → `raw/adyen/docs/point-of-sale/offline-payment/2026-09-15.md`.

1. **What is this page for, and what should it not be used to infer?** The Adyen Docs guide explains configured POS payments during temporary loss of terminal or Mobile SDK internet access: offline EMV and store and forward, including setup, recognition, reconciliation, retries, refunds, and tests (raw lines 23–27). It does not prove a merchant has enabled the feature, that a given terminal/card/scheme/region qualifies, or that an offline approval became issuer authorization, capture, or settlement. The page says the merchant bears the failed-capture, chargeback, and dispute risk (lines 44–50), and offline response data lacks a PSP reference and issuer authorization fields (lines 159–166). Website evidence remains distinct from versioned GitHub examples in the existing concept.

2. **What central capability, prerequisites, and warnings should a reader retrieve?** Offline payments require Support enablement and per-mode amount limits (raw lines 110–150). The stated routes are local Terminal API, printer-equipped standalone terminals, and specified Mobile SDK solutions; cloud requests work offline only after the terminal has received the request, Mobile lacks offline EMV/refunds, and MSR is excluded (lines 29–42). Offline EMV depends on card and issuer configuration; store and forward approves without verification and may later be declined (lines 52–67). On loss of internet, the device checks mode/card/scheme/amount/count conditions and later submits stored payments to Adyen (lines 69–92). Mobile store and forward additionally needs prior security attestation, has a 24-hour secure window, fails during an Adyen platform outage, and has stored-data loss/restart warnings (lines 94–108). The initial response has only the tender reference, so reconcile against later webhooks or tender reference and handle issuer declines (lines 159–200, 271–278). Offline refunds are unreferenced offline-EMV only and need a configured maximum; see lines 296–326 for post-reconnection routes.
