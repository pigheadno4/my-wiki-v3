## Query 1: What is this Adyen POS pre-authorization page for, and what should it not be used to infer?

Answer: It is Adyen's unversioned guide for an in-person merchant Terminal API pre-authorization, subsequent authorization adjustment through Adyen's backend, and manual capture. It is not the online card/Klarna procedure or proof of present scheme support, account eligibility, issuer approval, or a successful adjustment/capture. ## Query 2: What is the central capability, and what prerequisites and warnings govern it?

Answer: The merchant starts a terminal pre-authorization by specifying `authorisationType=PreAuth` per payment, or by using a PreAuth merchant-account default configured by Adyen Support; with that default the field need not be sent (raw lines 77-80, 102-104, 128-152). The merchant can then submit backend `/amountUpdates` for a new total authorized amount while unexpired, and manually captures after the final adjustment. The terminal does not receive adjustment requests (lines 253-292, 842-846). The setup requires Terminal API, appropriate API credentials, payment-method setup, manual capture and adjustment/capture webhooks (lines 21-37, 96-106). Asynchronous results require webhook confirmation; synchronous adjustment needs account enablement and the latest blob, with permanent fallback if omitted (lines 82-100, 573-610, 798-830). Capture is asynchronous (lines 842-904). Method, MCC, issuer, scheme and validity rules constrain eligibility and timing; the Visa MCC 5542 rows conflict within this snapshot, and China UnionPay's adjustment does not extend validity (lines 913-1033). The same index → concept → source → raw route above applies; the provider catalog entry is pending coordinator promotion.
