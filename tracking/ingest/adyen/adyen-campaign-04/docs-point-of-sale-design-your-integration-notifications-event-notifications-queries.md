## Query 1: What is an Adyen POS event notification for, and what should not be inferred from it?

Answer: It is a terminal-generated `EventNotification` used by the merchant POS app to show staff terminal state or availability, such as shutdown, maintenance, network state or a rejected request (raw lines 15-23, 234-249). It is distinct from the payment `SaleToPOIResponse` that may reach the same endpoint for asynchronous cloud requests (lines 504-578), and from transaction-progress `DisplayRequest` notifications in the already-ingested display-notifications source. The raw's Next steps separately navigates to platform-generated webhooks; this page does not prove their behavior. An event notification itself does not establish a completed payment result. ## Query 2: How does the merchant configure and handle the event endpoint, including async responses?

Answer: Configure a JSON receiver as a public or local Event URL in Customer Area, or configure `nexo.eventUrls.eventPublicUrls/eventLocalUrls` through Management API at company, merchant, store or terminal scope; the API path needs the Terminal Advanced settings read/write role, and removal requires checking higher-level inheritance (raw lines 25-56, 58-98). The dated requirements list test HTTP 80/8080/8888 or HTTPS 443/8443/8843 with TLSv1.2, and live HTTPS 443/8443/8843 with TLSv1.2 (lines 29-33, 68-72). On receipt, store, acknowledge with successful HTTP status such as 202, then apply business logic (lines 223-232). Asynchronous cloud Terminal API responses are delivered to the configured event endpoint as `SaleToPOIResponse` messages, separate from terminal `EventNotification` messages (lines 21-23, 504-578).
