# Fixed retrieval checks — Adyen POS card acquisition

Catalog route pending coordinator promotion: `wiki/index.md` → `wiki/adyen-index.md` → `wiki/concepts/adyen-terminal-api.md` → proposed `wiki/sources/adyen/source-adyen-docs-point-of-sale-card-acquisition.md` → `raw/adyen/docs/point-of-sale/card-acquisition/2026-09-15.md`.

1. **What does card acquisition do, and what does it not prove about payment?** A Terminal API POS can obtain card/shopper identifiers before a payment or outside one. It is a distinct terminal step; continuing requires a separate Payment request with an acquisition reference, and identifier collection alone is not documented as authorization or capture. The card alias identifies a shopper but is not a payment token. Locators: raw lines 19–28, 221–229, and 270–297. The concept routes to this website guide; its GitHub Postman examples have separate provenance.

2. **How does the flow continue or end, and what constraints matter?** The POS may make a payment whose `PaymentData.CardAcquisitionReference` uses the acquisition response's `POIData.POITransactionID`, or cancel a completed acquisition with `EnableServiceRequest`/`AbortTransaction`, which discards data and makes a later reference invalid. An in-progress acquisition uses `AbortRequest` and the terminal/response outcome must be checked. A contactless shopper may need a second tap when the acquisition has no amount or a different amount unless Support enables single tap. QR-code wallet and one-time numeric-code details are unavailable through acquisition. Locators: raw lines 33–68, 221–225, 270–297, 440–465, 572–638. The Java example at lines 373–377 appears to use the local payment transaction ID where the prose/table specify the acquisition response ID; verify before implementing.
