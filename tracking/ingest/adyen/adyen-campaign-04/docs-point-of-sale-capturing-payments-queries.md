# Fixed retrieval checks — Adyen POS capture

1. **What is this source for, and what must it not be inferred to prove?** It is Adyen's 2026-09-15 snapshot of an unversioned guide to capturing in-person Terminal API payments immediately, after a delay, or manually; it also explains Checkout API capture/cancel modifications after authorization. It does not prove current merchant or payment-method enablement, a specific live payment outcome, online-checkout behavior, or behavior of any particular GitHub library release. Locate `# Capture` and `## Requirements` in [[raw/adyen/docs/point-of-sale/capturing-payments/2026-09-15|pinned raw]].

2. **What is the central capability, with prerequisites and warnings, and how is it found?** For eligible in-person methods, the merchant can set account-level or per-payment delay/manual capture; the per-payment `SaleData.SaleToAcquirerData` setting wins. Manual capture uses an API key, Standard webhooks, the authorization PSP reference from the terminal payment response, and Checkout `POST /payments/{paymentPspReference}/captures`. Most wallets lack separate capture; Alipay and WeChat Pay capture immediately; multiple partial captures need Support enablement and single partial capture releases the remainder. The `received` response is asynchronous acknowledgment; `CAPTURE success=true` can still precede `CAPTURE_FAILED`. See raw `## Requirements`, `### Partial manual capture`, `## Delayed automatic capture`, `## Manual capture` > `### Capture a payment`, `## Webhooks for captures`, and `## Cancel an authorization`.
