The categories include metadata, shopper identifiers, statements, platform splits, tender options, and other data (lines 30–42). Its examples and an API Explorer link to `latest` do not pin a Checkout API version, establish current account capability, or prove a given tender option, tokenization, split, or statement was accepted. 2. **What central capability, prerequisites, and warnings should a reader retrieve?** Encode `SaleToAcquirerData` as Base64 JSON or form-encoded `&`-separated key-value pairs (raw lines 84–93). `AdditionalResponse` ordinarily uses the corresponding format, and defaults to key-value pairs when no request field is sent; Support can set a fixed response format (lines 93–105). Select the desired additional-response types in Customer Area first (lines 95–103). Metadata has 20-field and length limits, and settlement-report inclusion requires Support (lines 50–54). Shopper identifiers must be supplied and returned before they are stored for recognition/token use (lines 56–60); a dynamic shopper statement appears on the bank statement only with account configuration (lines 62–68). The two example payloads show format and field placement at lines 107–327 and 329–468, including `ProtocolVersion: 3.0` as a Terminal API example value, not a Checkout API version.
