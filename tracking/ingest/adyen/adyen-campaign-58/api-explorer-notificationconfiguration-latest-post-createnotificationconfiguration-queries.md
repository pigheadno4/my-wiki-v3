## Q1

> For `NotificationConfiguration/latest/post/createNotificationConfiguration`, what purpose and object identities does this captured page establish, and which required/conditional fields, permissions, prerequisites or consequential constraints govern use?

This creates a Classic platform notification subscription by event type, not by account holder; a marketplace can configure multiple endpoints for an event type (raw lines 5–10). `configurationDetails` is the required request object. Its `active`, `apiVersion`, `eventConfigs`, HMAC key, notification ID, delivery URL, username/password and SSL protocol fields are table-optional; supplied event config entries require `eventType` and `includeMode` (`INCLUDE` or `EXCLUDE`) (lines 14–29). No omitted-field defaults are specified. `apiVersion` should match the processed API version; `sslProtocol` permits `TLSv12` or `TLSv13` (lines 19, 29). Optional HMAC key is stated as 32 bytes/64 hex characters; omitting it omits `HmacSignature` and `Protocol` notification headers (line 24). The separate Classic HMAC guide's “32bit” wording conflicts with its own 64-character example, so do not generalize from that wording. 401/403 indicate authentication/permission failures without a named role (lines 97–120).
