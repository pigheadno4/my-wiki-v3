# api-explorer-postfmapi-latest-post-findterminal — fixed retrieval checks

- Q1: For `postfmapi/latest/post/findTerminal`, what purpose and object identities does this captured page establish, and which required/conditional fields, permissions, prerequisites or consequential constraints govern use?
  - Answer: Captured legacy POS Terminal Management API v1 TEST `POST /findTerminal` looks up the company account, merchant account or store assignment of a terminal identified by required `terminal` in model-serial format. A 200 response requires `companyAccount` and `terminal`; optional merchant/store fields locate assignment. `merchantInventory: true` denotes merchant inventory that cannot be boarded, while false means an in-store terminal ready to board or already boarded. 401 authentication and 403 insufficient permissions are listed. The page says this API was deprecated 2025-01-01 with support stopping 2025-04-01 and routes automation to Management API. See [[source-adyen-api-explorer-postfmapi-latest-post-findterminal]] (https://docs.adyen.com/api-explorer/postfmapi/latest/post/findTerminal); raw lines 5–41, 57–80.
- Q2: What do the response/errors establish, and which lifecycle, deletion, verification/approval, propagation, asynchronous financial outcome, version/environment or missing-evidence boundaries prevent broader inference?
  - Answer: A 200 lookup reports assignment state, not actual boarding completion, applied settings, device readiness or payment outcome. `merchantInventory: false` explicitly covers both ready-to-board and already-boarded. The page lists 400/401/403/422/500 errors and examples, with no deletion, propagation, KYC or financial-outcome contract. Its deprecated v1 TEST endpoint cannot establish current live availability or the newer Management API's request/response behavior. See [[source-adyen-api-explorer-postfmapi-latest-post-findterminal]] (https://docs.adyen.com/api-explorer/postfmapi/latest/post/findTerminal); raw lines 9–12, 29–41, 44–169.
