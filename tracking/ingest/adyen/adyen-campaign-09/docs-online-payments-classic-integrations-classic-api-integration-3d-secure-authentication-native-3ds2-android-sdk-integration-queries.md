# C09 worker retrieval probes — Android Classic 3DS2

Q1. What is this page for, and what scope must a reader avoid inferring?
Expected: It is a 2026-09-15 snapshot of Adyen's Android native 3DS2 guide for the legacy Classic Payment API `/authorise` integration. Adyen says it no longer accepts new Classic integrations and points to the newer Android native 3DS2 plus Checkout API migration. It is neither the current Checkout API flow nor evidence that authentication alone authorized a payment. Raw lines 19–33; canonical route https://docs.adyen.com/online-payments/classic-integrations/classic-api-integration/3d-secure-authentication/native-3ds2/android-sdk-integration.

Q2. What central capability, prerequisites, branches and warnings does the guide preserve?
Expected: The Android SDK fingerprints the device and presents a challenge while the merchant server calls Classic `/authorise` and `/authorise3ds2`. The initial request's `sdkVersion` must reflect the SDK actually in use: the page recommends `ThreeDS2Service.INSTANCE.getSDKVersion()` to determine it and explicitly warns not to hard-code it. Separately, native 3DS2 requires SDK 2.2.9+; `IdentifyShopper` starts fingerprinting, `ChallengeShopper` starts issuer interaction, `RedirectShopper` may route to 3DS1, and only an `Authorised` result indicates payment authorization in the described flow. For SDK 2.2.0+ pass response `messageVersion` to `createTransaction`; for SDK 2.2.12+ the optional OOB return URL should be an Android App Link that the app handles. Close each single-use transaction and clean up the service even on failure to avoid later transaction failures. Raw lines 29–46, 61–67, 89–119, 515–567, 952–999, 1315–1350; same canonical route.
