# C09 retrieval probes — Adyen Classic native 3DS2 iOS

Q1. What is this page for, and which integration and payment-outcome boundaries should a reader retain?
Expected: This is the 2026-09-15 snapshot of Adyen's legacy Classic API `/authorise` native iOS 3DS2 guide. Adyen no longer accepts new Classic integrations and recommends the newer native iOS route with Checkout API migration. The SDK obtains an encrypted device fingerprint and presents a challenge; merchant-server requests to Adyen determine payment authorization. Authentication-only is a separate linked Classic route and does not itself authorize a later payment. Q2. How does the guide handle the main response branches and version-sensitive iOS requirements?
Expected: The server sends `/authorise` with app device channel, card data, `browserInfo` for possible 3DS1 fallback, and an SDK version preferably obtained with `ADY3DS2SDKVersion()` rather than hard-coded. `IdentifyShopper` supplies directory-server values, message version, and token; the app creates and retains an SDK transaction, then its fingerprint parameters go through the server to `/authorise3ds2`. A frictionless `Authorised` means payment authorization succeeded; `ChallengeShopper` requires the SDK challenge and a later `/authorise3ds2` request with `transStatus` and token. `RedirectShopper` may signal 3DS1 fallback. For SDK 2.2.0+, use the returned message version to create the transaction. The challenge URL is qualified to 3DS version 2.2.0+, with earlier versions ignoring it. The guide conflicts internally: setup says SDK 2.3.0+ for native flow while the Swift Package Manager tab says select 2.2.1+.
