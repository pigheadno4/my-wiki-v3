# Fixed retrieval queries — Classic retrieve stored details

Q1. What is this page for, what scope does it cover, and what should it not be used to infer?
Answer: It is an inactive Classic Recurring API guide for `/listRecurringDetails`, which lists payment details stored previously with an `/authorise` call and returns a `recurringDetailReference` for later requests. The request uses a merchant account and shopper reference; the test cURL example uses an API key. It is not a Checkout API token-creation guide, consent specification, proof of successful payment, or guarantee that illustrative card/shopper fields always appear. Evidence: pinned raw lines 16–27, 60–70, 239–250, 252–342. Canonical route: https://docs.adyen.com/online-payments/classic-integrations/classic-api-integration/tokenization/retrieve-stored-details

Q2. What is the central request/response capability, including prerequisites and absence cases?
Answer: For a shopper whose details were previously stored, send merchantAccount and shopperReference to `/listRecurringDetails`; the response can contain one or more `RecurringDetail` objects with the stored-detail reference, and method-dependent fields may be missing or nil. A nonexistent shopper reference yields an empty object. If a shopper exists but a requested contract type has no matching detail, the `details` array is omitted. The endpoint is inactive for new integrations; new builds are directed to Checkout API and existing users toward migration discussion. Evidence: pinned raw lines 16–23, 25–27, 239–248. Canonical route: https://docs.adyen.com/online-payments/classic-integrations/classic-api-integration/tokenization/retrieve-stored-details
