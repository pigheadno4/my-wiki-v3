# Retrieval checks: Classic stored-detail authorization

## Q1 — What is this page for, and what should it not be used to infer?

This is a dated guide for subsequent Classic `/authorise` payment requests after details were successfully stored in an initial `/authorise` call. It describes separate one-click and recurring request patterns. The endpoint is marked inactive and unsupported for new integrations; the page directs new builds to Checkout API and existing users to Adyen migration guidance. The page does not document initial shopper consent, establish that a shopper approved later charges, or show a successful authorization or capture. Its examples do not establish current eligibility for a new Classic integration. Canonical route: https://docs.adyen.com/online-payments/classic-integrations/classic-api-integration/tokenization/authorise-a-recurring-payment

## Q2 — How do the one-click and recurring request patterns differ, and what are the CVC and stored-detail limits?

Both sections use the `shopperReference` from storage and `selectedRecurringDetailReference` set to a listed `recurringDetailReference` or `LATEST`; both list `shopperInteraction: ContAuth`. The one-click section uses `recurring.contract: ONECLICK` with `recurringProcessingModel: CardOnFile` and lists a CVC collected from the shopper; its hosted-CSE variant passes the encrypted CVC as `additionalData.card.encrypted.json`. The recurring section uses `recurring.contract: RECURRING` with `recurringProcessingModel: Subscription` and does not list a CVC. These fields select a stored-detail request pattern and do not prove consent, payment success, or capture. The page assumes prior successful storage; consent and token creation belong to the provider tokenization routes.
