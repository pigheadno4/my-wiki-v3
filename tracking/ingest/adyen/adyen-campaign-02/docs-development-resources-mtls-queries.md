# Adyen mTLS retrieval checks

1. **Purpose, scope, and inference boundary.** This 2026-09-15 Adyen guide covers mutual TLS client authentication for supported API calls: the client certificate supplements the server certificate and API key, and Adyen verifies it on each request (`raw/adyen/docs/development-resources/mtls/2026-09-15.md:15-23`). A merchant-generated CSR can be signed by Adyen while the private key remains with the merchant (`:21,53-75`). This is transport/client authentication, not the JWE card-encryption route. The existing JWE concept records a separate EC-certificate versus `RSA-OAEP-256` sample conflict; the mTLS EC CSR example does not resolve it (`wiki/concepts/adyen-card-encryption.md`, `raw/adyen/docs/development-resources/mtls/2026-09-15.md:59-75`). The snapshot does not prove current credential eligibility, certificate trust or validity for a particular merchant, successful authentication, or successful payment execution.

2. **Capability, prerequisites, warnings, and detail route.** `wiki/index.md` → `wiki/adyen-index.md` → `wiki/concepts/adyen-api-access.md` → proposed `wiki/sources/adyen/source-adyen-docs-development-resources-mtls.md` → pinned raw; the reciprocal source link is pending promotion. Enrollment uses a company-level `ws_*@Company.*` credential, Management API client-certificate roles, an API key, and CSR tooling; the guide limits the company to 10 valid client certificates of 397 days and excludes merchant-level and balance-platform credentials (`raw/adyen/docs/development-resources/mtls/2026-09-15.md:25-39`). Adyen builds `subjectDN` from company and credential, returns a Base64 DER leaf plus CA chain, and requires leaf-first full-chain PEM with the private key; a leaf-only handshake fails with `unknown_ca` before HTTP (`:69-75,83-132`). Linking `subjectDN` is a cutover: subsequent supported-API calls using that credential require the certificate; test enrollment, linking, and a request before live linkage (`:136-180`). Checkout, classic Payment, Recurring, Payout, and BinLookup are supported, while Management, Balance Platform, Transfers, Legal Entity Management, and Terminal Management keep API-key calls at standard endpoints (`:205-215`). Checkout mTLS hosts vary by live region; the other supported group uses `palcert`, and the ordinary prefixed live Checkout API-key host is wrong for mTLS (`:217-239`). Curl/Java examples and external-CA trust/DN conditions remain at `:241-321`.
