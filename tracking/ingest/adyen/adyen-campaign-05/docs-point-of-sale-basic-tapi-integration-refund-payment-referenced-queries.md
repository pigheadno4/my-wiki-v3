## Query 1: What is the POS referenced-refund procedure, and which identifier/API does it use?

Answer: The basic full or partial refund is a Terminal API `ReversalRequest` (`MessageCategory: Reversal`, `ReversalReason: MerchantCancel`) sent via the selected terminal `POIID`. It references the original payment's `POIData.POITransactionID.TransactionID` in `tenderReference.pspReference` form plus its timestamp; the refund request receives a separate PSP reference (raw lines 19-26, 42-68, 133-142, 188-218). The guide is a POS/Terminal API source, not a Checkout API refund procedure, and does not add separate local-versus-cloud instructions. ## Query 2: What amount, offline/ecommerce exceptions and outcome boundaries matter?

Answer: A partial refund adds numeric `ReversedAmount` no greater than the original payment amount and a currency matching that payment; the page allows multiple partial refunds (raw lines 23-26, 208-218). For an offline payment without a PSP reference, once online the merchant can take the PSP reference from the webhook/Customer Area or use tender reference and payment date; the guide says an original device ID is needed in most cases and marks `OriginalPOITransaction.POIID` required in its terminal/card-reader/installation-ID examples. An early tender-reference refund is queued, and the page distinguishes pre-settlement cancellation from post-`Sent for Settle` refund status (lines 358-420). Its refund-when-back-online Mobile exception is iOS-only, with Tap to Pay on iPhone Store and Forward limited to the US (lines 28-36). For an ecommerce payment sent through this Terminal API procedure, use `.pspReference` with the leading dot and original date/currency; zero amount fields in its full response are not a zero refund outcome (lines 456-508). `ReversalResponse.Result: Success` only acknowledges receipt; await `CANCEL_OR_REFUND` for outcome (lines 133-186, 300-356). The same index → concept → source → raw route applies.
