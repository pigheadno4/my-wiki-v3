# POS card and shopper identifiers: fixed retrieval checks

1. **What does this guide cover, and what does it not prove?** It catalogs card and shopper identifiers in Terminal API card acquisition/payment responses and optional standard-webhook `additionalData` for merchant recognition, insights, loyalty or recurring use. Card alias represents a PAN for recognition but cannot pay; PAR represents the underlying account behind a card/NFC wallet when available; token variant is a wallet type, while recurring detail reference is the recurring-payment token. It does not establish raw PAN availability, authorize a payment, prove merchant entitlement, or guarantee that a particular scheme/region returns PAR. Locate raw lines 15-33 and `## Overview of card and shopper identifiers` (53-88), including the dated Visa/Mastercard conditional at 67.

2. **How are identifiers obtained and handled?** BIN/funding source are automatic in this guide's Terminal API response path; alias, issuer country, PAR, shopper reference and recurring detail reference need `Developers > Additional data` selection, and email must first be collected/submitted. Webhooks need a standard webhook plus separate additional settings; PAR and token variant also need the Developers switch. `AdditionalResponse` can be key/value or Base64 JSON. Merchant use needs consent/privacy review, its own storage and business logic; deletion of Adyen-held data through the linked Data Protection API is separate from merchant-held records. Locate raw lines 35-51, `## Receive identifiers in Terminal API responses` (90-117) and `## Receive identifiers in webhooks` (207-241).
