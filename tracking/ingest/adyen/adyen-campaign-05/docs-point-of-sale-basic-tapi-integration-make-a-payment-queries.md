# Adyen C05 — make a payment fixed answers

1. **Purpose/scope; what not to infer.** The 2026-09-15 *Make a payment* page explains a basic in-person Terminal API card-payment request from a merchant POS app to an Adyen terminal, or a Mobile-solution test device (`raw/adyen/docs/point-of-sale/basic-tapi-integration/make-a-payment/2026-09-15.md:15-40`). It documents request structure, shopper interaction, response interpretation, and troubleshooting (`:58-305`). It is not a Checkout or Management API procedure, an SDK-version specification, proof of card/wallet eligibility, or proof of capture/settlement/live execution. The example response's sensitive-card-data placeholder does not establish PCI handling (`:201-211`).

2. **Central capability/prerequisites/warnings and route.** The merchant must first design the relevant terminal or Android/iOS Mobile integration and obtain a POS test card plus boarded test terminal or test mobile device (`:21-34`). The POS sends `PaymentRequest` with a header identifying sale component, terminal, and per-terminal `ServiceID`; the latter is 1–10 alphanumeric characters and unique over 48 hours for the `POIID` (`:60-84`). The request's merchant reference differs from the returned `POITransactionID`, which should be saved for later lookup/reconciliation/actions (`:80-81`, `:156-165`). `Response.Result` distinguishes approved `Success`, declined `Failure`, and possible `Partial`; asynchronous cloud terminal response comes in an event notification (`:55-56`, `:161-165`). For a missing response, Adyen strongly recommends automatic status verification to reduce staff-initiated duplicate/refund actions; failures call for error-field inspection and separate refusal guidance before retry decisions (`:275-297`).
