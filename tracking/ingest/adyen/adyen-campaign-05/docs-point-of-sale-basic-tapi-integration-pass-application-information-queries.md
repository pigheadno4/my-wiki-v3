# Fixed retrieval checks — Adyen POS application information

1. **What does this page document, and what should it not establish?** The 2026-09-15 Adyen guide documents merchant-supplied platform, POS application and device-OS labels in Terminal API payment-request `applicationInfo` for troubleshooting. It is not a Checkout API `/payments` contract, credential setup, hardware model/serial inventory, independent software-version verification, or evidence that a merchant's payment authorized or settled. See `# Pass application information`, `## Requirements`, and `## Application information fields` in [[raw/adyen/docs/point-of-sale/basic-tapi-integration/pass-application-information/2026-09-15|pinned raw]].

2. **Which fields and formats are involved, and how is the route found?** Required metadata: `externalPlatform.name`, `externalPlatform.integrator`, `merchantApplication.name`, `merchantDevice.os`, and `merchantDevice.osVersion`; platform/app version fields are conditional on those having versions. Values have length/character rules and must be formatted consistently. Put `applicationInfo` in Terminal API `PaymentRequest.SaleData.SaleToAcquirerData` as Base64 JSON or ampersand-separated key-value pairs; the format determines `AdditionalResponse` format unless Support configures a consistent one. Example `SaleID`, `ServiceID`, `POIID` and `SaleTransactionID` are request identities outside `applicationInfo`. See `## Application information fields`, `### Field value requirements`, both `### Tab: Option` sections, and `## Combining application info and other data elements`.
