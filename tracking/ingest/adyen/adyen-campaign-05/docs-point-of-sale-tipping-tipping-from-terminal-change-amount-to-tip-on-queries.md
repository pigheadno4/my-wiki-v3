1. **What amount changes when the POS overrides the amount to tip on?** The merchant POS changes the suggestion base shown at the terminal, not the full purchase amount. It sends `RequestedAmount` as the full purchase (decimal units), `AskGratuity` in `SaleToAcquirerData`, and a Base64 `Operation` with `AmountToTipOn` plus `TipSuggestions` in `SaleToPOIData`; this replaces Customer Area tipping choices for that payment. The parameter table lists `AmountToTipOn` beside `TipOptions`, while the worked JSON nests it inside `TipOptions`; the page leaves that placement inconsistent. In the example, purchase EUR 20, base EUR 15, 20% choice yields EUR 3 tip and EUR 23 `AuthorizedAmount`. The prose describes minor-unit purchase/tip/authorized fields in `AdditionalResponse`, but names the total `authorisedAmountValue` while the sample shows `posAuthAmountValue=2300`; use the raw with this discrepancy in view. The sample omits receipt contents, so it does not establish receipt units. Locators: raw lines 19–25, 37–70, 94–100, 139–155, 171–191. Route through Terminal API concept to this source/raw.

2. **Who can use this flow and what money-flow claims are supported?** The guide requires a Terminal API integration with payment terminals on software 1.103+ and merchant logic to choose when to override; pay-at-table including split checks is excluded. Percentage presets are at most three and numeric percentage values must not exceed 100, with optional custom tip. The response separates selected `TipAmount` from purchase-plus-tip `AuthorizedAmount`; it does not establish a separate capture step or where the merchant distributes gratuity. Locators: raw lines 27–49, 72–100, 139–155. Broader Customer Area tipping configuration is routed through the linked terminal-tipping guide, not inferred from this worked example.
