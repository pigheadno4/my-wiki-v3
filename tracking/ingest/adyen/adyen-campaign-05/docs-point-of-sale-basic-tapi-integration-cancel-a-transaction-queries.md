# Cancel an in-progress POS transaction: fixed retrieval checks

1. **What is this guide's action, and what does it not establish?** It documents stopping an unfinished terminal payment from a Terminal API POS `AbortRequest` or terminal Cancel control. Abort must reach the terminal before approval; a completed payment cannot be aborted. Authorized-payment cancellation with delayed/manual capture and refund after failed cancel are separate linked paths; this page does not supply a ReversalRequest contract, cloud/mobile delivery semantics, or proof that HTTP `200` finalized a payment cancellation. Locate raw lines 15-47, `## Cancel from your POS app` (49-151) and `## Handling failed cancel requests` (260-262).

2. **Which IDs and responses keep an abort safe?** The Abort message header has the **new** request's `ServiceID`, `SaleID`, `POIID` and `MessageCategory: Abort`; its `AbortRequest.MessageReference` carries the **original Payment** request's `SaleID`/`ServiceID`. An accepted abort call returns HTTP `200` without a body, while the original payment should report `Failure`/`Aborted`; a status request referencing that original Payment can confirm. If the original `ServiceID` is unavailable because Payment/CardAcquisition is still in progress, an empty `TransactionStatusRequest` can recover its original reference; this form applies only while in progress. Terminal Cancel reports `ErrorCondition: Cancel` when successful, but Cancel on an already-authorized signature screen does not cancel payment. Locate raw lines 49-70, 100-159, 199-237 and 239-262.
