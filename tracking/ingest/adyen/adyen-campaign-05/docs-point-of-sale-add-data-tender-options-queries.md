# Fixed retrieval queries — docs-point-of-sale-add-data-tender-options

## Query 1: What are Adyen POS tender options and where are they carried?

Answer: They are per-payment parameters changing how a Terminal API tender is processed, carried in `PaymentRequest.SaleData.SaleToAcquirerData` for integrations with payment terminals (raw lines 23-37). The seven listed names cover partial-authorization allowance, Giving, gratuity, forced decline, MOTO, receipt ownership and AID-priority override (lines 39-47). Their listing is not proof that a specific account, card method, terminal or region permits the feature. Standalone configuration is routed to Adyen Support (lines 19-21). Route: `wiki/index.md` → `wiki/adyen-index.md` (Campaign 05 catalog pending coordinator promotion) → `wiki/concepts/adyen-terminal-api.md` → `wiki/sources/adyen/source-adyen-docs-point-of-sale-add-data-tender-options.md` → `raw/adyen/docs/point-of-sale/add-data/tender-options/2026-09-15.md`.

## Query 2: What format and consequential defaults/actions does the page specify?

Answer: Send one or more comma-separated option names without spaces either as Base64-encoded JSON containing `tenderOption` or as `tenderOption=...` key/value text; the selected format carries through to `AdditionalResponse` (raw lines 49-62). Without `ReceiptHandler`, the terminal must print and a terminal without a built-in printer causes transaction failure; with it, the POS app handles print or email (line 46). `MOTO` is card-not-present, `SkipAIDPriority` permits shopper application choice, and `ForcedDecline` declines the transaction (lines 41-47). The tip response's `OnlinePIN` is only an example and does not define a CVM rule (lines 137-169). Other data can coexist in the field; transaction conditions for entry/method choice and Support-configured every-payment defaults are separate controls (lines 182-193). No offline or token tender option or terminal-software gate is defined on this page. The same index → concept → source → raw route applies.
