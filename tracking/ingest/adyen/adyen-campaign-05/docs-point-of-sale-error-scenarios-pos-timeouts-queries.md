# POS time-outs: fixed retrieval checks

1. **What time-outs does this guide distinguish, and what should not be inferred?** It covers issuer **processing**, shopper/device-interaction, and overall **request** time-outs for POS transactions. A confirmed processing timeout after terminal verification is platform-canceled at 120 seconds local or 150 cloud, with `Failure`/`Communication timeout`; most device waits cancel but some advance a screen; a request timeout may leave the terminal payment active. The guide does not set Mobile SDK sessions, a universal retry count, or a safe retry solely from elapsed time or a `Reject` event. Locate raw lines 19-25, `## Processing time-out` (27-69), `## Device time-out` (71-134) and `## Request time-out` (136-175).

2. **What should a POS do with each result?** A confirmed processing timeout permits trying a different card/method, but if the result or timeout is missing at the stated local/cloud window, query transaction status first. For canceled device timeouts, the guide says retry; inspect the `Failure`/`Cancel` payment result and `AdditionalResponse` rather than treating a tipping-screen transition as cancellation. A request-timeout event has `EventToNotify: Reject` but the terminal can still accept shopper input and complete the payment; query status for the original result before any repeat. Device table values vary by interaction (raw lines 81-98), including PIN 60 seconds, signature check 900, and authorization-in-progress 200. Locate raw lines 29-69, 73-104, 134-175.
