## Query 1: What can this guide cancel, and which API and reference identify it?

Answer: It cancels a **pending unreferenced POS refund request**, during a Support-configured delay, by POSTing to the backend Payment API `/voidPendingRefund`; the page explicitly says this is not a Terminal API request (raw lines 15-21, 23-32). Preferred inputs are the **refund request's** `tenderReference`, `uniqueTerminalId` and `merchantAccount` (lines 34-42). Alternatively send `originalReference` equal to that refund request's PSP reference with `merchantAccount` (lines 63-72). These are not identifiers of the shopper's original purchase. The response's separate `pspReference` belongs to the void request, not to the pending refund (lines 52-60, 82-90). ## Query 2: What setup, timing and result boundaries govern cancellation?

Answer: Adyen Support must set up delayed POS refunds first; the delay covers only unreferenced refunds. Referenced refunds cannot be cancelled by this flow, and no delay or an expired delay leaves no cancellation window (raw lines 19, 23-32). Scope includes integrated/standalone terminals and Mobile solutions. The POS app needs an API key; cloud Terminal API setups may reuse the existing key, while this page names no additional API credential role. Set up Standard webhooks (lines 27-32). `[voidPendingRefund-received]` is request receipt, not the result; wait for `VOID_PENDING_REFUND` and its `success` field to learn whether cancellation succeeded (lines 52-60, 82-122). The page does not establish funds movement or bank posting from the response. The same index → concept → source → raw route applies.
