1. **What is this page for, and what should it not be used to infer?** The Adyen Docs guide explains how a POS app uses Terminal API response `PaymentReceipt` data to print, display, or email shopper receipts, and how built-in terminal printers behave (raw lines 15–21, 50–65, 144–160). It separately notes that standalone terminals auto-print and are not POS-integrated (line 21). It is not proof that a transaction captured, settled, or funded; receipt keys vary by result, including approved, refused and void states (lines 151–172). Its key table lists possible fields, not universally mandatory fields (lines 160–230). Route through the root index, Adyen index, Terminal API concept, proposed source, and pinned raw; versioned GitHub evidence is separate.

2. **What central receipt behavior, prerequisites, and warnings should a reader retrieve?** `CustomerReceipt` is for the shopper; `CashierReceipt` is for the merchant and may support signature or reconciliation (raw lines 144–149). Scheme and country/region requirements can change; Adyen recommends unaltered generated data and puts compliance responsibility on merchants that override or hard-code it, with chargeback risk for noncompliant receipts (lines 32–40). URL-decode `PaymentReceipt` before printing when non-Latin characters in the request were URL-encoded (lines 42–44). A built-in printer normally prints, while `ReceiptHandler` suppresses that printing so the POS app can deliver it; **Ask before printing** is another setting (lines 50–65). Merchant and shopper language paths differ and skip excluded languages (lines 67–100). `cardholderName` is off by default and Support-enabled only on the merchant receipt (line 179).
