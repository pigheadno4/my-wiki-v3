# Fixed locator-backed retrieval checks

1. **Purpose and scope; what should not be inferred?** This Adyen Docs guide is for recovering the status of an original Terminal API transaction when its POS response is missing, across payment-terminal, Android/iOS Mobile SDK, and Android Payments app solutions (raw lines 15–40). A `TransactionStatusResponse.Response.Result=Success` only says the original transaction reached an end state; the embedded original response determines approval, cancellation, or decline (119–138). It does not by itself prove successful payment, capture, or settlement. The linked `See also` pages (357–361) are navigation only. 2. **Request/result identities, timing, and retry warnings?** With internet intact and a missing/timed-out response, check status after 120 seconds local or 150 seconds cloud; Mobile SDK can check immediately when the response is noticed missing, from the POS app on the mobile device, and asynchronous cloud checks use `/sync` (raw 35–48). The new status request has its own unique `ServiceID`; `MessageReference` uses the **original** `SaleID`, `ServiceID`, and Payment/Reversal/StoredValue category (52–85). `Success` returns the original response for interpretation (119–138); `Failure/InProgress` can be polled without added delay, with mobile in-progress fields limited (276–287). `Failure/NotFound` may mean wrong identifiers or an original request never received; verify IDs before considering retry of the original (321–328).
