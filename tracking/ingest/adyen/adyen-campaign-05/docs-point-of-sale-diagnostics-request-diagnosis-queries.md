# Fixed retrieval checks — Adyen POS diagnosis

1. **What does the diagnosis request measure, and what must not be inferred?** In the 2026-09-15 snapshot, Terminal API diagnosis reports physical-terminal component state, host reachability and unforwarded offline payments; a separate Android/iOS Mobile SDK path checks security, offline queue and SDK expiry. It excludes the Mobile Payments app. A diagnostic `Result: Success`, `GlobalStatus: OK`, or `IsReachableFlag: true` does not establish authorization, capture, settlement, or a particular payment's final outcome. See `# Make a diagnosis request`, `## Requirements`, and both diagnosis sections in [[raw/adyen/docs/point-of-sale/diagnostics/request-diagnosis/2026-09-15|pinned raw]].

2. **How do conditions, side effects, fields and warnings differ by path, and where is the route?** A terminal `DiagnosisRequest` starts with `HostDiagnosisFlag: false`; a positive `unconfirmedBatchCount` prompts another request with true and a `HostStatus.IsReachableFlag` check. `POIStatus` and `AdditionalResponse` give conditional battery/printer, network/configuration, merchant/store, terminal ID and firmware/P2PE versions; `ARS_TRIGGERED` on UX300/UX410 requires stopping use. Mobile `POIID` is an SDK installation ID, and true host diagnosis attempts security scan, forwarding supported offline transactions and iOS-only failed-capture retry; false stays offline. `sdkExpiry`, offline and attestation status, and iOS retry status have distinct meanings; Busy returns diagnostic failure while another request runs. See `### 1. Verify the condition of a terminal`, `### 2. Verify that the Adyen host system is reachable`, `## Diagnose a Mobile SDK solution`, and `## Failed diagnosis request`.
