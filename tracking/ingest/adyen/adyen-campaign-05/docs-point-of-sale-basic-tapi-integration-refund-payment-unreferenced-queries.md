## Query 1: What is this POS unreferenced refund, and what API/request type handles it?

Answer: It refunds an amount to a card presented at the terminal **without linking the request to the original purchase**, leaving the merchant to reconcile it and fully liable for fraudulent or duplicate losses (raw lines 15-23, 50-59). The POS submits a Terminal API `PaymentRequest` with `MessageCategory: Payment` and `PaymentData.PaymentType: Refund`, plus refund reference, amount/currency and terminal `POIID` (lines 142-168). This differs from a referenced POS `ReversalRequest` and from an online Checkout API refund. The page covers terminal and Mobile Terminal API integrations and does not introduce a separate local/cloud refund request. ## Query 2: What enables and limits the flow, and how is outcome established?

Answer: Store or terminal/mobile-device enablement can use Customer Area with **Merchant POS Terminal Management** role, or Management API `/terminalSettings` PATCH with API key and **Terminal settings read and write** role. The API only enables the feature; Customer Area sets a store/terminal unreferenced refund limit, and Support handles company/merchant enablement and refund delay. The guide says a configured per-refund limit rejects over-limit requests (raw lines 25-48, 50-140). MCC and listed country exclusions apply; QR wallets require referenced refund, and gift cards need separate parameters (lines 35-48, 142-144). A PaymentResponse `Success` usually confirms receipt, with asynchronous processing; synchronous `acquirerResponseCode: Approved` is conditional on scheme and card-use country/region. Adyen directs the merchant to `REFUND_WITH_DATA` webhook outcome (lines 248-328). Its offline-payment tender reference suggestion concerns reconciliation, not proof of offline refund execution (lines 160-168). The same index → concept → source → raw route applies.
