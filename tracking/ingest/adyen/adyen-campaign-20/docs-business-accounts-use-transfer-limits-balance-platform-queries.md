# Worker retrieval checks

Q1. What does the guide configure, at which scope, and with which prerequisites?

A1. It documents a platform-level transfer limit for outgoing external transfers from all balance accounts on a Business Accounts-enabled Adyen for Platforms integration (raw lines 15–19, 27). The Configuration API credential needs Balance platform base role, and the requirements list Transfer and Transaction webhooks; internal and incoming external transfers are excluded (raw lines 28–32). The POST uses a balance-platform path ID, minor-unit amount/currency, `perTransaction` or `perDay` scope, `instant` or `all` transfer type, dates and `scaInformation.exemption: setByPlatform` (raw lines 42–60). Route: [[index]] → [[adyen-index]] → [[adyen-business-accounts]] → [[source-adyen-docs-business-accounts-use-transfer-limits-balance-platform]] → [[raw/adyen/docs/business-accounts/use-transfer-limits/balance-platform/2026-09-15]].

Q2. What lifecycle, conflict and evidence boundary matter when interpreting a configured limit?

A2. A future-start limit is scheduled, becomes active on its start date and inactive after its end date; no end date leaves it active until override (raw lines 34–40, 53–54). This platform page says no more than one future limit (raw line 53), but the parent [[source-adyen-docs-business-accounts-use-transfer-limits]] permits multiple limits with different `scope`/`transferType` combinations and only one scheduled or `pendingSCA` limit per same combination (parent raw lines 65–69); the cross-page descriptions conflict, so do not infer a global one-future-limit API cap. Only pending or scheduled limits may be deleted; active ones require a new overriding limit (raw lines 246–250). The page's blanket statement that creation starts scheduled conflicts with its later active-or-scheduled response instruction (raw lines 37, 89), and its create curl body is malformed (raw lines 73–86). The parent/related balance-account guide describes a matching account-level override, so a platform limit alone does not establish the effective limit for a user; a configuration example is not proof that a live transfer was blocked, approved or received.
