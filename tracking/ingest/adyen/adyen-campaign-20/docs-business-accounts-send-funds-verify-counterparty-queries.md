# Worker retrieval checks

Q1. What is the guide's purpose and which prerequisites does it state?

A1. It describes a Business Accounts recipient-name lookup before an outgoing transfer to a domestic EU or UK bank account (raw lines 15–26). The documented preparation is a Balance Platform API key with the **CounterpartyNameVerification Webservice Initiate** role and contacting Adyen Support to enable it (raw lines 28–36). The EU check uses an IBAN plus proposed account-holder name; the UK check uses account number, sort code, personal/business account type and proposed name (raw lines 48–62, 81–92, 118–132). Q2. What material boundary, failure state or conflict must an answer preserve?

A2. `POST /verifyCounterpartyName` returns a name-check classification. Even after a `nameMatch`, the platform prompts for the user's decision; only confirmation leads to the separate `POST /transfers` request (raw lines 62–75). `noNameMatch`, unsupported checks and UK account/type exceptions need distinct messaging, and the readable `responseDescription` is not for client logic (raw lines 202–219, 221–280). The test environment forces a chosen result through `reference` and defaults an unrecognized reference to 200/`nameMatch` (raw lines 282–294), so its output is not live bank verification or transfer/receipt proof. The raw's generic partial-match statement at line 70 is expanded by its UK-only partial business/personal result values at line 202; the final sample's `reference` also conflicts with the request (raw lines 525–541).
