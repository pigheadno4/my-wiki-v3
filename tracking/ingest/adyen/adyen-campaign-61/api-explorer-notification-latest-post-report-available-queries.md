## Q1

Adyen produces the incoming Classic `POST /REPORT_AVAILABLE` notification when a report has been generated and is available for download. Its request table requires `eventDate`, `eventType`, `executingUserKey`, `live`, and `pspReference` (the originating request's PSP reference). Optional `content` can contain `accountCode`, `accountType`, event date, `remoteAccessUrl`, and event `success`; optional `error` carries code/message. The page's example contradicts the event heading by using `eventType: TRANSFER_FUNDS` and transfer-specific content, so those sample fields do not establish the REPORT_AVAILABLE payload. No download lifetime or report-deletion rule is given. [[source-adyen-api-explorer-notification-latest-post-report-available]] (https://docs.adyen.com/api-explorer/Notification/latest/post/REPORT_AVAILABLE), raw lines 5–27, 29–72.

## Q2

The response table says optional `notificationResponse` may be set to `[accepted]` to acknowledge notification receipt; its 200 label concerns the receiver response, not report generation or download success. The event description says a report is available, while `content.success` is optional event data. This endpoint does not establish actual report retrieval, delivery order/retry/deduplication, signature verification, or failure/reversal handling; the transfer example cannot fill those gaps. No deprecation claim is made by this page. [[source-adyen-api-explorer-notification-latest-post-report-available]] (https://docs.adyen.com/api-explorer/Notification/latest/post/REPORT_AVAILABLE), raw lines 7, 14–27, 31–81.
