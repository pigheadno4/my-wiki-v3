## Q1

Adyen produces the legacy `balancePlatform.incomingTransfer.updated` Payment webhook when funds have been added to a balance account by a refund or incoming funds transfer. `data.id` correlates the incoming-transfer resource from `balancePlatform.incomingTransfer.created`; optional `paymentId` traces the original payment authorization, refund, or transfer request from `balancePlatform.payment.created`. For this event `status` is `Refunded` or `IncomingTransfer`, respectively. The request requires outer `data`, `environment`, and `type`, while most nested fields, including `id`, `status`, amounts and references, are optional. In optional `amount` and `originalAmount`, currency and minor-unit value are required when the object exists; signed values distinguish additions/deductions. The table also distinguishes optional modification details and split/payment/counterparty references. [[source-adyen-api-explorer-payment-webhooks-latest-post-balanceplatform-incomingtransfer-updated]] (https://docs.adyen.com/api-explorer/payment-webhooks/latest/post/balancePlatform.incomingTransfer.updated), raw lines 5–13, 17–72.

## Q2

This event describes a legacy balance-account funds addition and its cause-specific status; it does not establish beneficiary bank receipt or any separate payment authorization outcome. Any HTTP `2xx` accepts the incoming webhook, a receiver action distinct from the event's financial meaning. The family overview labels Payment webhooks v1 deprecated and directs use of accounting webhooks in the Transfer-webhooks family, so this endpoint cannot be substituted for that replacement contract. The endpoint supplies no delivery/order/retry/deduplication or signature rules, and its generic cross-event status table must be restricted to `Refunded`/`IncomingTransfer` for this type.
