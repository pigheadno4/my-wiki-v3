## Q1

This is an **incoming Payment webhooks v1** `balancePlatform.payment.created` event for an initiated payment authorisation, refund, or funds transfer. Adyen says the event informs the server of requests, and a payment case carries an authorisation result and processing merchant with a negative amount; a refund carries the target payment instrument with a positive amount; an incoming/outgoing transfer has a direction-dependent sign. The top-level body requires `data`, `environment` (`test` or `live`) and `type`. `data.status` is optional; for this *exact* type its listed values are `Authorised`, `Refused`, and `Error`. `data.amount` is in balance-account currency and `data.originalAmount` in transaction currency; each optional object, when present, requires its own ISO currency and minor-unit value. Optional IDs and references include account holder and balance account object IDs/references, payment-instrument ID/reference, `data.id`, split-linked `platformPayment` PSP/merchant references, transfer-request `reference`, and counterparty `referenceForBeneficiary`. The table also distinguishes event trigger `creationDate` from queue `timestamp` and gives a 140-character description truncation rule. The prose says a funds-transfer event contains only balance-account information, **but** its funds-transfer example contains `accountHolder` (lines 200–204); the schema marks that object optional, so neither universal presence nor absence follows. Examples illustrate authorised, refund, funds-transfer and refused cases without establishing a universal payload shape. ## Q2

This event reports initiation and, where applicable, authorisation status; it is **not** proof of booked movement, capture, settlement, completed refund, payout, or bank receipt. The endpoint says actual fund movements are reported by subsequent outgoing or incoming transfer webhooks. Any HTTP `2xx` accepts the webhook, with optional `notificationResponse`; that acknowledgment does not change the request's financial state. The separately captured Payment webhooks v1 overview labels the family deprecated and directs readers to accounting webhooks. The endpoint's shared status enum contains values for other webhook types and must not be imported into this type or into newer Transfer/Transaction webhook contracts. No delivery ordering, retry, deduplication, signature, or financial-finality guarantee is stated here; the `latest` URL does not prove current availability.
