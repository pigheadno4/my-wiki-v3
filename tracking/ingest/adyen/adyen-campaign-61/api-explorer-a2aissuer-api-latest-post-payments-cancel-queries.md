# Fixed query answers — api-explorer-a2aissuer-api-latest-post-payments-cancel

## Q1

The 2026-09-15 capture is A2A Issuer API v1 `POST /payments/cancel`, an issuer-facing Business Account payment operation, not a merchant Checkout cancellation endpoint. The request requires a body `token`, generated by Adyen in the payment-details response, to identify the payment. The reference lists test and live `/a2aissuer-api/v1` servers. A `200` response requires `links`; `links.cancel` and `links.success` are optional objects, with `href` required inside whichever object appears. Its response example provides only `links.cancel.href` for redirecting the user. The related iDEAL guide says the target payment must still be pending, unexpired and unconfirmed. The endpoint gives no additional request field, amount, deletion or reversal contract. Raw lines 5–45 and 103–116; related guide raw lines 484–511. ## Q2

The endpoint labels `200` a successful request and returns a redirect link, but the separately captured [[source-adyen-docs-business-accounts-send-funds-ideal-integration|iDEAL guide]] says the payment is considered canceled when `links.cancel.href` is opened. Thus the API response alone does not prove completion of that user path or funds movement. The reference documents `400` malformed/format, `422` validation and `500` server errors. Its `422` examples include invalid token (`1069_003`), expired payment (`1069_004`), final-state payment (`1069_005`), payment-method processing error (`1069_006`) and missing/invalid data (`29_001`); these examples are failure cases, not retry guarantees. Error fields are mostly optional, with required `message`, `name` and `value` only inside an `invalidFields` item when that item appears. This request/response API page gives no webhook acknowledgement, delivery-order, deduplication or signature rule and no current account eligibility proof. Raw lines 32–102 and 118–218; related guide raw lines 484–511.
