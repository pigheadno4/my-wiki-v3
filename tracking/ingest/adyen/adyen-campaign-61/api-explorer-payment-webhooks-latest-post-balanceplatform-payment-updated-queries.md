# Fixed query answers — api-explorer-payment-webhooks-latest-post-balanceplatform-payment-updated

## Q1

The 2026-09-15 capture is the incoming `POST balancePlatform.payment.updated` reference for an expired or cancelled payment authorisation. Adyen says `data.id` correlates it with the original `balancePlatform.payment.created` authorisation, although the table marks `data.id` optional. Required top-level fields are `data`, `environment` (`test` or `live`) and `type`; the listed nested `data` fields, including `status`, `modification`, account-holder and balance-account objects, are optional. If the optional `amount` or `originalAmount` object appears, its `currency` and minor-unit `value` are required. `modification` can describe partial cancellation or expiry. For this event type the status row lists `Expired`, `Cancelled`, `AuthAdjustmentAuthorised` and `AuthAdjustmentRefused`; other row values belong to other event types. The three TEST examples all use `Expired` for `status` and `modification.type`, even the one labelled partially cancelled. The examples' queue `timestamp` precedes event-trigger `creationDate`, so they do not support an event-to-queue timing inference. Raw lines 5–79 and 81–387. ## Q2

The response section shows `200 Success`; any `2xx` HTTP status accepts the incoming webhook, and `notificationResponse` is optional. That is receiver acknowledgement, not a payment settlement, booked balance-account transaction, bank receipt or reversal result. The endpoint gives no delivery-order, retry, deduplication or signature rule. The separate [Payment webhooks v1 overview](https://docs.adyen.com/api-explorer/payment-webhooks/latest/overview), captured 2026-09-15, explicitly deprecates this family and directs readers to accounting webhooks at the Transfer-webhooks overview; this endpoint's raw page does not itself state that migration. The `latest` route and dated capture do not prove a current live version. Raw lines 5–7, 63, 81–387 and 388–396.
