# Retrieval checks — Apple Pay web own certificate

**Q1 — What is this guide for, and what must exist before following it?** It is Adyen's historical own-certificate Apple Pay website setup for Web Drop-in/Components on Advanced or Sessions; Customer Area Merchant admin or Manage API Credentials role and an Apple Developer Program/Enterprise Program account are stated prerequisites (raw lines 15–31). The setup calls for separate TEST and LIVE merchant identifiers and processing certificates, then domain validation, a distinct merchant identity certificate, and Customer Area method addition (raw lines 35–41). **Q2 — Which certificate handles what, and how do renewal and exceptions limit the procedure?** The processing certificate is created from Adyen's CSR and added to the Adyen web-service user's merchant identifier for encrypted payment data; the merchant identity certificate uses a separate merchant CSR and merchant-server PEM to authenticate Apple Pay session requests (raw lines 37–40, 68–84, 168–194). After renewal, an old processing certificate may be used for roughly four hours after new activation; the decoded token `publicKeyHash`/Customer Area `KeyID` comparison and a new key on an authorized payment are the guide's checks (raw lines 86–154). Domain registration and identity-certificate steps instead route Salesforce Commerce Cloud plugin users to plugin documentation (raw lines 158–170). These steps do not prove deployed keys, present-day eligibility or completed payments.
