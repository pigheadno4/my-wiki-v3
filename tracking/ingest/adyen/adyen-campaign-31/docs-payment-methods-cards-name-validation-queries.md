Q1. What does this guide's cardholder name validation do, and what are its prerequisites?
A1. In the dated guide it compares a shopper-provided name to issuer records for Visa/Mastercard via an Advanced-flow Checkout API v69+ zero-value `/payments` authorization, with an API key/Checkout webservice role, issuer readiness, the stated US/UK/Europe scope, and `paymentValidations.name.status: requested`; performed validations incur a fee. The response is synchronous and the merchant chooses any follow-up action. Raw lines 19, 27–36, 47–54, 60–71. Q2. What limits or example conflicts matter before relying on a name-validation response?
A2. A zero-value `Authorised` example does not prove a paid payment or payout. `notPerformed` and `notSupported` are distinct; issuer-unsupported validation has no validation charge. Visa has raw status and per-name fields; Mastercard lacks raw status and returns full-name match only, with scheme-maintained combination logic. The Java/PHP/C#/Go/TypeScript examples omit the required `paymentValidations` field, and one Visa test row pairs raw `fullName: 01` with `partialMatch` although the mapping says `01` means `match`. Treat test fixtures as tests and current eligibility as unverified. Raw lines 49–54, 503–529, 537–590, 618–624, 639–653; example omissions at 142–151, 193–205, 249–260, 345–356, 477–487.
