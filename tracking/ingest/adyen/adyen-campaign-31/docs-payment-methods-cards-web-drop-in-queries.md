# Cards Web Drop-in retrieval checks

Q1. What does the page add, and what comes first? It adds card-specific options to an **existing** Web Drop-in integration, with either the Sessions or Advanced server flow already built and cards added in Customer Area (pinned raw lines 15–37). The v6 import applies only to v6 (39–45), and ordinary card use needs no extra card-specific fields (47–54). Q2. Can these snippets or callbacks prove a successful, compliant live or recurring card payment? No. The page's `onSubmit` and `onError` are client validation events (raw lines 143–161), token permission is a strong recommendation (309–315), and the test examples differ in `storePaymentMethodMode` values and `storePaymentMethod` types (325–631, 991–1376). The page separately calls for secure context and allowed origin for Web v5.20.0+, then test-card, live card-addition and PCI assessment/SAQ A steps before live use (2475–2487). Authentication, authorization, capture and settlement outcomes are not shown.
