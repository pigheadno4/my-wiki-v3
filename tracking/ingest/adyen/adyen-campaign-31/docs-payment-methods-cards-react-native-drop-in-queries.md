# React Native card Drop-in retrieval checks

Q1. What must exist first, and what card-specific setup or options does this page add?
A. It assumes an existing React Native Drop-in integration and cards added in test Customer Area (raw lines 15–26). It says no extra fields or required card-specific integration for basic cards (lines 28–36). Optional settings include holder name, CVC, stored-card and address fields; address lookup needs both callbacks (lines 38–56). Separate debit/credit methods require Checkout API v53+ and server `/paymentMethods` with `splitCardFundingSources: true` (lines 58–85). The test token example uses `test_` card placeholders and a token-created webhook only identifies a stored method (lines 168–193, 557); neither proves live authorization or settlement. Combo-card 3DS and automatic capture are recommendations, not observed outcomes (line 120). Before live payments the page calls for test-card testing and adding cards in live Customer Area (lines 1624–1633); PCI and native SDK version details require separate evidence.
