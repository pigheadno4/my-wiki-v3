# Apple Pay token-decryption retrieval checks

Q1. Who may decrypt, and what is required for Adyen versus merchant decryption?
A. If PCI compliant, the guide presents a choice; otherwise Adyen must decrypt (raw lines 21–29). For Adyen decryption, in-app `payment.token.paymentData` from the `PKPayment` callback is base64 encoded, while web `event.payment.token.paymentData` is JSON-stringified then base64 encoded, and the server submits it as `paymentMethod.applePayToken` in test-v72 `/payments` examples (raw lines 31–72, 363–402). Merchant decryption is for advanced API-only scenarios and requires an Apple Developer Program/Enterprise account, own Apple Pay certificate and PCI compliance to handle unencrypted card details (raw lines 693–703). Q2. What verification and CIT/MIT data boundaries matter, and do examples prove a payment?
A. Self-decryption directs certificate verification, matching key selection by `publicKeyHash`, symmetric-key recovery/decryption, duplicate `transactionId` check and original-transaction verification (raw lines 704–717). CIT mapping includes card and MPI values, but `mpiData.eci` may be omitted when token `eciIndicator` is absent despite a required marker (raw lines 725–738). MIT's table lists card values without MPI, while its illustrative sample adds recurring/network reference fields (raw lines 769–813). The curl PAN is masked even though the table maps real token PAN (raw lines 732, 753, 776, 794), so examples are redacted and show no authorization, capture or settlement.
