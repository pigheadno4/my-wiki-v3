# Card Component retrieval checks

Q1. What is required to add cards to the existing Web Components integration, and how do flows/versions differ?
A. The guide assumes an existing Sessions or Advanced Web Components integration and cards added in Customer Area (raw lines 15–37). No additional fields are needed merely for cards (line 49), but feature-specific parameters remain. Web v6 imports Card and uses `new Card(checkout, ...)`; v5.x.x or earlier uses `checkout.create('card', ...)` (lines 39–45, 66–85, 108–126). Flow-specific debit/credit splitting is in `/sessions` for Sessions and `/paymentMethods` for Advanced (lines 319–393). Q2. What security, consent and outcome boundaries matter, and are examples executable guarantees?
A. Explicit shopper permission for future recurring charges is strongly recommended (raw lines 395–399). Token-created webhooks and stored-method IDs are token lifecycle evidence, not authorization or settlement (lines 720–726, 1436–1466). v5.20.0+ JWE fields need a secure local/HTTPS context in allowed origins; before live card payments the page calls for testing, live Customer Area card setup, PCI DSS assessment and SAQ A (lines 2562–2574). The Advanced stored-card snippet has malformed `});.mount` and address snippets have unresolved example code (lines 225–303, 1450–1466); snippets must be verified. No 3DS, successful authorization, capture or settlement is shown.
