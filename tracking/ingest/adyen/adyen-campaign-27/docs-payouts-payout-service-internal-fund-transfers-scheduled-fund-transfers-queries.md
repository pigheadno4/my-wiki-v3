Q1. What does the scheduled internal-transfer sweep do, and what must be set up?
A. The Payout Service page configures push or pull sweeps between balance accounts on schedule/amount conditions; a met condition triggers a transfer request (raw lines 15–35). API creation is POST `/balanceAccounts/{balanceAccountId}/sweeps` with destination balance-account ID, matching currency and balance-account-time-zone cron (lines 124–150). Q2. What separates schedule configuration from booked movement, and what source conflicts matter?
A. The created/active sweep response and sweep-created/updated webhooks concern the schedule; optional trigger/target/fixed-amount objects govern when/how much a later transfer request moves (raw lines 425–499). Resulting internal movement has separate outgoing and incoming webhook series through received, authorised and booked or failed; Customer Area shows debit and credit entries (lines 831–837). The optional description example uses transferInstrumentId and bank-statement/Payout Report wording, unlike the core balanceAccountId destination; it also names remittanceForBeneficiary versus referenceForBeneficiary in the main parameter table (lines 134–140, 501–540, 824–829). The requirement table names a Transfers API role while the create route is Balance Platform Configuration API (lines 44, 130). Do not infer an external bank payout or substitute roles/fields.
