# C62 fixed-query answers: Terminal API POST /payment

Canonical source: [[source-adyen-api-explorer-terminal-api-latest-post-payment]] — https://docs.adyen.com/api-explorer/terminal-api/latest/post/payment

## Q1

The captured `POST /payment` reference calls this a `PaymentRequest` sent to a terminal to initiate payment and a `PaymentResponse` describing processing by the POI system. It is an API Explorer Terminal API `latest` page captured 2026-09-15. Its cloud **test** servers are Device API `/v1/merchants/{merchantAccount}/devices/{deviceId}/sync` and `/async`; local hosting is a `<local-terminal-IP-address>` placeholder. The merchant account and device ID are URL-routing identities, while the schema distinguishes the sale system, POI/terminal, acquirer and issuer roles. An optional original-transaction field labels SaleID and POIID as NEXO Sale-to-POI identities, but this page does not give a protocol version, full request envelope/MessageHeader, caller credential, SaleID/ServiceID for the current request, or session ID. Raw lines 5–20, 27–44, 54–62 and 108–141. See [[source-adyen-api-explorer-terminal-api-latest-post-payment]] (https://docs.adyen.com/api-explorer/terminal-api/latest/post/payment).

The required request objects are `SaleData` and `PaymentTransaction`. `SaleData.SaleTransactionID.TransactionID` and `.TimeStamp` identify the sale transaction; `PaymentTransaction.AmountsReq.Currency` and `.RequestedAmount` supply the requested money. The response separately requires `SaleData`/sale transaction ID and `POIData.POITransactionID.TransactionID`/`.TimeStamp`, so the current POI ID must not be confused with the request's sale ID or the optional `OriginalPOITransaction` reference. `PaymentData`, `LoyaltyData`, `TransactionConditions`, `OriginalPOITransaction` and optional amount fields are not universal requirements. Within an included `CardAcquisitionReference`, transaction ID and timestamp are required; within included `PaymentInstrumentData`, type is required; an included `LoyaltyAccountID` requires entry mode, identification type and loyalty ID. `PaymentType` offers Normal, Refund, reservation, Completion, Recurring and other enum values without documenting their lifecycle rules. The timestamp text says transaction/event time supports uniqueness, but supplies no expiry, timeout, idempotency, reversal or safe-retry rule. Failure/Partial and error-condition values are defined in the response, not a separate recovery sequence. Raw lines 27–106 and 117–143.

## Q2

The `200 Success` heading presents a response-body schema; it does not imply financial success. `Response` and `Response.Result` are required and the result can be `Success`, `Failure` or `Partial`. The description says `ErrorCondition` is absent or unused for Success and must appear otherwise; `AdditionalResponse` is optional logging information. Required response `SaleData` and `POIData` carry distinct sale and POI transaction IDs. `PaymentResult` is optional; within its optional `AmountsResp`, `AuthorizedAmount` is required while `Currency` is optional. A returned `AuthorizedAmount` is payment-result data, distinct from a transport acknowledgement, and should be interpreted with the actual result. `MerchantOverrideFlag` can state that the merchant forced the result to successful, so `Success` cannot automatically be read as independent issuer approval when that flag is present. Raw lines 108–158 and 177.

The listed async URL does not define callback delivery, completion timing or a final result at initial request acceptance. `OnlineFlag` says whether payment processing required host approval and `AuthenticationMethod` lists customer authentication methods; neither alone establishes an authorization outcome. Optional `PaymentAcquirerData.ApprovalCode`, `HostReconciliationID` and `POIData.POIReconciliationID` identify approvals/periods if present, without proving capture, completed reconciliation, settlement or bank receipt. `PaymentReceipt` is optional customer/merchant print or display material. Optional CMS-protected card data and signature fields are field descriptions, not a complete credential, transport security or payment-authentication recipe. The page has no deprecation statement, live server, explicit Nexo protocol version, reversal/status-recovery procedure, capture flow or settlement timing. Raw lines 11–20, 91–97, 117–120, 138–158 and 177–212. See [[source-adyen-api-explorer-terminal-api-latest-post-payment]] (https://docs.adyen.com/api-explorer/terminal-api/latest/post/payment).
