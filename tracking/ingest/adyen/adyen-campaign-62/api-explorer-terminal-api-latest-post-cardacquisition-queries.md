# api-explorer-terminal-api-latest-post-cardacquisition: fixed query answers

## Q1

The 2026-09-15 capture is an Adyen API Explorer `POST /cardacquisition` CardAcquisition request/response body reference for a Sale System to ask a POI System to read and analyse payment or loyalty card information, usually ahead of a distinct payment or loyalty message pair that refers to the acquisition. Its listed cloud test servers are Device API `/v1/merchants/{merchantAccount}/devices/{deviceId}/sync` and `/async`, identifying merchant account and device ID in the transport path; a local-terminal-IP placeholder is also listed. `SaleData.SaleTransactionID` identifies the Sale or POI transaction via required `TransactionID` and `TimeStamp`; the response additionally requires `POIData.POITransactionID` with those two nested identifiers. The request body requires `SaleData` and `CardAcquisitionTransaction`; optional `CardAcquisitionTransaction.TotalAmount` allows contactless processing, while optional brand, loyalty, entry-mode, customer-selection, payment-type and token-request fields qualify what is requested. In the 200 response body, `Response.Result` is required and can be `Success`, `Failure`, or `Partial`; the response description requires `ErrorCondition` for non-success and says it is absent or unused on success. The page supplies no timeout, retry, reversal, cancellation, expiry, or deprecation timing rule. The `latest` URL and test Device API `v1` transport paths do not state a Terminal API protocol version or complete message header. ## Q2

The page documents a 200 `Card Acquisition Response` body and its processing `Result`, optional `AdditionalResponse`, required Sale/POI transaction identities, and optional payment-brand, instrument, and loyalty-account information. It does not state that HTTP acceptance equals acquisition success: `Result` may be `Failure` or `Partial` and non-success requires an `ErrorCondition`. Even `Success` describes card acquisition processing, not a payment authorization, capture, reconciliation, settlement, or bank receipt; the introductory text places a payment or loyalty message pair after acquisition. The page lists test cloud sync/async addresses and a local placeholder but gives no authentication scheme, security prerequisites, request-header/`ServiceID` correlation, asynchronous callback/status mechanism, or absent-result recovery rule. The URL label `latest` and the Device API path `v1` do not establish the version of a Terminal API message contract. Optional `CardData`, masked PAN, PAR, protected data, and token fields do not promise a particular returned identifier or payment capability. Separate flow guidance is needed for later reference, abort/cancellation, and payment outcomes.
