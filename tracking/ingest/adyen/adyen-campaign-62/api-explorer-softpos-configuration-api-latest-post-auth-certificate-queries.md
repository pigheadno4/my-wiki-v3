# C62 fixed-query answers: SoftPOS POST /auth/certificate

## Q1

The 2026-09-15 SoftPOS configuration API **v3** reference at https://docs.adyen.com/api-explorer/softpos-configuration-api/latest/post/auth/certificate describes `POST /auth/certificate` creating a communication session through mutual authentication between the **Mobile SDK** and Adyen payments platform. The request sends an SDK/device-identifying `setupToken` and a required `merchantAccount`; the page lists SDK callback routes for Android and iOS but does not name a separate caller application or transaction session in the request. Its listed servers include TEST and distinct Australia, Asia Pacific South East, Europe, North East Asia and US live regions. Optional `store` must be omitted when merchant accounts act as stores or for a registered payment facilitator. `subMerchantData`, though marked optional in the table, is required for a registered facilitator and prohibited otherwise; its `displayName`, `id`, `mcc` and `name` are required when supplied, with Amex email/phone and Brazil/Cartes Bancaires tax-ID conditions. A successful 201 response can list optional communication-session `id`, SDK `installationId`, merchant/store, and `sdkData`; if the backend creates a Terminal API transaction request, `installationId` is its `MessageHeader.POIID`. Errors are 400, 401, 422 and 500. The page gives no session expiry, renewal, reversal or payment timing rule. [[source-adyen-api-explorer-softpos-configuration-api-latest-post-auth-certificate]] (raw lines 5–55, 67–79, 82–155).

## Q2

The captured 201 response says the **session request succeeded** and provides possible session/installation identity and `sdkData` to pass to the POS app for authenticating Adyen-platform responses. It is not a Terminal API payment response and proves no authorization, capture, reconciliation, settlement or bank receipt. The header schema marks `X-API-Key` **No** while calling it an API-request authentication key; the explicit 401 “Authentication required” prevents interpreting that table flag as permission for unauthenticated use. The introduction refers to a returned “session token,” but the response schema has no field of that name; it lists optional `id` and `sdkData`. The page does not specify an asynchronous callback or correlation contract, session lifetime, retry/deprecation rule, or successful SDK/device attestation beyond this described mutual-authentication request. The 201 and error examples are placeholders, not actual operational outcomes. https://docs.adyen.com/api-explorer/softpos-configuration-api/latest/post/auth/certificate; [[source-adyen-api-explorer-softpos-configuration-api-latest-post-auth-certificate]] (raw lines 7–34, 67–79, 82–218).
