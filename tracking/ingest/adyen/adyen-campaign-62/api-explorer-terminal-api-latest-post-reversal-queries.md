# C62 fixed-query answers: POST /reversal

## Q1

The 2026-09-15 capture at https://docs.adyen.com/api-explorer/terminal-api/latest/post/reversal describes a Terminal API `POST /reversal` request concerning a **previous payment or loyalty transaction**. It lists cloud **test** `/v1/merchants/{merchantAccount}/devices/{deviceId}/sync` and `/async` URLs and a local-terminal-IP option; the cloud path supplies merchant/device routing, while the request's `OriginalPOITransaction` can separately include a Sale-system `SaleID`, terminal `POIID` if the original transaction came from another POI, and original POI/host identifiers. The page does not state a caller credential, a session ID, or a numbered Terminal API protocol version: `latest` is its Explorer path, `v1` is in the cloud device URL, and the field descriptions refer to the NEXO Sale-to-POI protocol. `OriginalPOITransaction` and `ReversalReason` are required request fields; the reason is one of `CustCancel`, `MerchantCancel`, `Malfunction`, or `Unable2Compl`. The original object's `POITransactionID` and `HostTransactionID` are each marked optional, but each supplied ID object requires its own `TransactionID` and `TimeStamp`. Optional `SaleData` requires `SaleTransactionID` only if that parent is supplied, again with its nested ID and timestamp required. `ReversedAmount` is optional and defaults implicitly to `AuthorizedAmount` when absent. The page specifies no currency requirement, amount cap, reversal completion time, retry window, or subsequent lifecycle. ## Q2

The same captured contract labels its response `200 Success`, yet the required body `Response.Result` permits `Success`, `Failure`, or `Partial`; `ErrorCondition` is absent or unused on Success and required in other cases. Its `POIData`, original-transaction echo, copied reversed amount, and `PaymentReceipt` are optional; `POITransactionID` is required only within a supplied `POIData`, and the optional `POIReconciliationID` identifies a Sale–POI reconciliation period when Result is Success. Thus HTTP 200 alone does not prove a successful reversal, and neither a response receipt nor a reconciliation-period ID proves financial settlement or bank receipt. The API Explorer page does not establish authentication/security procedure, callback correlation, async outcome delivery despite listing an `/async` transport URL, deprecation/version migration, or timing/eligibility guarantees. Separately, the captured referenced POS refund guide says `ReversalResponse.Result: Success` acknowledges a refund request and the later `CANCEL_OR_REFUND` webhook gives the outcome; that is guide evidence, not an additional rule stated in this API Explorer table. https://docs.adyen.com/api-explorer/terminal-api/latest/post/reversal; [[source-adyen-api-explorer-terminal-api-latest-post-reversal]] (raw lines 10–19, 59–100).
