## api-explorer-possdk-latest-post-sessions

**Q1. For `possdk/latest/post/sessions`, what captured purpose, API/protocol/version, caller and resource/device/session identity does this page establish, and which required/conditional fields, limits, lifecycle, failure/reversal or timing rules are central?**

The 2026-09-15 API Explorer `POST /sessions` page establishes a mutually authenticated **POS Mobile SDK communication session** with Adyen's payments platform for **mobile in-person** transactions; it expressly cannot create online payments sessions. Its only listed server is `https://checkout-test.adyen.com/checkout/possdk/v68`, so `v68` is the captured endpoint version and the operation page does not list a live endpoint. The raw does not identify the HTTP caller, though it conditionally discusses backend-built Terminal API transactions. The request-body table requires string `merchantAccount` and string `setupToken`, with optional string `store`. The SDK-provided setup token identifies SDK and device; the table names Android `AuthenticationService.authenticate(setupToken)` and iOS `PaymentServiceDelegate.register(with:)` callback routes for obtaining it. The `201 Success` description says a request was fulfilled and one or more resources created. The response table marks each listed property optional: `id` identifies the session, `installationId` the SDK installation, `merchantAccount`, `sdkData` for SDK authentication of platform responses, and `store`. If a backend builds the Terminal API transaction request, use `installationId` as `MessageHeader.POIID`, and pass `sdkData` to the POS app. The page gives no session lifetime, renewal, retry, failure/reversal, timeout or field-size rule; the sample bodies do not change table requiredness.
