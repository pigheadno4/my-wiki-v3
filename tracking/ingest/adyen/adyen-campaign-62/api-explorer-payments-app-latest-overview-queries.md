# C62 fixed query answers: api-explorer-payments-app-latest-overview

## Q1

The captured page identifies **Payments App API v1** as the management API for boarding and managing the separate Adyen Payments App on Android mobile devices. Requests use versioned `management-test.adyen.com/v1` or `management-live.adyen.com/v1` endpoints, with a merchant `{merchantId}` path identity; store-level variants add `{storeId}`, and the revocation path identifies an app instance by `{installationId}`. It lists five routes: POST merchant/store boarding-token creation, GET merchant/store Payments App lists, and POST installation-authentication revocation. The overview gives no request-body required fields, conditional fields, token limits or lifetime, installation/session lifecycle, revocation timing, failure/reversal semantics or payment-processing rules; those require operation-specific evidence. ## Q2

The overview establishes endpoint purpose and API-key transport requirements, not command acceptance or a completed boarding, revocation or payment outcome. Each request must carry a Customer Area API key in `X-API-Key`, and live requests require a key from live Customer Area; no role, fine-grained permission or token-response contract is stated. Versioning is part of the URL and the captured server examples are **v1**. Merchant, store and installation identifiers in paths indicate the target scope, but the page defines no request/result correlation field, asynchronous notification or operation response schema. A listed create/list/revoke path therefore does not prove app installation or authentication state, payment authorization, capture, reconciliation, settlement or bank receipt. There is no deprecation notice in this overview, and `latest` in the canonical path should not be generalized to another version or current device/account availability.
