## Q1. What is this source's purpose and scope, and what cannot be inferred?

It is Adyen's 2026-09-15 method-specific addition guide for an **existing Web Drop-in** integration, with separate Sessions and Advanced flow instructions (primary raw `raw/adyen/docs/payment-methods/pad/web-drop-in/2026-09-15.md:15-25,181-189`; canonical source stem `source-adyen-docs-payment-methods-pad-web-drop-in`). It is not an end-to-end Drop-in setup, an enabled merchant/account eligibility confirmation, proof that a mandate has actually been obtained, or evidence of settled funds. Support must add PAD Canada in Customer Area, and the page requires a way to obtain mandate consent (`:29-37,185-193,397-399`). Its Advanced example `Authorised` response is illustrative while the page states bank authorization can take up to five business days (`:298-330`). For merchant-held agreement details, follow the approved PAD overview `source-adyen-docs-payment-methods-pad`; do not infer them from an API response field alone.

## Q2. What are the central capability, prerequisites and warnings?

Both flows require matching existing Web Drop-in integration, Checkout API **v69+**, notice-of-change webhook, Support enablement and a mandate acquisition route (`:25-37,181-193`). Sessions has no PAD-specific Drop-in config; it lists optional billing and tokenization fields in `/sessions` (`:39-68`). Advanced optionally imports `PreAuthorizedDebitCanada`; Web **v5.24.0+** `enableStoreDetails` controls the save-details checkbox and defaults false; its `/payments` table requires type `eft_directdebit_CA` plus account, five-digit branch, three-digit bank and owner-name fields (`:195-245`). The v71/v72 test endpoints in examples do not revise the stated v69 minimum (`:34,73,190,252`). Both curl examples omit a continuation after `-X POST`, so their `-d` lines are detached as printed (`:72-99,251-284`). Both show `storePaymentMethod` as JSON string `"true"`, and the Advanced request shows `amount.value` as string `"1000"` although its response uses a number; these are illustrative examples, so consult the linked Checkout API for request types (`:98,260,283,304`). PAD recurring supports tokenization but requires shopper mandate; the page discourages one-off PAD because of chargeback risk (`:108-125,287-296,328-345`). Bank authorization can take up to five business days, and failures may produce `CHARGEBACK` (`:110,330`). TEST return simulation and reason-code table allow one retry within 30 days for **01/08**, with the other listed codes marked no retry; TEST direct-to-Chargeback behavior is not a live lifecycle claim (`:133-175,353-395`). Live use requires a Support request in live Customer Area (`:397-399`).
