## Q1. What is this source's purpose and scope, and what cannot be inferred?

This 2026-09-15 Adyen page covers **giact gVERIFY account validation** for ACH Direct Debit first consumer WEB payments, with account setup, configurable trigger options, zero-value flows and TEST mappings (primary raw `raw/adyen/docs/payment-methods/ach-direct-debit/verification-with-giact/2026-09-15.md:15-47`; canonical source stem `source-adyen-docs-payment-methods-ach-direct-debit-verification-with-giact`). giact checks a proprietary database and static rules, without real-time bank access (`:19-21`). ## Q2. What are the central capability, prerequisites and warnings?

Setup requires Adyen addendum, Support enablement, one mutually exclusive trigger option, ACH in test Customer Area and bank-verification results in Standard webhook settings (`:23-47`). Consumer ecommerce checks first ecommerce/WEB payments; all ecommerce checks first ecommerce with any SEC; zero amount checks USD 0 independent of interaction/SEC, but its table labels it **API-only** (`:40-47`). Drop-in/Components should retain owner-name collection or collect it manually; API-only collects bank number, routing and owner name itself; failure refuses the attempt (`:49-99`). The zero route also needs checking/savings type for actual Advanced `/payments`, but giact does **not** validate type, and a wire routing number should not be supplied (`:101-126`). The how-to contains both `/sessions` and `/payments` tabs despite the API-only scope; `/sessions` token webhook field names differ between prose and sample, and `/payments` sample contains a templating hint in the JSON key (`:134-215,217-286`).
