## Q2 — What central capability, prerequisites, and warnings are stated?

Sessions requires existing Android Components Sessions, Checkout API v68+, BACS in Customer Area and `shopperEmail` on `/sessions`; Advanced requires existing Android Components Advanced, additional-action handling, BACS setup and `/payments` fields for email, `directdebit_GB`, holder name, account number and sort/routing code (raw lines 25–45, 508–516, 620–632). Both offer Compose/non-Compose `bacs` module paths, `BacsDirectDebitComponent` and optional submit-button visibility (raw lines 341–439, 518–618). For recurring, tokenization and explicit permission are recommended, while the source says advance notice **must** be given when amount or collection date changes under the Direct Debit Guarantee; later token payments use `/payments`, `storedPaymentMethodId`, shopper reference and `ContAuth` (raw lines 441–494, 1008–1061). The `Received` response needs webhook follow-up, and the Direct/voucher action mismatch remains unresolved (raw lines 993–1006, 1061). Test account details and a separate live Customer Area request are stated, but examples are not evidence of a real debit or active merchant account (raw lines 496–506, 1063–1073).
