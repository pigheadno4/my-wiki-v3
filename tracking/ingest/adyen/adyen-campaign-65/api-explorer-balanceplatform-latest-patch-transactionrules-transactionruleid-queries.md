## Q1

For `PATCH /transactionRules/{transactionRuleId}`, the 2026-11-03 captured Balance Platform API reference shows a v2 TEST base (`/bcl/v2`) and an update of the rule identified by required path `transactionRuleId`. The caller supplies a rule configuration for a scoped `entityKey` whose entity can be a balance platform, payment-instrument group, account holder, balance account or payment instrument; `reference` is the caller's rule reference, while the 200 response separately lists a rule `id`. The request table labels `description`, `entityKey`, `interval`, `reference`, `ruleRestrictions` and `type` required, but the introduction expressly allows a status-only payload; nested `interval.type` is required and `entityKey` children are table-optional. For each included restriction, the prose says both `value` and `operation` must be present, but nested rows label `operation` required and `value` optional; that conflict does not establish that omitting `value` is safe. The bypass type is a separate exception requiring an empty `ruleRestrictions` object and an `overridesRule` ID. `requestType` defaults to `authorization` and also lists `authentication`, `tokenization` and `bankTransfer`; `outcomeType` defaults to `hardBlock`. Rolling/sliding duration is conditional and limited to 90 days or equivalent, `score` is required for `scoreBased` and limited to -100 through 100, and `aggregationLevel` defaults to `paymentInstrument` for accumulation rules. The 200 schema returns rule configuration/state, including optional `id`, `status`, scope, restrictions and timing. No LIVE base, account eligibility or caller role is established by this snapshot. ## Q2

The page says a status-only request leaves all other parameters unchanged, while changing another parameter requires sending all existing resource parameters because omitted ones are removed. A returned 200 means the update request succeeded and supplies a rule configuration; it does not show that a rule was evaluated, an authorization or authentication succeeded, a bank transfer moved funds, or a payment was captured, booked or settled. `status` can be active or inactive and `startDate` and `endDate` describe evaluation timing; the table's automatic-active wording explicitly concerns creation and does not establish that supplying `startDate` on PATCH activates an existing rule. The bypass type skips an identified rule for a scoped entity. The reference documents 401 authentication required, 403 insufficient permissions, and 400/422/500 failures; it does not state a credential role, idempotency key, retry guarantee, deletion propagation, approval flow, asynchronous activation timing, reversal or version-conflict contract. Its 422/500 JSON examples refer to payment-instrument operations and cannot be generalized to this PATCH endpoint. The displayed server is TEST and the capture/“latest” URL is a snapshot boundary, not proof of live eligibility, compliance or financial outcome.
