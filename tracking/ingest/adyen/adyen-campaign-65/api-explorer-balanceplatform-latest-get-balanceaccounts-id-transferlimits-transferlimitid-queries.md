## Q1

The 2026-11-03 captured Balance Platform API v2 reference shows `GET /balanceAccounts/{id}/transferLimits/{transferLimitId}` at the TEST `/bcl/v2` server for reading one transfer limit. Both path inputs are required: `id` is the balance-account ID and `transferLimitId` is the limit ID. No query, body, caller credential role or idempotency input is specified in this endpoint snapshot. The 200 response requires `amount.currency`, integer `amount.value` in minor units, returned limit `id`, `limitStatus`, `scope`, `startsAt` and `transferType`; `reference`, `endsAt` and `scaInformation` are optional. Scope distinguishes a per-transfer maximum from a per-day total; transfer type distinguishes instant-priority transfers from all priorities. Status can be active, inactive, pending SCA or scheduled. If `scaInformation` is present, its `status` is required within that object, while `exemption` is optional. The table describes a no-end-date limit as active until a new limit overrides it, but the GET itself sets no limit and specifies no default input. ## Q2

A 200 means the details were returned for the addressed transfer limit. It is readback of configured amount, scope, timing, reported status and optional SCA information, not a new-limit approval, SCA completion, actual enforcement decision, transfer execution, booking, settlement or bank receipt. `pendingSCA` is pending until the user performs SCA; `scheduled` points to a future start, and `notPerformed` can mean failed authentication or an exemption. Those distinct states and the illustrative `active`/`initialLimit`/`notPerformed` response must not be collapsed into current eligibility or compliance proof. The page documents 404 for a missing limit and 422 validation error; it does not specify an authentication scheme, retry/idempotency semantics, change or deletion operation, propagation timing, approval/reversal outcome, version conflict, or live account access. Only a TEST server and a 2026-11-03 snapshot are shown.
