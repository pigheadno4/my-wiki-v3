## Q1

The 2026-11-03 Balance Platform API v2 TEST reference documents `PATCH /registeredDevices/{id}` to validate device authentication data and complete SCA-device registration for a Business Account or Adyen-issued card. Its server is `https://balanceplatform-api-test.adyen.com/bcl/v2`. The required path `id` is the SCA-device ID obtained from a prior `POST /registeredDevices`, not a payment-instrument ID. The request-body table marks `paymentInstrumentId` and `strongCustomerAuthentication` required, and marks nested `strongCustomerAuthentication.sdkOutput` required; the SDK produces that base64-encoded blob. Optional `name` is generated by Adyen when omitted. The table does not separately declare whole-body requiredness, and the page states no query parameters, conditional inputs, limits or idempotency key. A 200 has an optional `success` boolean, described as whether registration was initiated successfully. The page gives no named caller role; 401 and 403 distinguish authentication and permission failures. Source: [[source-adyen-api-explorer-balanceplatform-latest-patch-registereddevices-id]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/patch/registeredDevices/(id); pinned raw lines 5–36, 59–80. The separate product guides identify a server PATCH finalization step: [[source-adyen-docs-business-accounts-register-sca-devices]]; https://docs.adyen.com/business-accounts/register-sca-devices; guide raw lines 451–461; and [[source-adyen-docs-issuing-3d-secure-oob-auth-sdk-register-devices]]; https://docs.adyen.com/issuing/3d-secure/oob-auth-sdk/register-devices; guide raw lines 419–445.

## Q2

The API heading says PATCH completes registration, yet its optional `success` field says whether registration was *initiated* successfully. The Business Accounts and Issuing guides separately require checking for `success: true` after PATCH before describing the device as registered and connected to the payment instrument. A bare 200 or omitted `success` is therefore insufficient evidence of that guide-defined completion; neither this API page nor the guides make it proof that the user completed a later SCA challenge or that a card or funds operation succeeded. The API page lists 400 request, 401 authentication, 403 permission, 422 validation and 500 server failures. Its 422 and 500 examples describe unrelated payment-instrument operations. It states no retry/idempotency, deletion/reversal, association-propagation timing, further asynchronous approval, version/conflict handling, live eligibility, authorization, capture, booking, settlement or bank-receipt result. This pinned TEST capture is a dated reference, not current service or account-state proof.
