# Original query answers: GET /networkTokens/{networkTokenId}

## Q1

The 2026-11-03 snapshot describes the Balance Platform API v2 TEST `GET /networkTokens/{networkTokenId}` operation to return details of one network token. Its sole documented input is a required string path `networkTokenId`, the token's unique identifier; the listed server is `https://balanceplatform-api-test.adyen.com/bcl/v2`. The response's `paymentInstrumentId` names the linked payment instrument, not the path token ID. `200` requires a `token` object, but its children are listed as optional: `brandVariant`, ISO 8601 `creationDate`, `device` (`formFactor`, `osName`, conditionally returned `phone`), `id`, `paymentInstrumentId`, `status` (`active`, `inactive`, `suspended`, `closed`), `tokenLastFour`, `tokenRequestor` (`id`, `name`) and `type` (examples `wallet`, `cof`). The page gives no request body, query parameter, caller identity or general GET role, default, limit or idempotency key. The `device.phone` field alone has a named access condition: a specific but unnamed user role, with availability up to 24 hours after provisioning. [[source-adyen-api-explorer-balanceplatform-latest-get-networktokens-networktokenid]] [API reference](https://docs.adyen.com/api-explorer/balanceplatform/latest/get/networkTokens/(networkTokenId)); verified raw lines 5–41.

## Q2

A `200` establishes that this GET succeeded and returned its required parent `token` object. If the optional `status` field is returned, it reports the token's state; the separate 2026-09-15 Issuing lifecycle guide defines `active` as usable for payments, `inactive` as not yet usable, `suspended` as temporarily disabled and `closed` as permanently deactivated. That guide, rather than this GET schema, supplies the usability meaning. This read operation does not initiate creation, update, deletion, review, approval, activation, reversal, booking or settlement, and neither a `200` nor reported `active` status proves a successful payment authorization, capture or settlement. No idempotency or asynchronous confirmation behavior is specified here. `401` is authentication required, `403` insufficient permission, `422` request validation error and `500` server processing failure. The generic `422` sample talks about changing a payment instrument's `balanceAccountId`, and the `500` sample about creating a payment instrument, so neither should be read as a GET lifecycle event or operation-specific failure rule. Only a TEST v2 server is shown; `latest` in the URL and this dated capture do not prove live availability, current version, account eligibility, a present token state, or an actual payment or bank receipt.
