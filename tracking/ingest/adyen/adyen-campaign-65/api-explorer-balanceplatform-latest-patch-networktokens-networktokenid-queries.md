## Q1

The 2026-11-03 capture documents the Balance Platform API v2 TEST `PATCH /networkTokens/{networkTokenId}` for updating a network token's status; the server is `https://balanceplatform-api-test.adyen.com/bcl/v2`. It names no particular caller, but documents 401 when authentication is required and 403 for insufficient permissions. The required path string `networkTokenId` identifies the network token. The API request-body table marks its only listed field, `status`, optional, with `active`, `suspended`, and `closed` values; `closed` is final. The separate Issuing guide instead marks `status` required. The API path matches the guide's linked operation, but the guide's curl sample uses `/paymentInstruments/{id}/networkTokens/{networkTokenId}`; neither discrepancy is resolved, and the sample path should not replace the documented API operation. No query parameters, other conditional inputs, defaults, limits, or idempotency key are documented by the API page. Its success entry is `202` without response fields or a JSON example. ## Q2

The API reference itself has a `202 Success` heading and tells the caller to check the actual response code, without a success body or final-result method. Separately, the Issuing guide says HTTP 202 with no content means accepted for asynchronous processing and directs readers to webhooks for the final result. Acceptance does not itself establish that the status has propagated, that the token is usable, or that a card payment was authorized, captured, booked, settled, or received. `closed` is expressly final; the API page gives no completion timing, deletion route, rollback, additional approval steps, or version/conflict behavior. Authentication, permission, validation, and server failures are listed as 401, 403, 422, and 500. Its generic 422 and 500 examples concern payment-instrument changes or creation, so they do not prove a network-token-specific failure mechanism. The TEST snapshot and `latest` URL establish neither live availability nor account eligibility.
