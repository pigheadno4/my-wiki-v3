## Q1

The captured `GET /cardorders/{id}/items` is a Balance Platform API v2 TEST reference for reading the item list of a particular card order, served at `https://balanceplatform-api-test.adyen.com/bcl/v2`. The caller needs the card order's unique path `id`; the page names no particular caller role, while its 401 and 403 responses distinguish missing authentication from insufficient permission. Optional query `limit` sets items per page and defaults to 10; optional `offset` starts the returned list and defaults to 0. No maximum, ordering, body, or conditional input is documented. The 200 body requires `data`, `hasNext` and `hasPrevious`. Each item may include balance-platform ID, card-order-item ID, resource ID, payment-instrument ID, creation date, shipping method, and card/PIN delivery objects with optional errors, statuses and tracking numbers. The card status description lists `created`, `rejected`, `processing`, `produced`, `shipped`, `delivered`, `notApplicable` and `unknown`; the nested card status/tracking descriptions instead say PIN delivery, an unresolved label mismatch. It does not create an order, confirm physical delivery or card activation, or establish authorization, capture, booking, settlement or bank receipt. The `shipped` card and `produced` PIN in the success example are sample values, not a guarantee for this or a future order. The page lists 401 authentication required, 403 insufficient permissions, 422 request validation and 500 server failure. Its generic 422 and 500 example details are about changing or creating a payment instrument, so they cannot be applied as card-order-item-specific lifecycle or failure rules. The GET documents no idempotency key, deletion/reversal action, propagation time, asynchronous review or approval, version-conflict behavior, live endpoint or account eligibility. The capture supports only the described TEST snapshot, not current availability.
