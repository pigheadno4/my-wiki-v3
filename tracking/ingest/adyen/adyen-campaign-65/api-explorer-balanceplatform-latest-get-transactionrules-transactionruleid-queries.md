# api-explorer-balanceplatform-latest-get-transactionrules-transactionruleid — original query answers (attempt 1)

Q1: The 2026-11-03-captured Balance Platform API Explorer `latest` page documents `GET /transactionRules/{transactionRuleId}` to return one transaction rule's details; its only listed server is TEST `https://balanceplatform-api-test.adyen.com/bcl/v2`, so the visible server version is v2. The sole listed input is a required string path `transactionRuleId`, the rule's unique ID; no query parameter or request body is specified. The page does not identify a caller role, though its errors include authentication and insufficient-permission cases. A 200 is request success and its top-level `transactionRule` is optional. Inside a returned rule, the schema marks `description`, `entityKey`, `interval`, `reference`, `ruleRestrictions` and rule `type` required, while `id`, `status`, `outcomeType`, dates and other fields are optional. `entityKey.entityType`/`entityReference` scope the rule to a balance platform, payment-instrument group, account holder, balance account or payment instrument, distinct from the path rule ID. The rule types are block list, maximum usage, velocity and bypass; `requestType` defaults to authorization and `outcomeType` to hard block. Rolling/sliding intervals conditionally require duration, limited to 90 days or equivalent, and score-based outcomes require a -100 to 100 score and exclude bank transfers; `enforceSCA` applies only to authentication requests. For accumulation, `aggregationLevel` defaults to payment-instrument level and must be at or below the entity scope. The full restriction/operation list and additional interval defaults are in the raw table. Q2: A 200 establishes successful retrieval under this reference, with an optional rule object; the example's `active` block-list rule is illustrative readback, not proof that a rule was evaluated, a card transaction was blocked, authentication occurred, funds moved, or a payment was booked or settled. This GET page gives no idempotency key, mutation, deletion, propagation guarantee or asynchronous approval/activation contract. Its returned `status` can be active or inactive, `startDate`/`endDate` describe evaluation windows, and rule type/outcome/conditions describe intended configuration rather than a particular transaction result. The schema itself conflicts: `ruleRestrictions` says one or more conditions, but `bypass` requires it empty with `overridesRule`; no valid bypass creation payload follows from this GET alone. The page lists 400 request-understanding, 401 authentication, 403 permission, 422 validation and 500 server errors; generic 422/500 examples concern payment-instrument update/creation and are not specific rule failures.
