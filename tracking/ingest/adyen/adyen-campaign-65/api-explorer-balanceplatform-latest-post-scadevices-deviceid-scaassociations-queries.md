# Original Q1/Q2 — api-explorer-balanceplatform-latest-post-scadevices-deviceid-scaassociations

## Q1

The 2026-11-03-captured Adyen Balance Platform API `/bcl/v2` reference documents `POST /scaDevices/{deviceId}/scaAssociations` on the listed TEST server `https://balanceplatform-api-test.adyen.com/bcl/v2`. It creates associations between one SCA-enabled device and body-listed entities; it names no specific caller role or live server. The required string path `deviceId` identifies the device. The required body `entities` array contains objects whose required `id` identifies the entity and whose required `type` is `accountHolder`, `legalEntity`, or `paymentInstrument`. The single account-holder example does not define an array limit. No query parameter, endpoint-specific default, or idempotency key is specified. A `201` response returns a required `scaAssociations` array; its entries require `entityId`, `entityType`, `scaDeviceId`, and `status` of `active` or `pendingApproval`. ## Q2

A `201` establishes that associations were created and reports their status; it does not guarantee immediate usability. The raw says an association may be `pendingApproval` if the account holder has existing devices. If the entity is configured for a single associated device **and** single-device replacement is enabled for the account, the new association immediately replaces the old one, becomes `active`, and the old device is no longer associated. The reference gives no pending-approval completion procedure or timing and does not establish device-registration completion, subsequent user authentication, transfer approval, payment authorization, booking, settlement, or bank receipt. It lists `400` invalid input, `401` authentication, `403` permissions, `404` device not found, `422` validation, and `500` server failures; it specifies no idempotency, reversal, version/conflict, or broader propagation rule. The `latest` URL and TEST server are this capture’s scope, not current live eligibility.
