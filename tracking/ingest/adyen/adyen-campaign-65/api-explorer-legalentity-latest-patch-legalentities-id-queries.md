# Original query answers: PATCH /legalEntities/{id}

## Q1

The 2026-11-03 snapshot is Legal Entity Management API v4 `PATCH /legalEntities/{id}` for updating the legal entity named by required string path `id`; the listed server is TEST `https://kyc-test.adyen.com/lem/v4`. The operation says a change of legal-entity type must contain only the new `type`, with other information sent separately; sending `entityAssociations` replaces the entire array, and each association item requires `legalEntityId` and relationship `type`. The body table lists optional top-level `capabilities`, `entityAssociations`, `individual`, `organization`, `reference` (maximum 150 characters), `soleProprietorship`, `trust`, `type`, `unincorporatedPartnership` and `verificationPlan` (`upfront` for marketplace upfront verification). Optional parents have conditionally required branches when the matching entity type is used, and nested fields have their own required flags and country/presence rules: individual name/residential address, organization legal name/registered address, sole-proprietorship name/registered address, trust governing-law country/name/registered address/trust subtype, and unincorporated-partnership governing-law country/name/registered address. The optional `x-requested-verification-code` header can use `0_0001` for suberrors in TEST only. Rates are stated as 700 requests/five seconds live, 200/five seconds test, and five failed requests/ten seconds. `200` requires returned legal-entity `id`; other response groups are optional, including capabilities with requested versus allowed settings/status, associations, branch details, `problems`, transfer instruments and verification deadlines. The top-level `type` enum lists only individual/organization/soleProprietorship/trust while an unincorporated-partnership branch says it is required for that omitted type; the page does not reconcile this. ## Q2

A `200` and required legal-entity `id` establish a successful update response, not automatic verification or capability permission. The response schema distinguishes `requested` from `allowed`: it directs readers to `allowed` for capability permission and says Adyen sets it true after successful verification. Capability and supporting-transfer-instrument `verificationStatus` can be `pending`, `invalid`, `valid` or `rejected`; an `allowed` supporting instrument can be usable despite a parent capability being disallowed because other supporting entities failed. Optional `problems` may carry verification errors, and `verificationDeadlines` identify future capability-disallowance consequences if errors remain unresolved. A type change needs its own type-only request; association replacement removes omitted entries, so neither is a harmless partial field update. The TEST-only verification-code header is not live verification. `400`, `401`, `403`, `422` and `500` are listed failures; no idempotency key, version/concurrency-conflict contract or review/approval timing is stated. The labeled `updateLegalEntitySoleProp` response has top-level `type: individual`, so examples must not be treated as type-transition guarantees. The type enum/branch contradiction remains unresolved. This dated TEST capture, including listed live rate limits, does not prove live eligibility, onboarding approval, legal compliance, payment authorization, payout, settlement or bank receipt.
