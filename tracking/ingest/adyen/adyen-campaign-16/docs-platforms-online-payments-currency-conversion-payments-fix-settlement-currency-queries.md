Q1. What is this document's purpose and scope, and what must not be inferred?
A1. It is a dated Adyen Platforms online-payment guide for a pilot flow that fixes a platform user's goods amount in the settlement currency while calculating the customer amount in the processing currency (raw lines 19–24, 47–53). It does not prove current availability, a merchant's entitlement, an actual rate, authorization, final funds movement or payout; the CZK/PLN figures and Checkout v72 sample are illustrative (raw lines 95–151, 234–286, 871–892). Q2. What is the central capability, what prerequisites and consequential warnings apply?
A2. Calculate the processing amount using FX API `/rates/calculate` or the Exchange Rate Report, whose rate includes markup; markup-bearing directional rates are not interchangeable (raw lines 55–91, 153–205). In a payment, customer `amount` is processing currency and user `splits.amount` is settlement currency; multiple settlement splits must sum to goods cost, and mismatch goes to the explicit `Remainder` balance account (raw lines 216–228, 892). The pilot requires the documented checkout integration, account-holder capabilities, webhooks, merchant currency configuration and appropriate API/role access; FX API use additionally requires enablement/Read FX rates, while report use requires a listed Customer Area role (raw lines 19–20, 26–45). The FX table says `exchangeSide=buy` yet the example response shows `sell`; this snapshot cannot resolve that inconsistency (raw lines 79, 86, 136). It does not define a general liable account or quantify FX exposure.
