## Q1 — What is the purpose and scope, and what must not be inferred?

The page is a 2026-09-15 limited-availability Adyen Platforms pilot guide for refunding a converted online payment while booking its FX remainder to the user's balance account (raw lines 15–37). The shopper-side amount remains the original processing-currency amount; the user's settlement-currency debit changes. It does not establish current eligibility, a merchant-of-record, a live rate, a completed refund or shopper receipt. ## Q2 — What capabilities, prerequisites, FX allocation, and warnings are central?

The integration requires online checkout, Checkout credential, webhook handling, three named account-holder capabilities, Support currency setup and prior capture; option 2 additionally needs Balance Platform FX credential, Read FX rates role and FX API enablement (raw lines 39–57). Option 1 reuses original top-level processing-currency and split settlement-currency amounts with a no-amount `Remainder` item naming the user account (69–76). Option 2 calculates a settlement-currency target via `splitRefund`/`sell`; `sourceAmount` is processing currency in minor units, `targetAmount` is the user debit, and `appliedExchangeRate` includes markup (550–581). The adjusted Checkout split sum should match that target; any mismatch goes to the named `Remainder` account (645–661). The examples use PLN/CZK and test Checkout v72, while example `status: received` is not refund finality (585–643, 665–1129). There is no separate partial-refund procedure here. The linked split-refunds source (raw lines 791–795 in its own pinned snapshot) cautions that invalid or closed-holder account targets can instead book to the platform liable balance; the pilot guide's guaranteed-split wording does not establish an actual booked result.
