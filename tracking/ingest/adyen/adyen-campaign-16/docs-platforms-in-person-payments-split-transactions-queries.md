Q1. What is this page for, and how do store profiles and request splits interact?
A. This 2024-modified, 2026-09-15-captured Adyen for Platforms POS overview routes booking of transaction amounts and fees across user and platform liable balance accounts. Automatic split profiles can apply per store; a specific API request's split instructions override them. With no profile or request instructions, the whole amount and fees go to the liable balance account; an omitted account within a split instruction is a separate liable fallback. Per-request splits require Terminal API with terminal or Mobile integration, and standalone cannot add them to individual payments/refunds. These booking rules do not establish MOR, funds ownership, authorization, or payout. Raw locators: lines 15–38, 110–129; source `## Overview` and `## Key takeaways`. Q2. Which operation uses which split format, and what are this overview's limits?
A. Terminal API payment authorization and referenced-refund requests carry form-encoded key-value or Base64 JSON instructions in `SaleToAcquirerData`; a Checkout `/payments/{paymentPspReference}/captures` request uses the authorization PSP reference and a `splits` array. The page lists payment sale/commission/fee/top-up, refund sale/commission/fee, and chargeback disputed-amount/fee purposes; the chargeback tab does not specify an in-person request flow. The split-type table gives required fields, notably account/amount/reference for `BalanceAccount` and amount for `Commission`. Its generic Split types paragraph says SaleToAcquirerData, but capture-specific instructions say `splits`. This overview does not specify currency units, partial rules, or event/booking proof; follow the linked operation guides and current contracts.
