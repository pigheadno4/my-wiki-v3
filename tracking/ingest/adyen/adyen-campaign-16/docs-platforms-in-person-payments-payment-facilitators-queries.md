# Fixed retrieval checks — Platforms in-person payment facilitators

Q1. What is this source's purpose and scope, and what must not be inferred?
- Expected: A 2026-09-15 Adyen for Platforms guide to additional user/sub-merchant data required by card schemes for **in-person transactions facilitated by a payment facilitator**. It says the user is considered Merchant of Record **when a transaction is facilitated by the platform**; this is conditional transaction scope, not a universal platform architecture, contract, seller/payee determination, or funds-flow rule. Adyen adds some data and the facilitator supplies the rest. The guide does not prove current account or scheme eligibility, exact data transmission, authorization, capture, split booking, payout, or bank receipt.

Q2. Which channel, credential, field, precedence and encoding boundaries govern the user data?
- Expected: The guide covers Terminal API with payment terminals or Mobile and standalone terminals. Standalone must use Management API store `subMerchantData`; integrated terminals can use store, request or both, and request data overrides store data. Store updates require Management API—Stores read and write; the store table marks email/id/mcc/name required, gives `subMerchantData.id` a 15-character alphanumeric limit, and says the name may overwrite part of the bank-statement description. Request data belongs to Terminal API payment and referenced/unreferenced refund requests; non-Terminal-API manual captures and authorization adjustments use the initial payment data. The request table describes `subMerchantId`, city, ISO alpha-3 country, name, postal code, street, tax ID and MCC, without marking requiredness; request `subMerchantId` has a distinct 19-character limit. Encode `additionalData` JSON to Base64 in `SaleData.SaleToAcquirerData`; with split instructions, all user and split data must be in that same JSON/Base64 form because concatenated key-value pairs cannot pass user data. The response does not echo user data. SDK/test snippets are versioned examples and some are incomplete; the combined JSON shows USD while its Base64 sample decodes to EUR, so examples do not validate a single transaction or booking.
