# Fixed retrieval checks — In-person split payments at authorization

## Q1. What is this page for, what is in scope, and what should not be inferred?

The 2023-modified, 2026-09-15-captured guide explains supplying split instructions in each Adyen for Platforms in-person Terminal API payment request at authorization. It covers formatting, currency/amount units, account and fee targets, and checking split bookings via webhooks. Standalone mode excludes per-request authorization splits. It does not prove a real payment or payout, current terminal/payment-method eligibility, legal ownership or merchant of record, and it does not specify a universal partial-capture rule. ## Q2. What is the central capability, prerequisites, and material warnings?

A Terminal API integration with terminals or mobile solution plus general Platforms in-person requirements is needed; standalone cannot add these per-payment splits. Send Split API 1 instructions as one SaleToAcquirerData string, form-encoded or Base64 JSON. Split totals use minor units and known item amounts sum to total, while Terminal AmountsReq.RequestedAmount uses decimal major units; the dated example specifies ProtocolVersion 3.0. BalanceAccount needs a target balanceAccountID and reference; Commission books to liable without account. Tip/Surcharge can be included at authorization; unspecified fees book to liable, so PaymentFee or another fee type is recommended rather than universally required. Format validation does not validate balance-account existence/holder status: nonexistent or closed-holder target sends the full transaction and fees to liable. PaymentResponse Success is not per-split proof; track Transfer/Transaction webhooks. Capture-time splits can override authorization splits, but initial splits are recommended because some methods cannot delay capture. Request and webhook fee-account IDs conflict in the test example, so do not infer a fixed allocation from them.
