Q2. What are the central split-refund steps, prerequisites and warnings?
A. Use the original terminal payment TransactionID/UTC TimeStamp and original split-item references; refund deductions can target only accounts credited by that payment. Put key-value or Base64 JSON split instructions in SaleToAcquirerData. A partial reversal includes original-currency `currency`, decimal-major-unit `ReversedAmount`, and SaleTransactionID reference/UTC timestamp; a full referenced reversal can omit separate currency and ReversedAmount. Use Service/Reversal ProtocolVersion 3.0 and MerchantCancel, then await CANCEL_OR_REFUND for outcome. The transfer and transaction webhook payload examples are explicitly based on an online refund request (line 325); their outgoing debit stages and identifiers illustrate balance-platform booking, not an observed Terminal reversal trace. The fund-tracking prose says credited while examples show outgoing deductions, and the commission transaction example names user-account IDs despite its liable-account narrative. The Terminal response table calls `POIData.POITransactionID.TransactionID` a refund PSP reference, but its displayed value (`TF995R5G6L2GWR82`) differs from `AdditionalResponse.pspReference` (`KHLWK3Z3FZTQ7RT5`); the online-derived webhook examples use a third `modificationPspReference` (`QFQTPCQ8HXSKGK82`). These sample values do not establish one-to-one refund matching or a definitive field; reconcile actual event payloads with the relevant current API and webhook contracts.
