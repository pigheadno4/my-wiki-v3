# Fixed retrieval checks — Refund with original split ratio

## Q1. What is this page for, what is in scope, and what should not be inferred?

The 2024-modified, 2026-09-15-captured Platforms POS guide describes a referenced Terminal API reversal without new split instructions when the intended account allocation is the same as the original payment request. Its worked request is a full refund. It does not define partial-refund proportional math, a later capture-override inheritance rule, fallback for invalid balance accounts, merchant-of-record identity, or a completed refund from the request alone. ## Q2. What is the central capability, prerequisites, and material warnings?

Given the original payment's POIData.POITransactionID TransactionID and TimeStamp, the platform sends a Terminal API Reversal with OriginalPOITransaction, ReversalReason MerchantCancel and no new splits, under the general in-person Terminal/mobile prerequisites. The dated example uses ProtocolVersion 3.0. ReversalResponse Success only acknowledges receipt; the receipt says REFUND REQUESTED and AdditionalResponse amounts are minor units. Wait for CANCEL_OR_REFUND for the asynchronous refund outcome, then trace per-split Transfer/Transaction webhooks for the illustrated sale and commission stages. The prose describes a user sale-share debit and liable-account commission debit, but its commission transaction.created example names the first user balance account, while the commission transfer names the liable account. The initial commission received mutation is -7500 despite the USD 10 amount. The full USD 188 request also does not reconcile cleanly with later USD 75 sale and USD 10/5 commission samples. Fee prose variously points to an account 'specified in the request' and the liable account; fee transfers name a second user account, while fee transaction.created names the first. These conflicting test snippets do not establish the booked account, exact ledger amount, definitive fee-account rule or partial formula.
