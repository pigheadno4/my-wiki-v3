Q1: What is this page for, what scope does it cover, and what must it not prove?
A: A dated Adyen SFTP `AuthoriseReferral` Modification request schema for MOTO transactions declined with Referral where the shopper contacts the issuer and an authorisation code is obtained. It describes a conditional `Authorised` journal entry only after Adyen receives and processes the file; mere submission, ACK, or a sample row does not establish approval, capture, settlement, or a retry decision. The page's “bank transfer authorisation request” sentence conflicts with its title/narrative/example. Q2: Which input fields, prerequisites, and warnings matter?
A: `PaymentDetails` and `AuthoriseReferral` are mandatory sub-lines. PaymentDetails fields 4–6 are amount, currency exponent and ISO currency; empty optional positions need commas. AuthoriseReferral field 4 is the original payment PSP reference and field 5 the authCode received for the transaction. The TEST example uses Modification/`AuthoriseReferral` with `SL,1` PaymentDetails and `SL,2` AuthoriseReferral. The source does not define ACK/result or capture finality, and its bank-transfer wording at line 26 remains unresolved.
