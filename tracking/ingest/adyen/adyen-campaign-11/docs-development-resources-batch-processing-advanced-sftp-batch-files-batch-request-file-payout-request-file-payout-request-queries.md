Q1 — purpose, scope, and non-inference

Question: What does this batch Payout request page define, and what financial conclusion cannot be drawn from a completed request row?
Answer: It defines the `SL` sub-lines used with a Payout line in an SFTP batch request: `PayoutDetails` and `Recurring` plus one destination sub-line (`Card`, `BankAccount`, or `IBAN`). The parent Payout request file page defines the surrounding `L` metadata. This schema and its TEST examples do not show file validation, payout authorization, beneficiary credit, settlement, or safe retry. Q2 — central fields, permission, destination and warnings

Question: Which fields and permission matter for a payout request, and where do the examples need caution?
Answer: `PayoutDetails` has separate required amount, currency exponent, ISO currency code, shopper reference/email/birth date, entity type, and nationality. The raw example's `1000,2,EUR` maps to those three fields; do not infer a universal payout amount unit beyond the table. `Recurring` requires `PAYOUT` and table value `Latest`. The destination is a card, bank-account or IBAN sub-line; the page says a role with permission to store payout details is needed. The Card table requires PAN, expiry, CVC and holder name; BankAccount requires owner/country/account and other bank fields; IBAN requires owner/country/IBAN, optional BIC, and has owner-name error 203. Sensitive card and identity fields warrant careful handling. The examples differ from tables: `LATEST` versus `Latest`; the Card row lacks a separate CVC-position field; and the BankAccount sample puts numeric `20010020`, multiword `Postbank Stockholm`, and `Hameln` where the table requires two-letter alphabetic bank-location and bank-name fields and describes an optional two-letter check code. Do not treat the BankAccount sample as a validated payout row; follow the table and confirm accepted format with Adyen. Raw: same pinned page, lines 20–48, 50–83, 85–116, 118–146.
