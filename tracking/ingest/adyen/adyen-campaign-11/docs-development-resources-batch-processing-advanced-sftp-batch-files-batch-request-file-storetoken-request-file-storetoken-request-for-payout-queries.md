# Fixed-query probes — Adyen batch StoreToken request for payout

## Q1 — purpose, scope, and non-inference

**Question:** What is the StoreToken request for payout page, and what does sending that record not prove?

**Answer:** This 2019-last-modified Adyen reference describes sub-lines and fields for a payout-oriented `StoreToken` request in the advanced SFTP batch-file format. It says the request includes mandatory `ShopperDetails` and `Recurring` sub-lines and one `Card`, `BankAccount`, or `IBAN` instrument sub-line. The `Recurring` table uses `PAYOUT,Latest`. It says only payment requests after sending StoreToken are tokenised, but the page does not prove a submitted record was accepted, that a token/alias exists or can be charged, that a beneficiary was verified, or that a payout was instructed or completed. The `TEST` records are examples, not live eligibility or account-scope proof. ## Q2 — capability, prerequisites, and warnings

**Question:** What records, permissions, and field cautions are necessary for this payout-oriented StoreToken request?

**Answer:** The reference requires `ShopperDetails` with shopper reference and email, `Recurring` with fixed `PAYOUT` and `Latest`, and one instrument sub-line: `Card`, `BankAccount`, or `IBAN`. Its fixed-field format requires delimiter commas even when optional values are blank. It says a user role with permission to **store payout details** is needed; it does not identify an exact role or prove that the account has it. The card table says to leave CVC blank. The IBAN owner name must have at least three characters and not be all digits, with error 203 for invalid format; invalid ISO alpha-2 country codes cause request rejection in the bank and IBAN descriptions. Card/bank identifiers, shopper email and holder details are sensitive. Valid-looking fields, file upload or an ACK are not proof of token availability, beneficiary validation, payment or payout success.
