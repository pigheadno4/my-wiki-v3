# Fixed retrieval checks — AccountUpdater SFTP request file

## Q1 — What is this page for, what is its scope, and what should not be inferred?

The 2019-modified Adyen page, captured 2026-09-15, defines the SFTP AccountUpdater **request-file** `L` record and its Recurring or Single `SL` records. It is not the result-file status table; a submitted or validated request does not prove changed card data, changed stored credentials, or a successful financial transaction. ## Q2 — What is the central identity/data choice, prerequisite, and warning?

The required `L` record names the merchant account and transaction-specific merchant reference (raw lines 18–30). Recurring `SL` is for unavailable shopper payment details; the page says this request type stores shopper payment details in a recurring contract (line 39). Its input uses a shopper reference plus a card alias when not stored, or a stored recurring detail reference/`LATEST` when stored (lines 32–59). That stated purpose and submitted request do not prove an issuer update or changed Adyen stored-card details; the related Batch Account Updater workflow says changed details in an Adyen token need a later payment-request update. Single `SL` is for at least partially available card details and requires number or alias, expiry, and cardholder name; CVC is to be left blank and Maestro UK fields are optional (lines 72–94). Live/actual PAN in the file requires PGP encryption before submission (line 76). The email-shaped shopper reference and card number in examples are illustrations, not validation or processing outcomes (lines 61–70, 96–105). Consult the common request-file schema, ACK, and AccountUpdater result source through the same concept route for file and outcome stages.
