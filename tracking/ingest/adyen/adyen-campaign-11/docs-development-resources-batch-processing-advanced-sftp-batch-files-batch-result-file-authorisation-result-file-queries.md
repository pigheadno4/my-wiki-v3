# Fixed retrieval checks — SFTP Authorisation result file

## Q1 — What is this page for, what is its scope, and what should not be inferred?

This 2019-modified page captured 2026-09-15 defines the `L` and `PaymentResult` `SL` records in an Adyen SFTP Authorisation result file. It routes parsing/validation errors to another result-file structure. It is per-transaction authorization-result schema, not a file-upload ACK, capture/settlement status, stored-credential consent record, or a guarantee that a particular transaction succeeded. ## Q2 — What fields identify the result, and what warnings govern interpretation?

The `L` record identifies the merchant account, merchant reference and transaction status; the enumerated statuses include `Success`, `Authorised`, `Refused`, `Cancelled`, `Received` and `Error` (raw lines 22–36). The `PaymentResult` sub-line separately identifies the original payment PSP reference, an authorization code only for successful authorization, an optional-if-available result code, and refusal/error reason (raw lines 40–75). The example uses matching-looking merchant and PSP values but the columns have different identities (raw lines 82–85). `Received` is not defined as authorized; even `Authorised` says nothing here about capture or settlement. The long reason list contains recurring-related text but the documented result has no Recurring sub-line or consent claim. For parsing/validation errors follow raw line 16's alternate route; for batch ACK versus result stages use the linked sources from `[[adyen-batch-processing]]`.
