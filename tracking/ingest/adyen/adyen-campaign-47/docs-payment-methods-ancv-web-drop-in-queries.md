## Q2 — How do await, partial authorization and setup work?

Use the root/provider/concept route through `[[source-adyen-docs-payment-methods-ancv-web-drop-in]]` and its pinned child raw `raw/adyen/docs/payment-methods/ancv/web-drop-in/2026-09-15.md`; also follow `[[source-adyen-docs-payment-methods-ancv]]` to overview pinned raw `raw/adyen/docs/payment-methods/ancv/2026-09-15.md` lines 25 and 33–39 for method-level prerequisites. Sessions adds no ANCV-specific `/sessions` parameters; Advanced requires `paymentMethod.type=ancv` and beneficiaryId, with an `await` action (raw lines 39–53, 137–166). `/payments` returns Pending and `action.paymentData`; use that in `/payments/details`, and use details' `order.orderData` rather than the initial response's value (lines 538–645). Customer Area can show requested rather than actually authorized amount; details and AUTHORISATION webhook carry authorized value (lines 91–123, 678–710). The partial examples disagree: 3000 request, 2400 authorized with 2500 order/100 remaining, and webhook authorized 2500; sample JSON has missing commas (lines 173–194, 592–612, 678–710). The separate ANCV overview says merchants must contract directly with ANCV (which handles settlement/reporting while Adyen is gateway) and must use Adyen's partial-payments feature for shopper partial authorization (overview raw lines 25, 33–39). These are overview requirements, not claims from the child raw. Testing needs ANCV-supplied app credentials and partial-payment checks; live Customer Area setup needs ANCV Merchant ID/shopID (child raw lines 125–131, 712–718). The Advanced base link has an unresolved platform template (line 141).
