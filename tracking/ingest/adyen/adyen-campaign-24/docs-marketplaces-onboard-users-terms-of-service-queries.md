# docs-marketplaces-onboard-users-terms-of-service — retrieval checks

Q1. How does a marketplace with its own onboarding UI arrange Adyen Terms of Service acceptance, and what must exist first?

The guide requires an Adyen for Platforms integration, Legal Entity Management API credentials, webhooks, and legal entities for the contractual user plus individual accepter (raw lines 30–42). The platform detects a requirement in `balancePlatform.accountHolder.updated` `verificationErrors` (lines 55–59), GETs the required types for the main legal entity (lines 109–115), generates and presents the document (lines 127–156, 333–381), and after user acceptance PATCHes the generated document ID with required `acceptedBy` individual ID (lines 383–394). Hosted onboarding incorporates this step itself (line 21). Q2. Which actor, document and environment distinctions prevent using a TEST sample or a generated document as proof of acceptance?

An individual legal entity must accept; an organization uses an authorized signatory (raw lines 23–28). The GET uses the main entity ID (owner's individual ID for a sole proprietorship), and a user may need multiple documents (lines 109–115, 357–361). TEST returns only default `adyenForPlatformsAdvanced` regardless of actual integration, whereas LIVE returns actual types (line 115). POST generation and presentation precede the distinct acceptance PATCH; that PATCH uses the main entity plus `termsOfServiceDocumentId` in the path and the individual ID in `acceptedBy` (lines 383–394). An optional acceptance-info GET exposes `acceptedBy` and `acceptedFor` records (lines 619–788). Neither examples nor a document-generation response proves that a real user accepted or that KYC/capabilities are approved.
