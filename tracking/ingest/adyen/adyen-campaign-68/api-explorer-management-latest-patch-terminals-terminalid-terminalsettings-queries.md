# C68 terminal-specific settings PATCH query answers

## Q1

The 2026-11-07 Adyen Management API `latest` capture describes `PATCH /terminals/{terminalId}/terminalSettings`, which updates settings on the uniquely identified payment terminal. It lists the Test `/v3` server and warns that Live requests face rate limits. The caller's API credential needs `Management API—Terminal settings read and write`; sensitive settings additionally require `Management API—Terminal settings Advanced read and write`. `terminalId` is a required path parameter. The request-body table marks its top-level settings objects optional. To change a value, the caller includes the full containing object; to restore higher-level inheritance, include the containing object with an empty or omitted parameter; absent objects are not updated. Nested requirements still matter: each Wi-Fi profile has required `authType`, `bssType`, `ssid` and `wsec`; `hiddenSsid`, despite a `No` table flag, is described as mandatory for Android terminals. Store-and-forward `maxAmount`, `maxPayments` and `supportedCardTypes` must be configured in the request or inherited. The raw has detailed fields for receipts, connectivity, DCC, tipping, passcodes, payment, refunds, standalone, surcharge and Wi-Fi. `resetTotalsHour` and `restartHour` default to 6:00 AM in the terminal's timezone and allow 0–23. A `200` response provides an optional-field settings representation. See [[source-adyen-api-explorer-management-latest-patch-terminals-terminalid-terminalsettings]] and [the captured operation](https://docs.adyen.com/api-explorer/Management/latest/patch/terminals/(terminalId)/terminalSettings), raw lines 5–56, 95–196, 289–454.

## Q2

A `200` response establishes that the settings update request succeeded and may return a settings representation; it does not prove the terminal has received or applied the configuration, is boarded or payment-ready, passed a compliance check, or processed a transaction. This PATCH can change existing configuration or restore an inherited value under the full-containing-object rule; it is not a terminal deletion, payment/refund execution or financial settlement. The operation lists `400` request problem, `401` authentication required, `403` insufficient permission, `422` validation error and `500` server error; it specifies no idempotency key, asynchronous approval state, reversal flow or universal propagation time. The Advanced role gates sensitive settings, and Live rate limits and the Test v3 snapshot limit any current-access inference. Consequential settings have their own caveats: DCC compliance responsibility, Adyen contact before first contactless-currency change, unreferenced-refund loss liability, standalone/MOTO coupling, and store-and-forward inherited-or-requested prerequisites. The PEAP example includes `eapIntermediateCert`, although the field text says TLS, so it cannot establish PEAP acceptance. See [[source-adyen-api-explorer-management-latest-patch-terminals-terminalid-terminalsettings]] and [the captured operation](https://docs.adyen.com/api-explorer/Management/latest/patch/terminals/(terminalId)/terminalSettings), raw lines 7–26, 46–47, 68–70, 104–105, 130–145, 181–222, 289–554, 630–650.
