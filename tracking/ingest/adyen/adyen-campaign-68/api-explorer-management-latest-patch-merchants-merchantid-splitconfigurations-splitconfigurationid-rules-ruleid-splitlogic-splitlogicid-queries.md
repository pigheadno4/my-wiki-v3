## Q1

The 2026-11-07 Management API `PATCH /merchants/{merchantId}/splitConfigurations/{splitConfigurationId}/rules/{ruleId}/splitLogic/{splitLogicId}` changes the split logic selected by all four required path IDs: merchant account, configuration, rule, and split logic respectively. Its listed server is TEST `/v3`, and the API credential needs `Management API - SplitConfiguration read and write` (raw lines 5–24). The request body requires `commission`, which can use fixed minor units, variable basis points, or both, and is booked to the platform's liable balance account. Other listed allocation fields are optional; additional commission can name a balance account. DCC allocation is a pilot unavailable to some platforms (lines 27–52). If no transaction fee type is included in `splitLogic`, the documented fallback uses `paymentFee` to book all transaction fees to the platform's liable balance account (line 46). A `200` returns a split configuration with required `description` and `rules`, including rule conditions and split logic; `204` has no additional content (lines 74–114). The 200 response table calls for a three-character ISO rule currency, while the 200 example uses `ANY`; this capture does not settle whether `ANY` is accepted (lines 86, 226). The `200` response means the update request succeeded and describes a split configuration; `204` means successfully processed without content (raw lines 74–114). Neither proves that a particular payment matched a rule, had its fees booked, was captured, settled, or paid out.
