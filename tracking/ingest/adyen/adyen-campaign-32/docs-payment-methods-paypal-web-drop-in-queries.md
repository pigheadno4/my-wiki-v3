Q1. What does this guide add and what must be in place first? The server branches are default v5.0.0+ `/sessions` versus additional-use-case `/payments` (38–40, 516–528); conditional risk and client configuration are at 1041–1274. Q2. Does a synchronous `Authorised`, token request, or refund example prove a completed payment/refund? No. The page says `resultCode` is not final and directs order decisions to `AUTHORISATION` webhooks, with optional `OFFER_CLOSED` enablement (raw lines 1276–1303). A zero-value `/payments` request without required client configuration creates no token (1329–1366); token receipt uses `recurring.token.created` (1372–1379). A delayed-capture partial refund needs its capture reference under the detailed three conditions, and the sample refund status is only `received` (1442–1452, 1473–1491). The broader summary and mismatched illustrative order/refund amounts/items require caution (59–84, 1392–1408, 1412–1442).
