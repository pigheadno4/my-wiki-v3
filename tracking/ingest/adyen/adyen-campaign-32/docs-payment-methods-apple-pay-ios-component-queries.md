# Apple Pay iOS Component retrieval checks

Q1. What must exist before adding Apple Pay here, and which flow/version is covered? This is an add-on to an existing iOS Components Sessions or Advanced integration, with the merchant's own Apple Pay certificate and Apple Pay added in Customer Area (pinned raw lines 15–41). Sessions `/sessions` is the v5.0.0+ default; `/payments` is the additional-use-case route (lines 43–48). The client configuration differs across v5.3.0+, v5.0.0–v5.2.0 and the v4.10.0-or-earlier example (lines 52–147). Q2. Does showing Apple Pay or setting `PKRecurringPaymentRequest` prove live acceptance or recurring success? No. `allowOnboarding` changes wallet-card availability display but does not authorize payment (pinned raw lines 149–168). Recurring use needs `PKRecurringPaymentRequest` plus separate token creation and later token transactions (lines 169–179). Live use calls for API Clientside Encryption Payments role and merchant Apple Developer setup for its live identifier (lines 189–193); the guide provides no observed authorization, capture, settlement or token success. The v5.3 table names merchantIdentifier but its sample does not pass one explicitly, and the v4 Component section assigns to a Drop-in configuration (lines 58–80, 112–147), so samples need version review.
