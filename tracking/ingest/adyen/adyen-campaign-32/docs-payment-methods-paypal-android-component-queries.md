# C32 retrieval checks: PayPal Android Redirect Component

Q1. What is the flow and what setup and request conditions precede it?

The guide adds PayPal Redirect Component to an existing Android Components integration after PayPal setup (raw lines 15–26). Discover `paypal` via `/paymentMethods` for a supported country/currency and minor-unit amount (raw lines 28–38). The server uses `/payments` with `paymentMethod.type: paypal`, Android/return URL guidance and conditional line-item, Magnes and `paypalRisk` fields (raw lines 42–139); it passes redirect `action` to Android, then sends the returned Component details to `/payments/details` (raw lines 649–710). Q2. Which outcome, recurring and refund limits matter?

Synchronous `resultCode` is not final; AUTHORISATION webhooks resolve outcome, and OFFER_CLOSED requires opt-in (raw lines 714–750). Recurring requires PayPal Reference Transactions and permissions plus token webhooks; zero-value token creation alone has a special `shopperEmail` condition, and later charges use webhook `storedPaymentMethodId` with `ContAuth` (raw lines 753–810). Cancel before capture versus refund after it; a later-capture partial refund needs the **capture** PSP reference under the stated three conditions (raw lines 812–819, 897–915). Test samples and a `received` refund response do not prove capture, settlement or returned funds. The `/payments` field table directs `channel: Android` and `returnUrl` from `RedirectComponent.getReturnUrl(context)` (raw lines 133–134), but every shown request example omits `channel` and uses a fixed generic HTTPS return URL (for example raw lines 154–160, 301, 374, 406, 488, 522, 644); those URLs are not established to return to the Android Component. Keep the table guidance primary. PHP/Python/Ruby snippets also have field/encoding problems (raw lines 286–302, 530–541, 580–589, 821–895).
