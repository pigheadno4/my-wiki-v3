# Google Pay Web Component retrieval checks

Q1. What does the guide require and which flow/version is being configured? It adds Google Pay to an existing Web Components integration after Google Web setup and Adyen Customer Area method addition (pinned raw lines 19–29). `/sessions` is the default at Components v5.0.0+, while `/payments` is the linked additional-use-case path (31–36); v6+ constructs `new GooglePay(checkout,...)`, v5.x.x or earlier uses `checkout.create('googlepay',...)`, and mounting waits for `isAvailable()` (68–157). The direct-payment configuration has required amount/currency/country/environment and conditional native-3DS fields (94–105). Q2. Do client availability, test cards or Google sheet approval prove live authorization, and is the optional event example complete? No. `isAvailable()` gates mounting only (pinned raw lines 144–157). The table's Authorize Payments note calls for `onAuthorize`, but its event list has `onAuthorized` instead (229–251); preserve the naming gap. TEST suite DPAN is restricted to native Android/Chrome Android, non-suite real wallet cards map to Adyen test cards, and that path's 3DS2 fixtures use Amex/Discover (279–303). LIVE additionally needs the credential role, Google Merchant ID/production access and a logged-in shopper with a valid method (305–317); this is not payment/capture/settlement proof.
