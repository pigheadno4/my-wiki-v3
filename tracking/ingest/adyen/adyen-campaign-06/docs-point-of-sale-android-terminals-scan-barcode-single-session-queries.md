**Q1: Which terminals can use the single-scan Terminal API flow, and what must the POS implement?** Adyen's guide names S1E Barcode, S1E2L, S1F2L, and S1U2 Android payment terminals with barcode scanners. It requires a Terminal API integration plus POS-app logic to trigger a scan and process returned content. The terminal's Customer Area scanning-button setup is unnecessary for this method. A separate batch session covers multiple scans. **Q2: How does one scan start and end, and which example values are unsafe to copy?** The guide's parameter table calls for JSON containing a unique session ID, `Session.Type: Once`, `Operation.Type: ScanBarcode`, and `TimeoutMs` of 0–30000; Base64-encode that JSON and put the encoded string in `AdminRequest.ServiceIdentification` in a Terminal API Service/Admin request with protocol 3.0. On success, `AdminResponse.Response.AdditionalResponse` carries barcode data and symbology after decoding; the guide warns its format can be Base64 or URL encoded. A separate Admin request with the session ID and `Session.Type: End` cancels before timeout. The full activation example's embedded Base64 decodes to `Begin`, contradicting `Once`; its `ServiceID` exceeds the stated 1–10 characters, response headers swap identifiers, and the cancel response uses a V400m `POIID` outside the named scanner models. These are scanner-control results, not payment outcomes.
