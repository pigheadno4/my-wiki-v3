# C67 api-explorer-management-latest-patch-companies-companyid-terminalorders-orderid — original query answers

## Q1

The 2026-11-05 captured **Management API v3** reference uses `PATCH /companies/{companyId}/terminalOrders/{orderId}` to update the identified terminal products order under a company account. The listed server is TEST, `https://management-test.adyen.com/v3`; live requests are noted as rate limited without a numeric limit. The API credential must have **Management API—Terminal ordering read and write**. Required string path parameters are the company and order IDs. Updates are permitted only while order status is `Placed`. The body may include only changed fields, but a change to `items` requires the whole replacement array. The schema marks `billingEntityId`, `customerOrderReference`, `items` and item subfields, `orderType`, `shippingLocationId`, and `taxId` optional. It notes that Brazil product orders do not need `billingEntityId` and gives no body defaults. The `200` response has optional order ID, status, items, order date, billing entity and shipping location details, customer reference and tracking URL. ## Q2

HTTP `200` reports request success and returns order details; its `Placed` example remains an illustrative order state, not proof of fulfillment, shipment, inventory, hardware arrival, terminal boarding or payment execution. The decisive lifecycle condition is `Placed` for updates, and submitting `items` replaces the array, so omitted existing products are removed. The page requires the ordering read/write role; errors include `400` request problem, `401` authentication required, `403` insufficient permission, `422` validation error and `500` server failure. It gives no idempotency, propagation timing, asynchronous review/approval/activation, reversal or version-conflict rule. Its dated TEST server listing and live rate-limit notice do not establish current eligibility, real procurement completion, compliance or financial outcome.
