# api-explorer-management-latest-patch-companies-companyid-terminallogos — original query answers

## Q1

The 2026-11-05-captured Management API `latest` reference describes `PATCH /companies/{companyId}/terminalLogos`, which updates the company-level logo for one specified payment-terminal model per call. It lists the TEST server `https://management-test.adyen.com/v3`. The calling API credential needs `Management API—Terminal settings read and write`. Required path string `companyId` identifies the company account; required query string `model` selects a terminal model from the values listed in the raw. The body schema marks `data` optional, while the prose instructs a Base64-encoded image string for a change and an empty logo value to restore the Adyen PSP-level inherited logo. It gives no meaning for omitted `data`. The `200` response has optional `data` image data; the remove example returns an inherited higher-level Base64 string. The company logo applies to terminals of the chosen model unless a merchant, store or terminal override exists. Live requests have rate limits, but no numeric value is supplied here. ## Q2

A `200` establishes a successful configuration request with optional image-data readback. It does not show that the image has reached or appeared on every terminal, especially where a lower-level override exists. Sending an empty `data` value is the documented restoration of the company setting's inherited PSP logo; the page specifies no behavior for an omitted field, no per-device propagation timing, no idempotency or rollback rule, and no review/approval/activation workflow. Authentication and the Terminal settings read/write role gate the call. The listed failures are `400`, `401` authentication required, `403`, `422` and `500`. The page gives a TEST `/v3` server and a Live rate-limit notice, but no current Live URL or numeric rate. The `latest` label and dated snapshot do not establish present eligibility, compliance, device readiness, payment authorization or settlement.
