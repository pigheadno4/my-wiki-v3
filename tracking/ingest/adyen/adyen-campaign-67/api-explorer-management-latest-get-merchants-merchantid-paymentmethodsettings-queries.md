# Original query answers: api-explorer-management-latest-get-merchants-merchantid-paymentmethodsettings

- Q1: The 2026-11-05 snapshot of Management API v3 lists the TEST server for `GET /merchants/{merchantId}/paymentMethodSettings`, which returns all payment method settings for the merchant account named by required `merchantId`. The API credential needs Management API—Payment methods read. Optional `businessLineId` and `storeId` filter results; optional `pageNumber` and `pageSize` paginate, with a default page size of 10 and maximum 100. A 200 response includes optional pagination links and `data`; each method has required resource `id`, while variant `type`, `enabled`, Adyen-screened `allowed`, `verificationStatus`, stores, countries/currencies and method-specific details are optional. The response table marks `data[].businessLineId` No but says it is required for a platform model; this differs from the optional `businessLineId` query filter. Required top-level `itemsTotal` and `pagesTotal` and optional `typesWithErrors` describe the list. [[source-adyen-api-explorer-management-latest-get-merchants-merchantid-paymentmethodsettings]]; https://docs.adyen.com/api-explorer/Management/latest/get/merchants/(merchantId)/paymentMethodSettings; verified raw lines 5–30, 32–78, 104–115, 175–205.
- Q2: A 200 readback establishes only the returned settings/status for this merchant and filters at this captured TEST reference; 204 has no content. `enabled`, `allowed` and `verificationStatus` are distinct fields: `allowed` is true after Adyen screening and verification can be pending, invalid or rejected. The GET documents no idempotency key, change, deletion, propagation, review/approval transition, reversal or payment operation. Its 401/403 errors distinguish authentication and permission, while 400/422, 429 and 500 cover other failure categories. Listing a method does not establish live eligibility, compliance, authorization, capture, settlement or bank receipt; the November snapshot is not current account proof.
