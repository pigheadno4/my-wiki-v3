# C67 api-explorer-management-latest-post-merchants-merchantid-webhooks-webhookid-test — original query answers

## Q1

The 2026-11-05 captured **Management API v3** TEST reference uses `POST /merchants/{merchantId}/webhooks/{webhookId}/test` to send sample notifications for a merchant webhook configuration. The listed server is `https://management-test.adyen.com/v3`; the API credential must have **Management API—Webhooks read and write**. Required string path IDs identify the merchant account and webhook configuration. The request body marks `types` optional, with event codes constrained by webhook `type`, and `notification` optional except **required if `types` contains `CUSTOM`**. If `notification.amount` is included, its ISO `currency` and integer minor-unit `value` are required. Other custom fields include optional `eventCode`, `eventDate`, `merchantReference`, `paymentMethod`, `reason`, and `success`. The page provides no default for omitted `types` or other numeric limits. It says four sample notifications per chosen event code cover success/failure in fixed EUR and GBP regardless of configured currencies; CUSTOM sends only the specified notification. The `200` response optionally contains `data` with a result per test, including required per-element `status` and optional merchant ID, sent body, output, receiver code, and response time in milliseconds; `204` is a separate no-content success. See [[source-adyen-api-explorer-management-latest-post-merchants-merchantid-webhooks-webhookid-test]], [pinned reference](https://docs.adyen.com/api-explorer/Management/latest/post/merchants/(merchantId)/webhooks/(webhookId)/test), raw lines 5–91.

## Q2

For a `200` test result, `data.status=success` means the receiver returned HTTP `2xx`; other receiver responses produce `failed`. The `output` and `responseCode` help troubleshoot, while `204` gives no result body. These describe sample webhook delivery/receiver responses, not real transaction `success`, payment authorization, account eligibility, compliance, production delivery, settlement, or bank receipt. The reference requires the Webhooks read/write role and lists `400`, `401` authentication required, `403` insufficient permission, `422` validation, and `500` server errors. It does not document idempotency, deletion/propagation, asynchronous approval/activation, reversal, or version-conflict handling. Its custom request example sets HUF amount `1000` but the response's `requestSent` has HUF amount `100`, so exact echo cannot be inferred from the examples. This is a dated TEST server snapshot, not current live capability proof.
