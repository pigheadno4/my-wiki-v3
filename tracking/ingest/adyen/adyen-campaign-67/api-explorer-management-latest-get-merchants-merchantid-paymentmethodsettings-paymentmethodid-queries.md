# Original campaign query answers — api-explorer-management-latest-get-merchants-merchantid-paymentmethodsettings-paymentmethodid

## Q1

`GET /merchants/{merchantId}/paymentMethodSettings/{paymentMethodId}` reads details for the merchant account and payment method named by the two required path identifiers: `merchantId` identifies the merchant account and `paymentMethodId` the payment-method resource. The captured Management API reference lists Test `https://management-test.adyen.com/v3` and requires the caller's API credential to have **Management API—Payment methods read**. There is no query parameter or request body in the page. `200` says the request succeeded and its response schema requires `id`; optional `type` is the payment-method variant. Other optional fields include `allowed`, `enabled`, `verificationStatus`, `associatedPaymentMethods`, country/currency/store scopes, `businessLineId`, reference and method-specific objects. The optional `associatedPaymentMethods` array's items require `enabled`, `id`, and `type` within each item. The `businessLineId` response description says required for a platform model despite its table-level optional mark. `allowed` is set true by Adyen after merchant-account screening; `enabled` is the on/off setting; `verificationStatus` can be valid, pending, invalid, or rejected. The broad schema has method-specific defaults and limits rather than a universal GET default: PayPal `directCapture` defaults true, `payerId` specifies 13 single-byte alphanumeric characters, and transaction-description text recommends up to 22 characters because banks may truncate longer text. `204` is also listed as successfully processed with no content. ## Q2

A `200` establishes success of this detail read and supplies whichever configuration/status fields are present, with `id` required by the schema. A `204` establishes successful processing but supplies no additional content; neither status changes a payment method. The optional `allowed` flag reflects Adyen's post-screening permission to receive payments, `enabled` reflects configuration, and `verificationStatus` reports a separate valid/pending/invalid/rejected state. Their presence is not proof of a successful payment, account-wide or current Live eligibility, an authorization, capture, settlement, or bank receipt. The optional associated-method list describes an associated transition already represented in readback; this GET does not trigger it. The documented caller role and 401/403 errors bound authentication and permission; 400/422, 429, and 500 cover other error classes. The captured page states no idempotency mechanism, lifecycle change, deletion, propagation delay, asynchronous approval/activation action, reversal procedure, Live endpoint, or conflict/version rule beyond the listed Test v3 server. Its 2026-11-05 snapshot cannot prove current availability or merchant-specific access.
