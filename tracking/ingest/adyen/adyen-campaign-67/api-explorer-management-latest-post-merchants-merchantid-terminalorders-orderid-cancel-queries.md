# api-explorer-management-latest-post-merchants-merchantid-terminalorders-orderid-cancel — original query answers

## Q1

The 2026-11-05-captured Management API `latest` reference covers `POST /merchants/{merchantId}/terminalOrders/{orderId}/cancel`, cancellation of a terminal-products order under a merchant-account path. It lists the TEST server `https://management-test.adyen.com/v3`. The caller's API credential needs `Management API—Terminal ordering read and write`; `merchantId` is the required merchant-account ID and `orderId` the required order ID. The order must still be `Placed`; the POST has no request body, and no query parameters or defaults are specified. Live requests are rate limited, with no numeric value supplied here. On `200`, the introduction says the full order returns with status `Cancelled`, although the response schema marks `status` and other top-level fields optional. The optional detail schema covers order ID/reference/date, items, billing entity, shipping location and tracking URL, with nested address/contact fields. A separate `204` success has no content or response fields. ## Q2

Cancellation is restricted to an order still `Placed`. A `200` is documented as success and the introduction describes returned order details with `Cancelled` status; a `204` means successful processing without additional content, so it does not provide order-state readback. Neither status establishes shipment interception, inventory restoration, a payment reversal/refund, terminal boarding, or financial settlement. The reference provides no idempotency, undo, downstream propagation or fulfillment timing, and no asynchronous review/approval/activation workflow. Authentication and the terminal-ordering read/write role gate the call; documented failures are `400`, `401`, `403`, `422` and `500`. It lists a TEST `/v3` server and a Live rate-limit notice, but no Live endpoint or current limit; the `latest` label and dated capture do not prove present eligibility or compliance.
