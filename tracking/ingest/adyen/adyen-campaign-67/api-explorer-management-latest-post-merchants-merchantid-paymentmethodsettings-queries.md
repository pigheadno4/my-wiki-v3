# Original query answers — api-explorer-management-latest-post-merchants-merchantid-paymentmethodsettings

Q1. The 2026-11-05-captured Management API v3 TEST `POST /merchants/{merchantId}/paymentMethodSettings` requests adding a payment method to the required merchant-account path ID. The caller needs `Management API—Payment methods read and write`. Request body `type` (variant) is required; method-specific parent objects are table-optional but their children and prose conditions can require data for the chosen method or region. `businessLineId` is required for platform models; `shopperInteraction` is required if the account lacks a sales channel or `type=alipay`. Optional country/currency lists default to all supported, and optional `storeIds` selects stores. Apple Pay allows at most 99 domains per request; PayPal `directCapture` defaults true. The 200 response requires resource `id` and can include `allowed`, `enabled`, `verificationStatus`, and associated method transitions; 204 has no content. Q2. A successful response means the request was processed and, for 200, identifies the returned resource; it does not mean the method is screened, enabled, or verified. Adyen sets `allowed=true` after merchant screening; `enabled` reports a distinct on/off state; `verificationStatus` distinguishes valid, pending, invalid and rejected. Related methods may have associated transitions. 400, 401, 403, 422, 429, and 500 are documented errors. The capture gives no idempotency, propagation, deletion/reversal, live availability, or payment authorization/capture/settlement proof. Examples show Visa and Swish partner-model shapes only.
