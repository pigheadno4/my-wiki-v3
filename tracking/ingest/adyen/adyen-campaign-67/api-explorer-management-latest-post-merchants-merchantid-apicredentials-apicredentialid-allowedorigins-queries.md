# Checked answers: api-explorer-management-latest-post-merchants-merchantid-apicredentials-apicredentialid-allowedorigins

## Q1

The 2026-11-05 pinned Management API “latest” reference describes `POST /merchants/{merchantId}/apiCredentials/{apiCredentialId}/allowedOrigins`: it adds an allowed-origin domain to the specified API credential under a merchant account. The listed environment is TEST at `https://management-test.adyen.com/v3`; the page does not establish a Live endpoint or current account eligibility. The caller needs **Management API—API credentials read and write**. Required path identifiers are `merchantId` (merchant account) and `apiCredentialId` (target credential). In the body-property table, `domain` is required; `id` and `_links` are optional, with `self` marked required only inside supplied `_links` and `href` optional. Whole-body requiredness is not independently stated. No default, limit, domain-validation rule or idempotency rule is given. A `200` body marks `domain` required, `id` and `_links` optional, and nested `self` required if its parent appears; `204` carries no additional content. ## Q2

A `200` says this configuration request succeeded and may return allowed-origin fields; `204` says it was processed without content. Neither proves that a later browser request authenticates, that an origin has propagated, that a client key was generated, or that a payment was authorized, booked or settled. The captured page requires the caller role above and lists `401` for authentication and `403` for permissions, alongside `400`, `422` and `500`; it states no idempotency, propagation, deletion/reversal or asynchronous review/approval/activation contract. Its generic error `requestId` wording (“essentially the same as `pspReference`”) is not a payment outcome. The TEST `/v3` server conflicts with the example `/v1` self link, so the example cannot settle version routing. The November 2026 snapshot is not proof of present Live access, eligibility, compliance or financial effect.
