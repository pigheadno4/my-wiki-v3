# Checked answers: api-explorer-management-latest-post-merchants-merchantid-webhooks

## Q1

The 2026-11-05 Management API “latest” snapshot describes `POST /merchants/{merchantId}/webhooks` to subscribe a merchant account to webhook notifications. It lists a TEST `https://management-test.adyen.com/v3` server and requires the caller's API credential to have **Management API—Webhooks read and write**. The required path `merchantId` is the merchant account ID; the returned optional `id` is the webhook configuration ID. In the request property table, `active`, `communicationFormat`, `type` and public recipient `url` are required; `active` must be true for sending, and formats are SOAP, HTTP or JSON. Username/password are optional basic-auth settings. The three certificate acceptance flags default false; `encryptionProtocol` lists TLSv1.3, TLSv1.2 and TEST-only HTTP, with a stated TLSv1.2 fallback; `networkType` defaults public, and the SOAP action flag defaults false and applies only to SOAP. The reference states no whole-body requirement separately, numerical limit or idempotency rule. A `200` response can include configuration ID, account reference, active/type/URL/format, certificate settings, error/password indicators, HMAC check value and optional links; `204` has no additional content. Company-level filter fields appear only in the response schema and are scoped as company-level fields. ## Q2

A `200` reports request success with configuration readback; `204` reports successful processing without content. Neither proves that Adyen emitted a webhook, that the receiver accepted it, that an HMAC key was generated, that a test passed, or that a payment was authorized or settled. `active: true` is stated as necessary for sending, not sufficient to prove delivery. The `generateHmac` and `testWebhook` links name separate operations. Authentication and permission failures are separately listed as `401` and `403`, with `400`, `422` and `500` also documented. The page states no idempotency, propagation timing, retry, deletion/reversal or asynchronous review/approval contract. Its TEST `/v3` server conflicts with `/v1` links in the response example; its request type enum includes `rreq-notification` while its response enum instead includes `terminal-api-notification`. Those captured inconsistencies and the dated TEST scope prevent treating the example as a current Live route, eligibility or compliance guarantee.
