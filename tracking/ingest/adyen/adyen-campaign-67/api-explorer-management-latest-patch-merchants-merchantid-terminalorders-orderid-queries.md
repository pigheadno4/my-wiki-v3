# C67 api-explorer-management-latest-patch-merchants-merchantid-terminalorders-orderid — original query answers

## Q1

The 2026-11-05 captured **Management API v3** reference uses `PATCH /merchants/{merchantId}/terminalOrders/{orderId}` to update the identified terminal products order under a **merchant account**. The listed server is TEST, `https://management-test.adyen.com/v3`; live requests have rate limits, without a numeric limit here. The credential needs **Management API—Terminal ordering read and write**. Required string path IDs are the merchant account and order IDs. The order must be `Placed` to update. The body can contain only fields being changed, but updating `items` requires the entire replacement array. All listed body fields are schema-optional: `billingEntityId`, `customerOrderReference`, `items` and product subfields, `orderType`, `shippingLocationId`, and `taxId`. The page says Brazil product orders do not need `billingEntityId`, and gives no defaults. A `200` response lists optional order ID, status, items, order date, billing and shipping details, customer reference and tracking URL; `204` is processed with no content. ## Q2

HTTP `200` reports request success with order details, while `204` reports processing success without a body. The `Placed` sample remains illustrative and does not prove shipment, delivery, inventory, hardware boarding or payment readiness. The lifecycle gate is `Placed`, and an `items` update replaces the whole array, so leaving out an existing item removes it. The role is required, and documented failures include `400` request problem, `401` authentication required, `403` insufficient permission, `422` validation error and `500` server failure. The page does not specify idempotency, propagation timing, asynchronous review/approval/activation, reversal or version-conflict handling. Its dated TEST listing and live rate-limit notice do not establish present account eligibility, production procurement completion, compliance, authorization, settlement or bank receipt.
