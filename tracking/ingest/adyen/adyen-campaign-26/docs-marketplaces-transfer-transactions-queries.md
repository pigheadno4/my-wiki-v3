# C26 Q1–Q2: Marketplace transfer transactions

**Q1. What does this hub help track, and which methods does it route to?**
Follow [[index]] → [[adyen-index]] → [[adyen-platforms]] → [[source-adyen-docs-marketplaces-transfer-transactions]] → [[raw/adyen/docs/marketplaces/transfer-transactions/2026-09-15]]. The Marketplace-path hub says each balance-platform fund movement yields a transaction that can be used to follow its state, availability and outcome (raw lines 15-19). It routes to real-time Transfers/Transactions webhooks and on-demand Transfers API tracking (raw lines 33-47); it gives no request schema or correlation keys itself, so use the child method guides for implementation. The page does not state an additional setup prerequisite.

**Q2. How should transfer states and later exceptions be interpreted?**
At the same route, `authorised` reserves funds, `booked` means deduction from the source balance account, `failed` is inability to initiate, `refused` is clearing-system or recipient-bank rejection, and `returned` is a transfer sent but later returned by the receiving bank (raw lines 21-31). A `booked` debit is not proof of bank receipt or finality. The guide says `failed` and `refused` do not deduct balance-account funds; notify the user and check bank details or balance, without inferring an automatic retry (raw lines 49-53). A bank return may arrive several days later; Adyen says it sends `balancePlatform.transfer.updated` with `returned`, credits the original balance account and records a separate Balance Platform Accounting Report entry (raw lines 55-61). This page does not provide a fixed return deadline, a bank statement, or proof that a particular payout succeeded.
