Q1. How is this Balance webhook configured and scoped?
A1. In this pilot, subscribe through Customer Area, set server/security details and save the webhook ID, then POST Configuration API settings with balance platform and webhook IDs, target type/id, currency, status and optional conditions (raw lines 19–39, 41–96). Targets are the platform, an account holder's balance accounts, or one balance account; role gates and 20-settings/20-conditions limits apply (raw lines 26–39, 83–90). Q2. What does an alert prove, and what ambiguities affect multi-condition behavior?
A2. It is a notification for balance changes under a pilot rule, not a transfer-booking or payout/bank-receipt outcome (raw lines 19–30, 73–96). The active-status row says **any** condition triggers, but the conditions row says **all** must be met (raw lines 88–90); no-conditions settings notify for all target changes. The narrative settings POST requires `/balancePlatforms/{id}/webhooks/{id}/settings` (raw line 75), but the example curl ends at bare `/bcl/v2/balancePlatforms` (raw line 103); do not copy it as a settings request or infer what succeeded. The account-not-found and invalid-currency “resend POST” remedies link PATCH settings paths (raw lines 214–215, 241–244), so verify endpoint before use.
