# C26 Marketplace Checkout Components — retrieval checks

**Q1. What does this guide build, and what must be set up?** It builds a Sessions-based Web Components checkout: server creates `/sessions`, client initializes `AdyenCheckout` and payment-method Components, and a webhook server receives outcomes (raw lines 52–85). The snapshot requires payment/account-management roles, API credential/key/client key, Standard webhook and TEST setup, with iframe, WebView, SSR and 3DS2/CSP conditions (lines 109–130). The `/sessions` request needs merchant account, minor-unit amount, return URL and reference (lines 479–500). **Q2. Which checkout result is safe to use for order and balance decisions?** Shopper callbacks show a current result; a missing shopper return leaves no `redirectResult`, so wait for the webhook (raw lines 878–919). The optional GET session-result `status` is fixed and `completed` means authorized in this guide, not captured/settled; do not poll it for updates (lines 937–987). The asynchronous `AUTHORISATION` webhook is matched by `merchantReference` for the order outcome (lines 989–1062), but this UI guide does not define Marketplace splits or prove user-balance booking or bank payout. Live endpoint requests for one session must remain in the same region (lines 1084–1096).
