## Q1 — Purpose, scope, and what not to infer

**Question:** Who grants partner OAuth access, and which resources can the token reach?

**Answer:** This 2026-09-15 capture of a 2023-modified guide describes a registered OAuth application asking its customer to authenticate at Adyen and authorize selected account resources; only after that authorization can a partner use the access token for API requests on the customer's behalf (raw lines 15–27, 40–54, 56–60). The app's registered scopes are all-or-nothing for the customer and cannot be extended after creation (lines 49–54). A successful token response reports the granted `scope` and merchant-account `accounts`, so a token should not be treated as company-wide or universal access (lines 222–231). The guide does not establish seller identity, merchant of record, actual customer consent, current eligibility or a payment outcome. ## Q2 — Central flow, prerequisites, and security warnings

**Question:** What role, redirect, PKCE, token and environment boundaries govern this OAuth flow?

**Answer:** Registration needs **OAuth apps manage**: the guide says newer test merchant accounts have it by default, older test accounts need Support, and live availability is limited to partner accounts (raw lines 29–38). Register a Redirect URL and scopes, save the one-time-view client secret, and send the customer to the proper test/live Adyen grant URL with exact redirect URI and scopes, `response_type=code`, random CSRF `state`, and PKCE `S256` challenge derived from a unique 43–128-character verifier (lines 40–100). The success redirect supplies a short-lived code and returned state; failure supplies an error (lines 107–138). Exchange the code through OAuth `/v1/token` with Basic client ID/secret, the associated verifier and redirect URI; the default bearer access-token lifetime is 24 hours and the refresh token is one-time-use (lines 186–231). Refresh invalidates the prior access token immediately, lets the prior refresh token expire shortly after a small retry grace, and retains scope/accounts (lines 249–290). The parameter table at line 70 calls `code_challenge` a verifier, contrary to the dedicated PKCE construction at lines 86–100; follow the distinct verifier/challenge steps. No revocation endpoint is specified. Going live requires a separately registered live client and replacing client values and endpoints (lines 299–305).
