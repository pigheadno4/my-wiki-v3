## Q1 — Captured operation and inputs

The 2026-11-02 Balance Platform API v2 `PATCH /paymentInstruments/{paymentInstrumentId}/authorisedCardUsers` reference updates a card's authorized users by replacing its entire existing list. The captured server is TEST, `https://balanceplatform-api-test.adyen.com/bcl/v2`; `latest` does not independently verify a current live endpoint. The caller supplies required `paymentInstrumentId` in the path. The request-body table marks `legalEntityIds`, an array of authorized users' legal-entity IDs linked to that payment instrument, optional; it does not separately mark the entire request body required. Its JSON example has two IDs, which is illustrative. No query parameters, default values, or schema-level array maximum are listed. Success is 204 with no documented body or response fields. The 422 error example mentions a maximum of 10 legal-entity references, but that number appears only in an example detail, not in the request schema. ## Q2 — Update effect and boundaries

The operation's documented effect is replacement of all existing authorized users for the specified card; it is not an additive append. A 204 reports successful completion of that list update, without a returned resource body. Because the field is marked optional but the prose describes replacement, the capture does not establish whether omitting `legalEntityIds` or sending an empty array clears the list. It also gives no propagation timing, asynchronous confirmation, idempotency, card activation, verification, authorization, capture, booking, settlement, failure reversal or bank-receipt contract. Errors listed are 400, 401, 403 and 422. The 400 example suggests POST for an instrument without a linked legal-entity reference; the 403 example says a card partner is not allowed yet; the 422 example mentions a 10-reference maximum. Those example details are not general eligibility proof or a complete validation contract. The dated TEST snapshot does not prove current live access or successful card payments.
