# C64 account-holder PATCH: original fixed-query answers

## Q1

`PATCH /accountHolders/{id}` is the 2026-11-02-captured Balance Platform API v2 account-holder update reference, listing only `https://balanceplatform-api-test.adyen.com/bcl/v2` as its server. The caller uses the required account-holder path `id`; this is distinct from the associated `legalEntityId` returned in the response and the optional request `balancePlatform` selector. That selector becomes required when the caller's API credentials span multiple balance platforms. The body lists optional `capabilities`, `contactDetails`, `description`, `metadata`, `primaryBalanceAccount`, `reference`, `status`, and `timeZone`; omitted parameters are generally unchanged, but an update to `metadata` deletes existing pairs omitted from the supplied metadata. Nested address, email and phone fields under optional `contactDetails` have their own required markers, and `stateOrProvince` is required for US/Canada by prose. Capability settings include `enabled`, `requested` and `requestedLevel` (`notApplicable`, `low`, `medium`, `high`). The first created balance account is the default primary balance account, and unset time zone inherits the balance platform's. The 200 body reports holder `id`, `legalEntityId`, `balancePlatform`, capability request/allowance/verification fields, status, and possible verification deadlines. Field-level limits, examples and error schemas remain at the pinned raw locators. [[source-adyen-api-explorer-balanceplatform-latest-patch-accountholders-id]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/patch/accountHolders/(id); verified raw lines 5–46, 69–133.

## Q2

A 200 says this update request succeeded and returns an account-holder resource. `requested: true` does not establish capability permission: inspect `allowed`, `enabled`, `verificationStatus` and any problems or deadlines; the example itself has `requested: true`, `allowed: false`, `verificationStatus: pending`. `suspended` temporarily disables the holder and blocks payouts; `closed` permanently disables the holder and its capabilities and is final. Metadata omission during a metadata update deletes prior pairs, despite the general unchanged-when-omitted rule. The raw lists 400, 401, 403, 422 and 500 responses, but gives no operation-specific idempotency contract, propagation timing, reversal route, live endpoint, caller grant, or proof of payment authorization, capture, booking, settlement, payout execution or bank receipt. Generic 422/500 examples concern payment instruments, so they do not establish this endpoint's account-holder failure behavior. The `latest` URL and TEST snapshot do not prove current live availability or an individual account's eligibility.
