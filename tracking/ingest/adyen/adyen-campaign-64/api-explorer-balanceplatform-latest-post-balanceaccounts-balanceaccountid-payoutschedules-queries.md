# C64 account payout schedule: original fixed-query answers

## Q1

The 2026-11-02-captured Balance Platform API v2 TEST `POST /balanceAccounts/{balanceAccountId}/payoutSchedules` applies an existing platform managed payout schedule to a balance account; the listed base is `https://balanceplatform-api-test.adyen.com/bcl/v2`. The required path ID identifies the balance account, while required body `balancePlatformPayoutScheduleId` identifies the existing platform schedule and `transferInstrumentId` the payout destination; the response's optional `id` names the separate account-level schedule. Optional configuration includes currency, description, enabled, frequency, frequencyValue, minimum/maximum payout amounts, merchant and beneficiary references, retained amount and sales-day closing time. Frequency is daily, weekdays, weekly or monthly; frequencyValue is allowed only for weekly 1–5 or monthly 1–31, with documented weekend/nonexistent-date behavior. Description has a 140-character limit and may truncate; sales-day closing time is 00:00–07:00 HH:mm:ss in the account time zone. Description, frequency, frequency value and beneficiary reference inherit platform-schedule defaults; min/max/retained amounts default to zero. The 200 body reports the account ID, platform schedule ID, transfer instrument ID, createdAt, optional account schedule ID and configuration fields. [[source-adyen-api-explorer-balanceplatform-latest-post-balanceaccounts-balanceaccountid-payoutschedules]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/post/balanceAccounts/(balanceAccountId)/payoutSchedules; verified raw lines 5–35, 58–80, 158–180.

## Q2

A 200 establishes a successful account-level schedule application and returned configuration, not a scheduled payout's execution, transfer, settlement or bank receipt. `enabled` concerns whether the schedule is active; if available funds fall below `retainedAmount`, execution is not initiated. The response does not establish destination eligibility or a transfer's outcome. The merchant `reference` stays in the schedule; the beneficiary reference is sent to recipients and payout webhooks. Request and response descriptions disagree on permitted beneficiary-reference characters (request includes hyphen/space, response lists only alphanumerics), so neither should be generalized into a validator claim. The raw lists 401, 404, 422 and 500 errors but no operation-specific idempotency, propagation, deletion/reversal, completed payout or live-server contract. Its `latest` URL and TEST capture do not prove current live availability, permissions or financial results.
