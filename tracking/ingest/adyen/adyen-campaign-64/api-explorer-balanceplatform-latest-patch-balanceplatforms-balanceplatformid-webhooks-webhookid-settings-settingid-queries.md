# C64 api-explorer-balanceplatform-latest-patch-balanceplatforms-balanceplatformid-webhooks-webhookid-settings-settingid — original fixed-query answers

## Q1

The 2026-11-02 Balance Platform API `PATCH /balancePlatforms/{balancePlatformId}/webhooks/{webhookId}/settings/{settingId}` reference describes updating the conditions for sending Balance webhooks; its captured server is the TEST `https://balanceplatform-api-test.adyen.com/bcl/v2` endpoint. The `latest` URL does not establish live or current availability. The three required string path IDs separately identify the balance platform, Balance webhook, and one setting. The API request table marks `conditions`, `currency`, `status`, `target`, and `type` optional and does not separately mark the entire body required. A supplied `conditions` item requires `balanceType`, `conditionType`, and integer `value`; the threshold value is in minor units, with four balance types and four comparison operators. `target` may refer to a balance platform, account holder, or balance account; its nested fields are marked optional in this PATCH table. `type` says to set `balance`. The 200 schema requires `currency`, setting `id`, `status`, `target.id`, `target.type`, and `type`; response examples also show `conditions`, which the response field table omits. No numeric threshold limit, default status, exact caller role, or idempotency key is specified here. A dated Platforms guide labels Balance webhooks pilot/limited availability, and its PATCH table marks `type` required, contradicting this API table. ## Q2

A 200 says the PATCH request succeeded and returns setting configuration. `active` and `inactive` describe notification configuration; neither response status proves a webhook was delivered, a balance changed, or funds were authorized, booked, settled, paid out, or received by a bank. The November API text says `active` can trigger when *any* condition is met, whereas the dated Platforms configuration guide says *all* configured conditions must match; compound-condition behavior remains unresolved in these captures. The separate dated management guide says condition updates must include all conditions to retain, that removing the last condition produces alerts for all balance changes, and that `inactive` differs from deleting a setting. This API reference itself does not specify the effect of `null` or empty `conditions`, propagation timing, a delivery guarantee, reversal behavior, version/conflict handling, or an idempotency rule. It lists 400, 401 authentication, 403 permission, 404, 422 and 500 errors; the 404 text says “The payment was not found” even though the endpoint updates a webhook setting, so that wording is not payment-outcome evidence. The examples and TEST snapshot do not prove current product eligibility, live access, or any financial result.
