# C64 balance-webhook setting: original fixed-query answers

## Q1

The 2026-11-02-captured Balance Platform API v2 TEST `POST /balancePlatforms/{balancePlatformId}/webhooks/{webhookId}/settings` configures balance-webhook trigger criteria; the listed server is `https://balanceplatform-api-test.adyen.com/bcl/v2`. Required path IDs identify the balance platform and the balance webhook, respectively; the created setting receives a separate `id` in the 200 body. Required body fields are three-character ISO `currency`, `status` (`active`/`inactive`), `target` (required `id` and `type` of `balancePlatform`, `accountHolder`, or `balanceAccount`), and `type: balance`. The optional `conditions` array has required fields per supplied condition: `balanceType` (`available`, `balance`, `pending`, `reserved`), `conditionType` (four greater/less comparisons), and integer threshold `value` in minor units. No condition-array count limit or default is stated. Higher-level settings apply below them; the most granular target setting overrides the higher levels. The response field table lists setting `id`, `currency`, `status`, `target`, and `type`; the example also includes conditions. ## Q2

A 200 establishes that the setting-creation request succeeded and returns a configuration resource. The API status row says `active` receives a balance webhook when any configured condition is met and `inactive` suppresses it even if met. But the [[source-adyen-docs-platforms-balance-updates-configure-balance-webhook|Platforms configuration guide]] says all configured conditions must match in its conditions row (guide raw line 90), while its status row says any (line 88); the Platforms Balance updates overview also says all (overview raw line 47). The captured documents do not resolve multi-condition Boolean behavior. The guide separately labels Balance webhooks pilot/limited availability (guide raw lines 19–20). Neither the response nor its sample proves a threshold crossing, event delivery, balance settlement, payout execution, or bank receipt. The captured reference lists 400/401/403/404/422/500 classes but no operation-specific idempotency, propagation timing, deletion or reversal behavior, caller grant, or live endpoint. Its 404 prose says “The payment was not found,” a mismatch with the setting route; it is not evidence that this endpoint looks up a payment. `latest` and the TEST snapshot do not prove current live eligibility or a specific account's permissions.
