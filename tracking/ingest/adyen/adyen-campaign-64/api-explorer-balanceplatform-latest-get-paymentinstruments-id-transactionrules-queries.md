## api-explorer-balanceplatform-latest-get-paymentinstruments-id-transactionrules

- Q1: `GET /paymentInstruments/{id}/transactionRules` lists transaction rules associated with a payment instrument in the 2026-11-02 Balance Platform API Explorer snapshot. The captured TEST server is `https://balanceplatform-api-test.adyen.com/bcl/v2` (v2 although the URL says `latest`). Required path `id` identifies the payment instrument; the page lists no query/body input, pagination or GET limit. A 200 response has an optional `transactionRules` array. Within an included rule object, `description`, scoped `entityKey`, `interval`, `reference`, `ruleRestrictions` and rule `type` are required; nested interval type is required, with duration required for rolling/sliding intervals and capped at 90 days or equivalent. Rule scope may name a platform, holder, balance account, instrument group or payment instrument, distinct from the path ID. Types include blockList, maxUsage, velocity and bypass; outcome defaults to hardBlock, request type to authorization, and scoreBased/enforceSCA have stated request-type gates. Score-based outcome requires a -100 to 100 score. Full restriction/operation choices and timing defaults are in the response schema. - Q2: A 200 means this GET succeeded and returns any included rule configuration, not that rules were created/changed, active at the moment of a transaction, evaluated, bypassed or enforced on a specific authorization, authentication, tokenization or bank transfer. The two active blockList rules in the example are illustrative, not proof of card activation, payment decline, booking, settlement or payout. The page lists 401 authentication, 403 permission, 400, 422 and 500 errors but no credential scheme/role, idempotency, deletion, propagation timing, asynchronous evaluation result, failure reversal or payment outcome for this GET; its generic 422/500 samples concern payment-instrument changes. Rule start/end dates, status, requestType and outcomeType qualify interpretation of a returned rule. The response schema also conflicts on bypass configuration: `ruleRestrictions` is described as containing one or more objects [raw line 47], yet bypass says to leave it empty with `overridesRule` [raw line 76], so this GET snapshot alone does not establish a valid bypass payload. Nested schema defaults describe fields rather than proving an actual decision. The `latest` URL and TEST v2 capture do not prove live eligibility or present behavior.
