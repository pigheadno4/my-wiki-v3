## api-explorer-balanceplatform-latest-get-balanceaccounts-balanceaccountid-sweeps

Q1. The 2026-11-02 Balance Platform API capture documents `GET /balanceAccounts/{balanceAccountId}/sweeps` on the TEST `https://balanceplatform-api-test.adyen.com/bcl/v2` server. It lists sweep configurations for the required path `balanceAccountId`, not a transfer execution. Optional integer query `limit` defaults to 10 items and has a 100-item maximum; optional `offset` skips items. The 200 body requires `hasNext`, `hasPrevious` and `sweeps`. Each returned sweep requires `counterparty`, ISO `currency`, sweep `id` and `schedule` with required `schedule.type`. Counterparty prose requires one of a balance-account ID, transfer-instrument ID or merchant account, although each child field is table-optional; a merchant account is limited to pull sweeps when processing payments with Adyen. Optional configuration includes direction, status, category/priorities, amount and threshold fields. The schema describes `status=active`, `type=push`, and `triggerAmount=0` defaults, mutually exclusive `sweepAmount`/`targetAmount`, and a cron expression required for cron schedules. Q2. A 200 response establishes a successful page read of associated sweep configurations and next/previous indicators. An active setting describes potential triggering, not a triggered transfer, booked debit/credit, payout, bank receipt or reversal. This GET has no request body or documented idempotency header, mutation/deletion, propagation timing or asynchronous outcome contract; separate operations and event evidence would be needed for execution. The page lists 400, 401 authentication, 403 permission, 422 validation and 500 errors, but its 422 and 500 examples describe payment-instrument update/creation rather than this list endpoint, so they do not establish sweep-specific causes or lifecycle behavior. The `latest` path and captured TEST v2 server do not prove current version, LIVE availability or account eligibility.
