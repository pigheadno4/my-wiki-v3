## Q1

The 2026-11-02 captured Balance Platform API v2 `GET /balanceAccounts/{balanceAccountId}/payoutSchedules/{id}` returns one specified managed payout schedule on a balance account. Its listed server is the TEST base `https://balanceplatform-api-test.adyen.com/bcl/v2`; the raw does not name a caller role. Both path inputs are required: `balanceAccountId` identifies the balance account and `id` identifies its applied schedule. No query inputs or request body are documented. In a 200 response, `balanceAccountId`, `balancePlatformPayoutScheduleId` (the applied platform schedule), `createdAt`, and destination `transferInstrumentId` are required; account-level response `id` and the other configuration fields are optional. Optional `enabled` reports active status; frequency supports daily, weekdays, weekly, monthly, and `frequencyValue` is allowed only for weekly 1–5 or monthly 1–31, with the documented weekend/missing-month-day initiation adjustments. Description may be truncated after 140 characters; description, frequency, frequencyValue and beneficiary reference inherit the relevant platform-schedule defaults, while min/max payout and retained amounts default to 0. The raw gives no unit for these integer amounts. ## Q2

A 200 return establishes a successful read of schedule configuration, including an applied platform-schedule ID and payout transfer-instrument ID. It does not establish that an execution was initiated, booked, settled, or received by a bank. The configuration says an execution is not initiated when balance funds are below `retainedAmount`; `enabled` denotes active status. The documented failures are 401 authentication required, 404 resource not found, 422 validation error, and 500 server failure. This GET reference specifies no idempotency, schedule deletion or propagation timing, reversal, or version-conflict behavior. Its `latest` URL and TEST host do not prove current live availability or account eligibility; the response example is illustrative configuration rather than a payout event.
