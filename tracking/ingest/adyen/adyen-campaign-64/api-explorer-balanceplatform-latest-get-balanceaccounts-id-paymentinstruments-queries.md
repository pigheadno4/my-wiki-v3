## Q1 — Captured endpoint, inputs and response

The 2026-11-02 capture describes Balance Platform API v2 `GET /balanceAccounts/{id}/paymentInstruments` as a paginated list of payment instruments associated with one balance account. Its displayed server is TEST, `https://balanceplatform-api-test.adyen.com/bcl/v2`; the `latest` URL does not independently prove current live availability. The required `id` is the balance-account identifier in the path. Optional query `status` filters payment instruments, with all statuses included by default; `limit` defaults to 10 and is capped at 100 items per page, while `offset` skips items. No request body or further conditional request field is listed. A 200 response requires `hasNext`, `hasPrevious`, and a `paymentInstruments` array. Each listed instrument's response schema requires its own `id`, associated `balanceAccountId`, `issuingCountryCode`, and `type` (`card` or `bankAccount`). Optional card and bank-account objects have their own nested fields; optional references include payment-instrument group ID and replacement IDs. This is a balance-account resource list, not a transfer-instrument or payment outcome. ## Q2 — Readback and outcome boundaries

HTTP 200 establishes that the list request succeeded and returns a page of reported instrument resources, with pagination flags for further or prior pages. It does not create, activate, modify, close or verify an instrument, and does not prove a card authorization, capture, booking, settlement, payout or bank receipt. The schema describes active, inactive, suspended and irreversibly closed status, with an active creation default subject to card form-factor/country exceptions; those are lifecycle descriptions, not GET effects or a guarantee that a card payment will succeed. The card `cvc` description expressly limits its return to a POST response for single-use virtual cards, and PAN is masked by default; the GET sample shows masked PAN and no CVC. This GET documents no idempotency, deletion, propagation, asynchronous outcome or reversal contract. Authentication and permission errors are 401 and 403, alongside 400, 422 and 500. The 422/500 examples describe changing or creating a payment instrument, so they do not establish this list endpoint's specific failures. The dated TEST capture and illustrative active cards do not prove current live eligibility or an actual transaction.
