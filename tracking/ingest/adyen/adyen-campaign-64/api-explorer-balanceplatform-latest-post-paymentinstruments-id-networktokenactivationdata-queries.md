## Q1 — Captured provisioning-data request and response

The 2026-11-02 Balance Platform API v2 `POST /paymentInstruments/{id}/networkTokenActivationData` reference creates provisioning data to add a user's payment instrument to a digital wallet. Its only shown server is TEST, `https://balanceplatform-api-test.adyen.com/bcl/v2`; the `latest` documentation URL does not independently verify current live access. Required path `id` identifies the payment instrument. The request-body table marks SDK-generated `sdkOutput` as optional, but the same row's prose says it is required to create provisioning data; the page does not separately mark the whole body required, list defaults or show a request example. The 200 response table marks `sdkInput` optional, while describing it as the activation-data block required to initialize Adyen's network-token provisioning SDK. No 200 example establishes whether the response always contains it. These fields concern provisioning data, not a network-token ID or payment result. Source: [[source-adyen-api-explorer-balanceplatform-latest-post-paymentinstruments-id-networktokenactivationdata]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/post/paymentInstruments/(id)/networkTokenActivationData; verified pinned raw lines 5–33.

## Q2 — Acceptance, token status and outcome boundaries

HTTP 200 means this provisioning-data request succeeded under the documented response contract; it does not prove the instrument was added to a wallet, that a network token was created or activated, or that cardholder authentication or a payment authorization, capture, booking or settlement succeeded. The `sdkOutput` table/prose requiredness conflict must remain visible, and `sdkInput` is optional in the response schema even though the downstream SDK initialization needs it. This endpoint states no idempotency, token lifecycle, deletion, propagation timing, asynchronous outcome, retry or reversal contract. It lists 400, 401 authentication, 403 permission, 422 validation and 500 server errors, without a named caller role. Its 422/500 JSON examples describe payment-instrument update or creation, not this provisioning-data operation. The dated TEST capture is not current eligibility or wallet/token-state proof. Source: [[source-adyen-api-explorer-balanceplatform-latest-post-paymentinstruments-id-networktokenactivationdata]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/post/paymentInstruments/(id)/networkTokenActivationData; verified pinned raw lines 20–33, 36–133 and 135–202.
