# C64 payment-instrument PATCH: original fixed-query answers

## Q1

The 2026-11-02-captured Balance Platform API v2 TEST `PATCH /paymentInstruments/{id}` updates the payment instrument identified by required path `id`; the only listed server is `https://balanceplatform-api-test.adyen.com/bcl/v2`. Its central lifecycle rule says that once an instrument is active, only status can be updated; cards created inactive may change associated `balanceAccountId`, and the request field repeats an inactive-only restriction. Body `balanceAccountId`, `card`, `status`, `statusReason`, and `statusComment` are table-optional, but optional `card` has nested required markers for brand, brandVariant, cardholderName, formFactor, and further required fields within optional configuration/deliveryContact. Authentication is conditionally described for EEA/UK online or wallet-capable cards. Status values are active, inactive, suspended and irreversible closed; creation defaults to active with card exceptions, which is not a PATCH omission rule. `statusReason: other` requires `statusComment`. The 200 body requires payment-instrument `id`, associated balance-account ID, issuing-country code, and instrument type (`card`/`bankAccount`), with optional status, card and bank details. Card CVC is described as only in a POST response for single-use virtual cards; PAN is masked by default and only returned for single-use virtual cards, so the PATCH readback example's masked number is not full card-data disclosure. [[source-adyen-api-explorer-balanceplatform-latest-patch-paymentinstruments-id]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/patch/paymentInstruments/(id); verified raw lines 5–61, 78–149, 251–303.

## Q2

A 200 establishes successful resource update and reported instrument state, not payment authorization, capture, settlement or bank receipt. Active status is described as usable for payments but does not prove a particular payment or account's eligibility. Inactive balance-account changes and status-only changes after activation constrain the lifecycle; closed is final. The generic 422 example says balanceAccountId can change in `Inactive or Requested`, conflicting with inactive-only operation prose and request field, while `Requested` is absent from the PATCH status enum. Preserve that conflict and do not treat the example as a permission grant. The response status-reason enum also includes `transactionRule`, absent from the request enum. The raw lists 400/401/403/422/500 responses but gives no operation-specific idempotency, propagation time, reversal after closure, live server or credential grant. `latest` and the TEST capture do not establish current live availability or financial results.
