## Q1 — Captured endpoint, input and response

The 2026-11-02 Balance Platform API v2 `GET /paymentInstruments/{id}` reference returns details of one payment instrument. The displayed server is TEST, `https://balanceplatform-api-test.adyen.com/bcl/v2`; the `latest` route does not independently prove a current live version. The caller supplies the required payment-instrument `id` in the path. The page lists no query fields or request body. Its 200 response schema requires the instrument's `id`, linked `balanceAccountId`, `issuingCountryCode`, and `type`, which can be `card` or `bankAccount`. Optional type-dependent card or bank-account objects carry nested detail; nested required fields do not make their optional parent objects request inputs. Other optional response identifiers include payment-instrument group ID and replacement IDs, with optional status and reason/comment. The `bankAccount` branch describes business-account details, while the `card` branch describes issued-card details. Source: [[source-adyen-api-explorer-balanceplatform-latest-get-paymentinstruments-id]]; https://docs.adyen.com/api-explorer/balanceplatform/latest/get/paymentInstruments/(id); verified pinned raw lines 5–17 and 19–90.

## Q2 — Readback, lifecycle and financial boundaries

HTTP 200 establishes a successful resource read and reports the instrument's fields; it does not create, activate, suspend, close or verify the instrument, and does not prove authorization, capture, booking, settlement, payout or bank receipt. The status description distinguishes active, inactive, suspended and permanently closed, with an active creation default subject to card form-factor and issuing-country exceptions. The GET sample reports `active` but includes a January 2024 card expiration in this 2026 capture, so it cannot prove current usability. The response schema says CVC appears only in a POST response for a single-use virtual card and PAN is masked by default; the GET sample shows a masked number and no CVC. This endpoint defines no idempotency, propagation, asynchronous outcome, deletion or reversal contract. It lists 400, 401 authentication, 403 permission, 422 validation and 500 server errors. The 422 and 500 examples concern changing a balance-account link or creating a payment instrument, not GET-specific behavior. The dated TEST snapshot does not prove current live eligibility.
