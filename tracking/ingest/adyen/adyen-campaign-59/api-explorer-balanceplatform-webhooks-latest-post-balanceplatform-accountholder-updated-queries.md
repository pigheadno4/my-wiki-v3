# C59 accountHolder.updated fixed-query answers

## Q1

The 2026-09-15 captured Balance Platform webhook reference says Adyen sends `balancePlatform.accountHolder.updated` after a successful account-holder update (raw lines 5–7, event `type` in example lines 78–80 and 231–233). It states no explicit API version beyond the `latest` documentation route. Top-level `data`, `environment` and `type` are required, with `environment` test/live; `timestamp` is optional and is the queue time (raw `## Parameters > ### Request body`, lines 11–32). `data.balancePlatform` and `data.accountHolder` are optional; if `accountHolder` is present, its `id` and `legalEntityId` are required in the table, while `balancePlatform`, `capabilities`, `status`, `reference`, `primaryBalanceAccount` and other holder fields are optional (lines 15–29). The optional status can be active, suspended or permanently closed; suspended blocks payouts, and the page's examples show capability verification errors and `allowed: false` even with holder status active (lines 26, 36–82, 84–235). ## Q2

This event indicates a successful account-holder update, not verified legal-entity data, approved capabilities or financial movement. The test example has an active holder with `sendToTransferInstrument.allowed: false` and `verificationStatus: invalid`; the live example also has `allowed: false` and pending status (raw lines 36–82, 84–235). The metadata field description says omitted existing key-value pairs are deleted during a metadata update, but an event does not prove metadata was changed (line 22). The response section says any `2xx` accepts the webhook (lines 236–244); it does not establish ordering, retry, deduplication, signature mechanics or final capability verification. `latest` is only the captured route label, with no current-version proof.
