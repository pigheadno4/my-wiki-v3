## Q1

Adyen says it sends the incoming `balancePlatform.transfer.created` event when there are platform fund movements (raw lines 5–7). The separately captured [[raw/adyen/api-explorer/transfer-webhooks/latest/overview/2026-09-15|family overview]] is headed Transfer webhooks v4 (overview raw line 5). The request-body table requires top-level `data` and `environment`; it marks top-level `type` and `timestamp` optional (endpoint raw lines 14, 115–117). Within `data`, amount with minor-unit value/currency, category and status are required (lines 19–21, 32, 94). Categories include bank, card, internal, issuedCard, platformPayment and topUp (line 32). Account-holder, balance-account, counterparty, instrument, event and reference IDs are separate optional identities (lines 15–18, 22–26, 34–39, 49–68, 77–89). Event history distinguishes accounting and tracking, and `transactionId` is only sent for accounting events that change balances (lines 50–68). A future execution date keeps status `received` and reason `pending` until that date (lines 70–72); nested ultimate-party descriptions impose some category-specific conditions (lines 103–113). The four examples are TEST snapshots of incoming internal, two initiated top-up routes and outgoing bank transfers (lines 119–362), not a universal category/status mapping.

## Q2

`status` examples distinguish `received` request creation, `authorised` reserve, `booked` balance-account deduction, `refused` Adyen rejection, `failed` counterparty-bank rejection and `returned` bank return (raw line 94). The four created-event examples all show `received` and do not prove booked funds or bank receipt (lines 121–362). Optional `sequenceNumber` helps reconstruct per-transfer order if delivery is out of order (line 93), but the page does not guarantee delivery order, retries or deduplication. The response `2xx` only accepts the webhook (lines 363–371). It gives no event-specific authentication/signature guarantee, and captured `latest` plus overview v4 do not prove the current served version. The request/transfer lifecycle needs later status and accounting/tracking evidence before financial-state conclusions.
