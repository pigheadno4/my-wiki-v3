## Q1 — Purpose, scope, and what not to infer

**Question:** What does this Adyen page explain, and what must a reader not infer from it?

**Answer:** It is a 2026-09-15 capture of Adyen's transaction-description guide: how a merchant can inspect and configure the shopper-facing charge description in the **live** Customer Area at merchant-account/store scope or through the **live** Management API at payment-method scope. The dynamic request value is a separate per-payment input. It does not prove a particular merchant's current setup, payment-method support, actual bank rendering, or a completed payment. The supported-method lists and wallet-underlying-card condition are at raw lines 304–335. ## Q2 — Central capability, prerequisites, and warnings

**Question:** How can a merchant set a static, dynamic, or combined transaction description, and which constraints or exceptions matter?

**Answer:** The options are a static DBA, a payment-request `shopperStatement`, or DBA plus that statement (raw lines 46–77). Dynamic values require both the setting and the request field; omitted dynamic request text falls back to DBA, and a per-method Management API setting overrides general Customer Area settings (lines 68–77, 79–92). Customer Area checking/changing needs Merchant admin or Change payment methods; Management API checking can use Payment methods read or read and write, but configuration needs read and write (lines 98–143, 154–167, 218–241). Configuration is live only; the DBA/dynamic/combined portion is capped at 22 characters including spaces and truncated before city/country are added (lines 26–44, 144–152). A single Customer Area change and a Management API method change are described as immediate for their scoped transactions; CSV changes take up to one calendar day, have a 10 MB file cap, and newly added methods default to DBA after a Customer Area change (lines 36–38, 154–162, 169–216, 241). Ecommerce sends `shopperStatement` through Checkout `/sessions` or `/payments`; POS uses Terminal API `SaleToAcquirerData` (lines 243–248). Localized ecommerce values and Japan routes have conditional locale/channel behavior, including `shopperStatement` fallback for missing localized content or cross-border transactions (lines 250–302). Only listed methods support customization, and wallet behavior follows a listed underlying card brand (lines 304–335).
