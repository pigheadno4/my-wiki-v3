# C23 query check: Classic notifications

Q1. Why are notifications needed and how are they configured? In this Classic guide, Platforms API create/update/delete calls are asynchronous and notifications to configured server URLs carry final results (raw lines 19–21). POST `/createNotificationConfiguration` takes a notification URL and chosen event types; get, list, update, delete and test endpoints follow (raw lines 33–35, 92–93, 131–133, 184–186, 245–247, 291–293). Q2. What acknowledgment/failure boundary and sample contradictions matter? The server acknowledges each notification with `[accepted]`; after no acknowledgment within 10 seconds the guide says Adyen queues endpoint notifications and retries at increasing intervals, then every 8 hours for seven days (raw lines 268–289). At-least-once delivery requires handling repeats. Deletion uses the `notificationIds` array (raw lines 245–257), and a test response is only test diagnostics (raw lines 291–371). Create/update examples request API v6 and `SSL` but show v5 and `SSLInsecureCiphers` responses; the get-one request ID 20272 differs from response ID 2 (raw lines 45, 61, 73, 87, 103, 124, 197, 214, 226, 240). Do not treat these sample mismatches as live configuration behavior.
