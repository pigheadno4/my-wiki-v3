Q1. How does a Classic platform request Score signal notifications, and what activation step follows?

For a new account-holder risk signal, the Classic guide offers subscription to `SCORE_SIGNAL_TRIGGERED` (pinned raw 19–25). POST `/createNotificationConfiguration` with the target `notifyURL` and event configuration including `SCORE_SIGNAL_TRIGGERED`/`INCLUDE`, or POST `/updateNotificationConfiguration` for an existing `notificationId` (29–49, 72–100). After setup, notify Adyen so it can turn on the webhook notification (27). These are Classic Notification API v6 TEST examples, not modern Platforms setup or evidence that live delivery has started (35–36, 80–81). Q2. What example conflict and outcome boundary must the reader keep?

The create request has `active: false` but its response has `active: true` (raw 40–49, 55–69); the update example sends and returns false (84–123). These examples do not establish how activation works; Adyen's separate enablement step still applies (27). The sample event is `live: "false"`, with `accountHolderCode`, `riskScore: 80` and an `EmailSyntaxCheck` signal (126–147). A signal/score is for review, not confirmed fraud or proof of a blocked payout, suspended holder or completed refund (companion Score overview; this page only configures notifications).
