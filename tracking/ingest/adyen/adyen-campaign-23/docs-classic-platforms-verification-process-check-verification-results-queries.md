# C23 query check: Classic verification results

Q1. Where can a Classic platform read verification checks, and which fields identify the result? The page names `ACCOUNT_HOLDER_VERIFICATION` notifications, POST `/getAccountHolder` with `accountHolderCode`, and Customer Area KYC; the latter needs the Merchant MarketPlace role (raw lines 19–25, 27–34, 71–94). Check `type`, `status`, summary code/description and `requiredFields` in the notification or API response (raw lines 29–34, 96–99). This is a Classic guide, not the current Platforms capability API. Q2. Which statuses justify correction, which stop retry, and what is version-specific? `INVALID_DATA` invites correction; `RETRY_LIMIT_REACHED` allows retry only for some checks, while `FAILED` is final and sets the account holder to suspended (raw lines 152–158, 164–167). Identity and payout-method retry limits route to photo ID and bank statement respectively (raw lines 171–187). For company/nonprofit `INVALID_DATA`, inspect `kycCheckCode`: v5+ uses its company-code list, v4 and earlier name `1604`; for matching cases, the guide offers registration-document upload and requires it after three matching attempts (raw lines 189–202). `PAYOUT_METHOD_VERIFICATION` replaces earlier bank-account/card types starting with notification v6 (raw line 143). A sample `INVALID_DATA` notification is not proof of an actual entity's approval or suspension (raw lines 36–71).
