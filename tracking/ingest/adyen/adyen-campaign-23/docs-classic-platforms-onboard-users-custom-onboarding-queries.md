# C23 Classic Platforms custom-onboarding retrieval checks

## Q1 — What must the platform implement for custom Classic account-holder onboarding?

For this older Classic route, the platform must collect data for Adyen's verification checks; the guide recommends Hosted Onboarding as simpler but allows a custom flow (raw lines 19–21). The platform chooses upfront versus staggered collection, retrieves country/legal-entity requirements, creates an account holder and retains `accountHolderCode`, updates missing details, listens for verification results and uploads documents when needed (raw lines 23–43, 45–55, 86–104). The guide's API example uses Classic Account API v6 in test (raw lines 60–77). ## Q2 — What does creation or an API response fail to prove?

The page says a newly created holder can process payments immediately, while a later tier or missing/invalid data can disable payouts until verification succeeds (raw lines 41–51, 84). For each failed verification check, the holder must supply the requested information within the linked deadline; the page gives no duration here, and higher-tier payouts resume only after information is sent and verification succeeds (raw line 84). HTTP 200 or 202 on `updateAccountHolder` is not the business-logic or resource-update gate: await `ACCOUNT_HOLDER_UPDATED`, and use `ACCOUNT_HOLDER_VERIFICATION` for check results (raw lines 79–88). Document upload is also asynchronous; its sample `pspReference`/empty `verification` object and average timing do not prove approval (raw lines 135–147). The `ID_CARD_FRONT` document row is self-referential, so the paired-front/back requirement needs the detailed document guide (raw lines 106–115).
