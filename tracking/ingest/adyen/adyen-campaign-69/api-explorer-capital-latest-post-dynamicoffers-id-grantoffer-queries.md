# api-explorer-capital-latest-post-dynamicoffers-id-grantoffer — actual query answers

## Q1

Captured Capital API `POST /dynamicOffers/{id}/grantOffer` creates a static offer for the financing amount a user selected from the dynamic offer identified by required path `id`. TEST and live servers are `https://balanceplatform-api-test.adyen.com/capital/v1` and `https://balanceplatform-api-live.adyen.com/capital/v1`, each subject to 30 requests per minute. The request-body table marks `amount` required, with three-character ISO currency and integer minor-unit value required within it; it does not separately state whether the whole body is required. No operation-specific role, default, query input or idempotency rule appears. The `200` response requires `accountHolderId`; static-offer `id`, prospective payout amount, loan/cash-advance type, validity times, fee and repayment details are optional top-level fields. Fee and repayment nested required members apply only under present parents; APR/repayment percentages are in basis points, term lengths in days, and maximum term is loan-only. [[source-adyen-api-explorer-capital-latest-post-dynamicoffers-id-grantoffer]] https://docs.adyen.com/api-explorer/capital/latest/post/dynamicOffers/(id)/grantOffer — raw lines 5–65.

## Q2

A `200` establishes success for static-offer creation from the selected dynamic-offer amount. It does not establish user acceptance, grant request, review or approval state, financing eligibility, grant-account activation, disbursement, settlement, bank receipt or repayment. The dynamic-offer `id`, returned offer `id`, and `accountHolderId` are different identifiers. The only documented failure is `422` validation; the page supplies no reversal/delete flow, asynchronous status contract, version conflict behavior or idempotency rule. Its TEST/live v1 endpoints and 30-per-minute limits are facts of the November 2026 capture, not proof of current access or live authorization.
