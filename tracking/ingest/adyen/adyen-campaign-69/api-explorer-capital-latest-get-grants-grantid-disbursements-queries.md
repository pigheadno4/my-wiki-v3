# C69 api-explorer-capital-latest-get-grants-grantid-disbursements — original query answers

## Q1

The 2026-11-07 Capital API `latest` capture documents `GET /grants/{grantId}/disbursements` on Test and Live `/capital/v1` servers. It lists records related to the grant identified by required string path `grantId`; no body, query filter, pagination, default, or count limit is shown. The `200` body requires a `disbursements` array. Each record requires account-holder and balance-account recipient IDs, grant and disbursement IDs, amount, balances, fee, and repayment objects. `amount` has a three-character currency and integer minor-unit value. `balances` has currency, fee, principal, and total repayable, with total defined as fee plus principal. `repayment` has required `basisPoints` and `updateDescription`; basis points express the configured share of incoming net volume deducted for repayment. Optional `fundsCollections` lists repayment-collection account information and may identify `UnscheduledRepayment` or `Revocation`. The endpoint page names no caller role or authentication method. ## Q2

A `200` establishes successful lookup under this captured contract and returns disbursement records for the specified grant; it does not itself initiate funding. Recipient balance-account ID and disbursement amounts describe the returned records, not independent proof of transfer booking, external bank receipt, present eligibility, or completed repayment. The page lists 404 for an entity not found and 422 for request validation; their top-level problem fields are optional, while `message`, `name`, and `value` are required only within an `invalidFields` item if that optional array is present. This GET page states no credential role, idempotency key, deletion or reversal behavior, propagation timing, review/approval/activation transition, dispute or conflict rule, or later status semantics. Its Test/Live v1 URLs and 2026-11-07 snapshot do not establish current account eligibility or financial finality.
