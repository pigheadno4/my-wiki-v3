# C69 Issuing dispute detail GET — original query answers

## Q1

The 2026-11-07 `GET /disputes/{id}` reference reads one raised dispute by its required unique dispute ID. The companion overview identifies the `transfers-api` URL family as Raise disputes API v4 for Adyen-issued-card transaction disputes and fraud reports, separate from funds-transfer operations and merchant acquiring dispute defense. The operation lists TEST and Live `/btl/api/v4` servers. The overview says Adyen supplies credentials, accepts `X-API-Key` or basic authentication, and sets up an additional API role; the GET itself names no finer role. It gives no query or request body, default, limit, pagination, or idempotency rule. On `200`, `transactionId` and `type` are required in the response schema; `id`, `status`, ARN, description, disputed amount, and reason-detail objects are optional. Conditional reason fields apply when their matching type is used. Types listed here are `cancelled`, `duplicate`, `fraud`, `notAsDescribed`, `notDelivered`, and deprecated `other`; the status enum lists `draft`, `submitted`, `closed`, `won`, `chargeback`, and `secondPresentment`. ## Q2

`200` says the detail request succeeded and returns a dispute representation; it does not create, submit, close, win, reverse, or financially settle a dispute. The schema marks `status` optional. Its text says creation can set only `draft`, updates can set `submitted` or `closed`, and its broader enum also includes later outcome states; a returned state is a lookup at that time. The `fraudInfo.reportOnly` description says true reports fraud without further action such as chargeback request or fee reversal, with false as its stated default. `other` is deprecated here with an explicit instruction not to create or submit it. The older September POST reference instead calls `other` beta and omits `cancelled` and `notAsDescribed` from its type enum; neither snapshot establishes current creation support for every listed detail type. The GET lists `401` authentication-required, `403` insufficient-permissions, and `422` validation errors; it does not specify retry, asynchronous approval, reversal, propagation, version-conflict, or financial-finality rules. Listed Live URLs and status values do not prove current account eligibility, a successful chargeback, fee recovery, or bank receipt.
