# api-explorer-transfers-latest-get-transactions-id — actual query answers

## Q1

Captured Transfers API `GET /transactions/{id}` returns one transaction by its required transaction ID. The reference marks Transfers API versions 1 and 2 deprecated and lists TEST `https://balanceplatform-api-test.adyen.com/btl/v4`; it gives no live server or operation-specific caller role. No body, query inputs, defaults, limits or idempotency rule are specified. A `200` response requires account-holder and balance-account objects, a balance-platform ID, transaction ID, amount currency and numeric minor-unit value, booking date, value date and `pending` or `booked` status. Holder/account nested IDs and references are optional. Optional payment-instrument and transfer objects, beneficiary reference, creation date and description add context; `transfer.reference` is marked required only when the optional `transfer` object is present. The transaction ID, transfer ID, balance-account ID, account-holder ID and balance-platform ID are separate identities. ## Q2

A `200` returns a transaction record. `pending` means still pending; `booked` means booked to the balance account, while `valueDate` describes when the transfer amount becomes available there. The table requires booking and value dates yet also permits pending status, without explaining the pending-date combination. The example's negative EUR amount and booked transfer are illustrative, not universal. This read operation supplies no transfer approval/review/activation outcome, deletion or reversal behavior, asynchronous notification contract, or recipient-bank receipt. The page specifies 401 authentication, 403 permissions, 422 validation and 500 processing errors; it does not give an operation-specific role or idempotency behavior. The November 2026 TEST snapshot is not current eligibility, compliance, payment authorization, settlement or external bank-credit proof.
