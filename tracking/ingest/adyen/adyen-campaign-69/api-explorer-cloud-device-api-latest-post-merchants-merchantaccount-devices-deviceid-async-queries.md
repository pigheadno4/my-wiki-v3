## Q1

`POST /merchants/{merchantAccount}/devices/{deviceId}/async` is the captured Cloud Device API v1 route for sending a JSON Terminal API request to a payment device and receiving the Terminal API response asynchronously. The API credential needs the Cloud Device API role. Both path parameters are required: `merchantAccount` is the merchant-account identifier; `deviceId` identifies the destination device and must equal the request's `MessageHeader.POIID`. For a payment terminal, the ID uses model–serial format; for a Mobile solution, it is the SDK installation ID. The body is a JSON Terminal API request; this page sends its structure to the Terminal API request-type references and specifies no body-property table. The captured servers are `https://device-api-test.adyen.com/v1` and live v1 endpoints for Australia, East Asia, Europe, and the United States. The page states no defaults or limits. Its `200 Success` section lists no response fields. ## Q2

HTTP `200 OK` establishes that the payment device was online and Adyen's backend sent the request. The actual Terminal API response arrives later as an event notification webhook at the event notification endpoint. Thus this HTTP response alone establishes neither the Terminal API operation's result nor payment authorization, capture, settlement, or device/account eligibility. The captured page requires the Cloud Device API role and matching `deviceId`/`POIID`, but gives no idempotency rule, webhook timing guarantee, response payload fields, or lifecycle, deletion, reversal, review, approval, or activation semantics for this route. Its test and region-specific live server list and 2026-11-07 raw capture are documentation scope, not current account-specific enablement.
