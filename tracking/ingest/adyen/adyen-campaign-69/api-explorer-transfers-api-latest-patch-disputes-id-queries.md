# C69 original query answers: api-explorer-transfers-api-latest-patch-disputes-id

## Q1

The captured 2026-11-07 `PATCH /disputes/{id}` reference at a `transfers-api` URL documents Balance Platform BTL v4 test and live servers. It updates a raised Issuing dispute, identified by required path `id`, or moves draft status to submitted or closed. The PATCH body table marks `cancelledInfo`, `duplicateInfo`, `fraudInfo`, `notAsDescribedInfo`, `notDeliveredInfo`, `otherInfo`, and `status` optional as top-level fields, but says the matching reason-information object is required for a dispute of that type. The `other` type is deprecated and must not be created or submitted. The request `status` row is typed object and describes submitted/closed update values; no nested request-status schema or request example is given. The 200 response is a dispute representation with optional status, ID, ARN, amount and reason data, plus response-required `transactionId` and `type`; those response fields are not declared PATCH inputs. The only amount default appears in the response `disputedAmount` description (entire transaction amount if no amount is provided), not in a PATCH body field. See [[source-adyen-api-explorer-transfers-api-latest-patch-disputes-id]] and [the captured API reference](https://docs.adyen.com/api-explorer/transfers-api/latest/patch/disputes/(id)), raw lines 5–36 and 38–121.

## Q2

A 200 says the update request succeeded; submission sends the raised dispute to the card scheme for review and acquirer defense, while closure removes card-scheme review eligibility. Both submitted and closed are final for editing, so supporting attachments are to be uploaded through `POST /disputes/{id}/attachments` before submission. Neither 200 nor submission establishes a card-scheme win, chargeback or fee reversal, financial booking, or bank receipt. The raw documents 401 authentication required, 403 insufficient permissions, and 422 validation error with structured optional error fields, but names no specific role or idempotency rule and gives no asynchronous outcome timing or reversal procedure. The request/response `status` type conflict (object versus string) leaves the input JSON shape unresolved; the November capture and `latest` URL do not prove present eligibility or behavior. See [[source-adyen-api-explorer-transfers-api-latest-patch-disputes-id]] and [the captured API reference](https://docs.adyen.com/api-explorer/transfers-api/latest/patch/disputes/(id)), raw lines 7–17, 27–41, 119, and 124–178.
