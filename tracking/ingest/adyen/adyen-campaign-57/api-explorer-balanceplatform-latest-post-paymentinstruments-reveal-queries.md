# Fixed query check: POST /paymentInstruments/reveal

Canonical source: `wiki/sources/adyen/source-adyen-api-explorer-balanceplatform-latest-post-paymentinstruments-reveal.md` — https://docs.adyen.com/api-explorer/balanceplatform/latest/post/paymentInstruments/reveal

## Q1: For `balanceplatform/latest/post/paymentInstruments/reveal`, what purpose and object identities does this captured page establish, and which required/conditional fields, permissions, prerequisites or consequential constraints govern use?

The 2026-09-15 API Explorer capture describes `POST /paymentInstruments/reveal` as returning encrypted PAN, CVC and expiry for a specified **card payment instrument**, to decrypt and show in a user interface (raw lines 5–15). It names the **Bank Issuing PAN Reveal Webservice** credential role (lines 17–19) and a Balance Platform API v2 **test** base URL (line 22). Its request-body table marks `encryptedKey` and `paymentInstrumentId` required (lines 26–30). The former is a symmetric session key encrypted with an Adyen public key obtained separately through linked `GET /publicKey` version-2 documentation; the latter identifies the target card instrument. The existing detailed Issuing guide at `wiki/sources/adyen/source-adyen-docs-issuing-manage-card-data-reveal-card-details.md` names a different **Bank Issuing PaymentInstrument Reveal Webservice** role; the labels conflict, so the two sources should not be silently reconciled. The API reference does not provide a purpose/format parameter or full key-generation/decryption procedure; see the separate `wiki/sources/adyen/source-adyen-api-explorer-balanceplatform-latest-get-publickey.md` and Issuing guide for their own scoped contracts.

## Q2: What do the response/errors establish, and which lifecycle, deletion, verification/approval, propagation, asynchronous financial outcome, version/environment or missing-evidence boundaries prevent broader inference?

`200` means the reveal request succeeded and includes required `encryptedData`, encrypted using the supplied key (raw lines 32–40). It does not prove client decryption, delivery to the intended cardholder, card activation or any authorization/payment/funds outcome. The page lists `400`, `401`, `403`, `422` and `500` errors with common problem fields (lines 43–140). The generic `422` example refers to changing a `balanceAccountId` at certain statuses, and the generic `500` example refers to creating a payment instrument (lines 183–209); neither gives a reveal-specific mutation or lifecycle rule. The page describes no deletion, approval, propagation, callback or asynchronous outcome. Its server is test v2 (line 22), while `latest` in the URL is not proof of the currently deployed version, live endpoint, product eligibility or permission grant.
