# Fixed query check: POST /terminals/scheduleActions

Canonical source: `wiki/sources/adyen/source-adyen-api-explorer-management-latest-post-terminals-scheduleactions.md` — https://docs.adyen.com/api-explorer/Management/latest/post/terminals/scheduleActions

## Q1: For `Management/latest/post/terminals/scheduleActions`, what purpose and object identities does this captured page establish, and which required/conditional fields, permissions, prerequisites or consequential constraints govern use?

The captured Management API v3 **test** endpoint schedules one terminal action for specified terminal IDs (raw lines 5–24). A request may address at most 100 terminals. The endpoint says an erroneous terminal ID prevents scheduling for all IDs (lines 9–15); the linked Android guide narrows that all-or-none result to `422` ID validation, while a later `200` may mix per-terminal planning successes and failures (Android guide raw lines 1290–1333). It requires the **Management API—Terminal actions read and write** credential role (lines 17–19). The API-reference body table marks `actionDetails`, `scheduledAt`, `storeId` and `terminalIds` **No** (lines 26–34). In contrast, the linked Android guide marks `actionDetails` and `terminalIds` **required** for its Android scheduling flow (guide raw lines 757–766); do not infer safe omission from the API table. If `storeId` is supplied, every listed terminal must be assigned to that store; the terminal IDs can be found through `GET /terminals` (lines 33–34). `scheduledAt` uses the documented offset timestamp form. The API reference says an empty value sends at the next maintenance call as soon as possible, and a specified date sends after that time in the terminal's time zone (line 32). The Android guide adds a WebSockets exception: implementation may be immediate when unscheduled or at the specified time when scheduled (guide raw lines 36–44). Examples show Android app installation and certificate removal, but the page does not enumerate all allowed `actionDetails.type` values (lines 36–87). The live rate-limit note gives no numerical limit (line 21).

## Q2: What do the response/errors establish, and which lifecycle, deletion, verification/approval, propagation, asynchronous financial outcome, version/environment or missing-evidence boundaries prevent broader inference?

`200` acknowledges the scheduling request. It can contain per-terminal action IDs and terminal IDs in `items`, plus `terminalsWithErrors`, `totalErrors` and `totalScheduled`; the last explicitly does **not** mean execution happened (raw lines 88–104). The linked Android guide says `422` ID-validation failure schedules none, whereas after ID validation `200` can include planning failures in `totalErrors` alongside scheduled actions in `totalScheduled` (guide raw lines 1290–1333). The two `200` examples show three planned actions and zero errors; those are illustrative, not actual device outcomes (lines 206–265). The `422` example reports empty terminal IDs (lines 268–279). Other listed errors are `400`, `401`, `403` and `500` (lines 107–204). The API reference describes sending at a maintenance call, while the Android guide supplies a WebSockets exception for immediate or specified-time implementation (guide raw lines 36–44). Neither `scheduledAt` nor a successful response proves that a terminal was online, received or completed the action, or became payment-ready. The separate guide at `wiki/sources/adyen/source-adyen-docs-point-of-sale-android-terminals-deploy-apps-terminal-actions-api.md` describes querying action status after scheduling; that later read is outside this endpoint. The raw shows v3 test only (lines 23–24); `latest` and the live rate-limit note do not establish a current live endpoint or deployment result.
