# Fixed query check: GET /transactions

Canonical source: `wiki/sources/adyen/source-adyen-api-explorer-transfers-latest-get-transactions.md` — https://docs.adyen.com/api-explorer/transfers/latest/get/transactions

## Q1: For `transfers/latest/get/transactions`, what purpose and object identities does this captured page establish, and which required/conditional fields, permissions, prerequisites or consequential constraints govern use?

The captured `GET /transactions` lists transactions associated with a balance account, account holder or balance platform; the base URL shown is Transfers API v4 **test** (`raw` lines 5–22). It requires `createdSince` and `createdUntil` ISO 8601 creation-time bounds and at least one of `balanceAccountId`, `accountHolderId` or `balancePlatform` (lines 11–17, 31–37). Supplied holder/account IDs must relate to each other. `paymentInstrumentId` is an optional filter, but needs one of those scopes and a relation to any supplied holder/account ID (lines 34–37). `limit` defaults to 10 and has maximum 100; `sortOrder` is by creation date with default `asc`; `cursor` comes from a prior response (lines 29–33). Each result has a **transaction** `id`, while optional `transfer.id`/`reference` identify a related transfer (lines 52–80). `amount.value` is in minor units; response fields also include account-holder, account and platform identities and booking/value dates. The page's `403` error denotes insufficient permissions but does not name a credential role (lines 103–104). The separate Business Accounts guide at `wiki/sources/adyen/source-adyen-docs-business-accounts-transactions.md` names a product-context role and prerequisites; the API reference does not assert those across all platform contexts.

## Q2: What do the response/errors establish, and which lifecycle, deletion, verification/approval, propagation, asynchronous financial outcome, version/environment or missing-evidence boundaries prevent broader inference?

`200` establishes a successful read; `data` and `_links` are marked optional in the top-level schema, with next/previous page links where applicable (raw lines 39–52). Transaction `status` values are `pending` and `booked`; `booked` is explicitly booking to the balance account, while `bookingDate` and `valueDate` describe balance-account booking and availability dates (lines 65–80). The four illustrated signed transactions and one next-page cursor are examples, not an account balance, full ledger, executed transfer or beneficiary-bank receipt (lines 162–273). Errors are `401` authentication, `403` permission, `422` validation and `500` server failure (lines 83–160). The page gives no deletion, transfer approval, final external delivery or async propagation guarantee. It says Transfers API v1/v2 are deprecated and shows v4 **test** (lines 7, 21–22); the `latest` URL does not prove the live/current version. The separate Business Accounts guide supplies scope-specific sign and pending/booked interpretations but does not turn this list read into final payout evidence.
